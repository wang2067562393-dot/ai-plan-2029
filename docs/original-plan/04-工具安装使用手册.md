## 4.0 三条环境铁律

- **铁律一：微调环境和部署环境必须分开。** 微调环境装 `torch + bitsandbytes + peft + trl`，部署环境只装 `onnxruntime-gpu` 或 `llama-cpp-python`。两者混装会让 onnxruntime 与 torch 争夺 CUDA 运行时 DLL。
- **铁律二：能原生跑的就原生跑。** `uv`、`PyTorch`、`timm`、`Ultralytics`、`Ollama`、`llama.cpp` 在 Windows 上都有官方支持，不要为了「统一」全部搬进 WSL。
- **铁律三：必须进 WSL2 的只有 4 类。** `bitsandbytes` 的 CUDA 版、`unsloth`、`vLLM`、以及需要源码编译 CUDA 扩展的东西。其余都可以在 Windows 上完成。

一台 4060 Laptop 8GB 的机器，把上面三条做到，能避开这一章 70% 的报错。剩下的 30% 在每节的「常见报错与解决」表里。

### 4.1 uv（Python 包与环境管理）

#### 它是干什么的

`uv` 是用 Rust 写的 Python 包与环境管理器，装包速度比 `pip` 快一个数量级，自带虚拟环境、Python 版本管理、锁文件（`uv.lock`）。它是你这半年的默认环境工具：一个项目一个目录一个环境，微调项目和部署项目互不干扰。**什么时候不该用它**：需要 conda 生态里非 Python 的二进制包（如 `cudatoolkit`、`gdal`）时，或者导师/实验室已有 conda 协作规范时，改用 conda，不要两边混用同一个项目目录。

#### 安装

下面这条命令在你自己的用户目录里安装 uv，不需要管理员权限。执行位置：Windows PowerShell。

```powershell
# 在 PowerShell（非管理员）中执行；装完必须重开一个终端
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
uv --version
```

预期输出：形如 `uv 0.8.x` 的版本号。若提示 `uv 不是内部或外部命令`，重开终端或手动把 `$env:USERPROFILE\.local\bin` 加入 PATH。

同一台机器的 WSL2 里再装一份（两份互不影响，WSL 里不要用 Windows 的 uv）。执行位置：WSL2 Bash。

```bash
# 在 WSL2 Ubuntu 22.04 中执行
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
uv --version
```

#### 最小可用示例

这段代码验证 uv 建环境、装包、跑脚本的完整链路。执行位置：二者均可（Windows PowerShell 或 WSL2 Bash，先 `cd` 到你的项目目录）。

```powershell

uv add numpy pandas scikit-learn
uv run python -c "import numpy, pandas, sklearn; print(numpy.__version__, pandas.__version__, sklearn.__version__)"
```


预期输出：`2.2.x 2.2.x 1.5.x` 这类版本号三个，且目录下出现 `.venv/` 与 `pyproject.toml`、`uv.lock`。

#### 常用参数 / API

| 命令 / 参数 | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `uv venv --python 3.11` | 建虚拟环境 | 微调环境固定 3.11（bitsandbytes/trl 兼容最好） |
| `uv add <包>` | 装包并写进 `pyproject.toml` | 逐个加，不要一次加 20 个 |
| `uv add torch --index-url https://download.pytorch.org/whl/cu124` | 指定 PyTorch 官方 CUDA 索引 | 必须显式给 `--index-url`，否则拿到 CPU 版 |
| `uv add --optional train -r requirements-train.txt` | 按分组装依赖 | 用 `train` / `rag` / `serve` 三组对应三套环境 |
| `uv sync --frozen` | 严格按锁文件还原 | 换机器/换云主机时用，保证版本一致 |
| `uv pip install -U <包>` | 升级单个包 | 只在你确认要换版本时用 |
| `uv cache clean` | 清包缓存 | 磁盘紧张时用；`torch` 的 wheel 单个 2–3GB |
| `--torch-backend=auto` | 自动挑 CUDA 版 torch | Windows + 4060 用 `cu124` 明确指定更稳 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `uv : 无法将“uv”项识别为 cmdlet...` | PATH 未刷新 | 重开终端；或 `$env:Path += ";$env:USERPROFILE\.local\bin"` |
| `error: No solution found when resolving dependencies` | 版本冲突（常见于 torch 与 onnxruntime） | 拆成两个环境：`uv venv .venv-deploy` 单独装 onnxruntime |
| `ImportError: DLL load failed while importing _C` | 装到了 CPU 版 torch | `uv pip install --reinstall torch --index-url https://download.pytorch.org/whl/cu124` |
| `Failed to download ... SSL certificate problem` | 公司网络代理 | 设 `$env:UV_INDEX_URL` 或用国内镜像 `https://pypi.tuna.tsinghua.edu.cn/simple` |
| `The system cannot find the path specified (os error 3)` | 项目路径含中文或空格 | 项目放在 `C:\work\...` 这类纯英文路径下 |

#### 8G 显存下的注意点

uv 管的是 Python 环境，不直接吃显存，但**决策影响显存**：微调环境里严禁同时装 `onnxruntime-gpu` 和 `tensorrt`，这两者会加载自己的 CUDA 上下文，占掉 200–400MB 显存，在只有 7GB 可用的情况下是致命的。用 `uv` 的多环境能力把 `requirements-train.txt` 和 `requirements-serve.txt` 装进两个目录，训练时另一个环境完全不加载。

### 4.2 PyTorch 训练骨架（AMP、梯度累积、断点续训、显存统计）

#### 它是干什么的

PyTorch 是深度学习底座，`torch.nn` 建模型、`torch.optim` 做优化、`torch.cuda.amp` 做混合精度。这一节给你的是一套可以套在任何项目上的训练骨架，包含自动混合精度（AMP）、梯度累积、断点续训、显存统计、显存碎片配置。**什么时候不该用它**：纯推理部署不想带 2.5GB 的 torch 依赖时，用 ONNX Runtime 或 llama.cpp，不要为了推理装 PyTorch。

#### 安装

执行位置：Windows PowerShell（原生即可，CUDA 版 torch 在 Windows 有官方 wheel）。

```powershell
# Windows PowerShell：先建独立环境，再装 CUDA 12.4 版 torch
uv venv --python 3.11
uv pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124
uv pip install numpy tqdm
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.get_device_name(0))"
```

预期输出：`2.6.x+cu124 12.4 NVIDIA GeForce RTX 4060 Laptop GPU`。

WSL2 里做法相同，只是路径与索引一致，注意 WSL 不要重复装 NVIDIA 驱动。执行位置：WSL2 Bash。

```bash
# WSL2 Bash：WSL 内不要装显卡驱动，只用 Windows 侧的驱动
uv venv --python 3.11
uv pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

#### 最小可用示例

下面这段是可直接运行的完整训练骨架，包含 AMP、梯度累积、断点续训、显存统计。执行位置：二者均可。

```python
import os
import time
import torch
import torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

# 关键：缓解 8G 显存碎片，必须在 import torch 之后、任何 CUDA 分配之前设置环境变量才生效，
# 因此在真实项目里建议放到启动脚本里（见本文末尾 requirements 与启动命令）。
os.environ.setdefault("PYTORCH_CUDA_ALLOC_CONF", "expandable_segments:True")

DEVICE = "cuda" if torch.cuda.is_available() else "cpu"
CKPT = "ckpt.pt"
ACCUM = 4           # 梯度累积步数：等效 batch = BATCH * ACCUM
BATCH = 8
EPOCHS = 3
MAX_LEN = 512


class TinyModel(nn.Module):
    def __init__(self, vocab=1000, dim=128):
        super().__init__()
        self.emb = nn.Embedding(vocab, dim)
        self.fc = nn.Linear(dim, 2)

    def forward(self, x):
        h = self.emb(x).mean(dim=1)
        return self.fc(h)


def build_data(n=256, seq=64, vocab=1000):
    x = torch.randint(0, vocab, (n, seq))
    y = torch.randint(0, 2, (n,))
    return TensorDataset(x, y)


def report_mem(tag=""):
    if DEVICE != "cuda":
        return
    alloc = torch.cuda.memory_allocated() / 1024 ** 2
    reserved = torch.cuda.memory_reserved() / 1024 ** 2
    peak = torch.cuda.max_memory_allocated() / 1024 ** 2
    print(f"[{tag}] allocated={alloc:.1f}MB reserved={reserved:.1f}MB peak={peak:.1f}MB")


def main():
    torch.manual_seed(0)
    loader = DataLoader(build_data(), batch_size=BATCH, shuffle=True, num_workers=0)
    model = TinyModel().to(DEVICE)
    opt = torch.optim.AdamW(model.parameters(), lr=3e-4)
    scaler = torch.amp.GradScaler("cuda", enabled=(DEVICE == "cuda"))
    crit = nn.CrossEntropyLoss()

    start_epoch, global_step = 0, 0
    if os.path.exists(CKPT):
        ckpt = torch.load(CKPT, map_location=DEVICE, weights_only=False)
        model.load_state_dict(ckpt["model"])
        opt.load_state_dict(ckpt["opt"])
        scaler.load_state_dict(ckpt["scaler"])
        start_epoch = ckpt["epoch"] + 1
        global_step = ckpt["step"]
        print(f"resume from epoch {start_epoch}, step {global_step}")

    for epoch in range(start_epoch, EPOCHS):
        model.train()
        t0 = time.time()
        running = 0.0
        opt.zero_grad(set_to_none=True)
        for i, (xb, yb) in enumerate(loader):
            xb, yb = xb.to(DEVICE), yb.to(DEVICE)
            with torch.autocast(device_type="cuda", dtype=torch.bfloat16, enabled=(DEVICE == "cuda")):
                out = model(xb)
                loss = crit(out, yb) / ACCUM
            scaler.scale(loss).backward()
            if (i + 1) % ACCUM == 0:
                scaler.unscale_(opt)
                torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
                scaler.step(opt)
                scaler.update()
                opt.zero_grad(set_to_none=True)
                global_step += 1
            running += loss.item() * ACCUM
        print(f"epoch {epoch} loss={running / len(loader):.4f} time={time.time() - t0:.1f}s")
        report_mem(f"epoch{epoch}")
        torch.save({
            "model": model.state_dict(),
            "opt": opt.state_dict(),
            "scaler": scaler.state_dict(),
            "epoch": epoch,
            "step": global_step,
        }, CKPT)
        print(f"saved checkpoint -> {CKPT}")
    torch.cuda.reset_peak_memory_stats() if DEVICE == "cuda" else None


if __name__ == "__main__":
    main()
```

预期输出：三行 `epoch 0/1/2 loss=0.69xx time=...`，每轮一行 `[epoch0] allocated=...MB reserved=...MB peak=...MB`，以及 `saved checkpoint -> ckpt.pt`。第二次运行会先打印 `resume from epoch 3, step ...` 说明续训生效。

把显存碎片配置写进启动脚本，避免忘记设置。执行位置：Windows PowerShell。

```powershell
# Windows PowerShell：推荐用这种方式启动训练脚本
$env:PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"
python train.py
```

```bash
# WSL2 Bash：等价做法
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python train.py
```

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `torch.autocast(device_type="cuda", dtype=...)` | 混合精度前向 | Ada 架构用 `torch.bfloat16`，省显存且不用 GradScaler 也能稳 |
| `torch.amp.GradScaler("cuda")` | fp16 梯度缩放 | 用 bf16 时可传 `enabled=False` |
| `accum_steps` | 梯度累积 | 目标等效 batch 32 时，batch=4、accum=8 |
| `torch.cuda.max_memory_allocated()` | 峰值显存 | 每个 epoch 打一次，超过 6.5GB 就要降 seq |
| `torch.cuda.memory_reserved()` | 缓存池占用 | 与 allocated 差距 >1GB 说明碎片严重 |
| `PYTORCH_CUDA_ALLOC_CONF` | 分配器行为 | `expandable_segments:True` 固定开 |
| `torch.utils.checkpoint.checkpoint` | 梯度检查点 | 7B QLoRA 必开，省 30–50% 激活显存，慢 20% |
| `torch.compile` | 图编译加速 | 8G 笔记本收益不稳定，先不用 |
| `pin_memory=True` | 锁页内存 | 数据在 CPU 端预处理重时空 |
| `num_workers` | 数据加载进程 | Windows 上设 0–2，设 4 以上容易在 WSL 外卡死 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate 2.00 GiB` | 显存不足 | 降 `batch`、降 `max_len`、开梯度检查点、清空缓存 |
| `CUDA error: out of memory` 但 nvidia-smi 显示只用了 3GB | 碎片或其它进程占用 | 设 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，关浏览器与本地 LLM |
| `AssertionError: Torch not compiled with CUDA enabled` | 装的是 CPU 版 | 用 cu124 索引重装 |
| `RuntimeError: CUDA error: no kernel image is available for execution on the device` | torch 太老不支持 sm_89 | 升到 torch 2.3+ |
| `RuntimeError: Expected all tensors to be on the same device` | 张量没 `.to(DEVICE)` | 检查数据与模型都在同一设备 |
| `UserWarning: GradScaler is enabled, but CUDA is not available` | 在 CPU 上传了 `enabled=True` | 用 `enabled=(DEVICE == "cuda")` |
| 续训后 loss 突然变大 | 只存了模型没存优化器 | checkpoint 必须含 `opt` 与 `scaler` |

#### 8G 显存下的注意点

实际可用约 7GB。这套骨架的显存账是这样：模型参数 + 梯度 + 优化器状态（AdamW 是参数量的 8 倍字节）+ 激活。估算时用 `16 bytes/参数` 做全量微调上限，`0.5B ≈ 8GB` 已经贴着天花板，`1.5B ≈ 24GB` 直接放弃。能跑的全量训练上限是 0.5B 级（如 Qwen3-0.6B），且必须开 AMP + 梯度检查点 + batch=1。每轮用 `report_mem` 打一次显存，看到 peak 超过 6.5GB 就先降 `MAX_LEN`（512 → 384 → 256），这是性价比最高的旋钮。

### 4.3 NumPy / Pandas / Matplotlib

#### 它是干什么的

这三个是数据处理与可视化的基本功：NumPy 管数组与向量化运算，Pandas 管表格与时间序列，Matplotlib 管画图。你的 P4 时序异常检测、日志统计、以及所有实验报告里的曲线都靠它们。**什么时候不该用它**：数据超过内存（>32GB）时不要硬上 Pandas，改用 Polars 的流式或 DuckDB + Parquet 分批处理。

#### 安装

执行位置：二者均可。

```powershell
# Windows PowerShell
uv venv --python 3.11
uv pip install numpy pandas matplotlib pyarrow
python -c "import numpy, pandas, matplotlib; print(numpy.__version__, pandas.__version__, matplotlib.__version__)"
```

```bash
# WSL2 Bash
uv venv --python 3.11 && uv pip install numpy pandas matplotlib pyarrow
python -c "import numpy, pandas, matplotlib; print(numpy.__version__, pandas.__version__)"
```

#### 最小可用示例

这段代码读一份 CSV、做缺失值处理与分组聚合、画图存盘，是数据分析的标准三步。执行位置：二者均可。

```python
import numpy as np
import pandas as pd
import matplotlib

matplotlib.use("Agg")  # 无界面环境必须设置，否则 WSL 里会报无 display
import matplotlib.pyplot as plt

# 造一份带缺失值与时序的样例数据并落盘
rng = np.random.default_rng(0)
df = pd.DataFrame({
    "ts": pd.date_range("2026-10-05", periods=200, freq="h"),
    "device": rng.choice(["pump-a", "pump-b", "fan-c"], size=200),
    "temp": rng.normal(60, 5, 200),
})
df.loc[10:14, "temp"] = np.nan
df.to_csv("sensor.csv", index=False)

# 读回来，做标准清洗
data = pd.read_csv("sensor.csv", parse_dates=["ts"])
data["temp"] = data["temp"].interpolate()          # 线性插值补缺失
data["temp_smooth"] = data.groupby("device")["temp"].transform(lambda s: s.rolling(6, min_periods=1).mean())
summary = data.groupby("device")["temp"].agg(["mean", "std", "count"]).round(3)
print(summary)

# 纯 NumPy 的向量化统计：比 for 循环快几百倍
arr = data["temp"].to_numpy()
print("z-score 超阈样本数:", int((np.abs((arr - arr.mean()) / arr.std()) > 2).sum()))

fig, ax = plt.subplots(figsize=(9, 3.5))
for name, g in data.groupby("device"):
    ax.plot(g["ts"], g["temp_smooth"], label=name, linewidth=1)
ax.set_xlabel("time"); ax.set_ylabel("temperature"); ax.legend()
fig.tight_layout(); fig.savefig("sensor.png", dpi=120)
print("saved sensor.png")
```

预期输出：一张 3 行 4 列的 `summary` 表（含 `mean/std/count`），一行 `z-score 超阈样本数: N`（N 通常 5–15），以及 `saved sensor.png`。

#### 常用参数 / API

| API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `pd.read_csv(..., dtype=..., usecols=...)` | 只读需要的列并指定类型 | 日志类数据先 `usecols`，内存能省 60% |
| `df.groupby(...).transform(...)` | 组内变换后广播回原表 | 做设备级标准化必用 |
| `df.rolling(6, min_periods=1).mean()` | 滑动平均 | 时序异常检测的基线特征 |
| `np.memmap` | 超内存数组映射 | 大 embedding 矩阵读取 |
| `matplotlib.use("Agg")` | 关掉交互后端 | WSL2 与服务器上必须设置 |
| `df.to_parquet()` | 列存落盘 | 中间数据一律 Parquet，读取快 5–10× |
| `pd.set_option("display.max_columns", 50)` | 显示更多列 | 调试宽表时用 |
| `np.float32` | 单精度 | 图像/embedding 默认 fp32，不要用 fp64 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ImportError: numpy.core.multiarray failed to import` | numpy 版本与依赖不匹配 | `uv pip install --reinstall numpy`，或锁 numpy<2 配旧包 |
| `TclError: no display name and no $DISPLAY environment variable` | Matplotlib 试图开窗口 | 在 import pyplot 前 `matplotlib.use("Agg")` |
| `SettingWithCopyWarning` | 对切片赋值 | 用 `df.loc[mask, "col"] = value` 或先 `.copy()` |
| `ValueError: could not convert string to float: '--'` | 脏数据占位符 | `pd.to_numeric(s, errors="coerce")` |
| 中文标签显示成方块 | 字体缺失 | `plt.rcParams["font.sans-serif"] = ["Microsoft YaHei"]`（Windows） |
| `MemoryError` 读 CSV | 文件比内存大 | 用 `chunksize=100000` 分块，或换 Parquet |
| `FutureWarning: The default dtype for empty Series...` | 版本行为变更 | 显式给 `dtype`，不依赖默认 |

#### 8G 显存下的注意点

三者都在 CPU 上跑，不吃显存，但**吃内存并且决定显存压力**：把 `pandas` 的 `DataFrame` 直接转成整块 `torch.Tensor` 再搬上 GPU，是 8G 机器最常见的 OOM 原因。正确做法是让 `Dataset.__getitem__` 只在需要时把单个样本搬上 GPU，`DataLoader` 用 `num_workers=0–2`（Windows 上进程多了会抢内存导致卡顿）。特征标准化一律在 CPU 上用 NumPy 做完再进模型。

#### 最小可用示例

这段代码用 Pipeline 把标准化与逻辑回归串起来并做交叉验证，再用 Isolation Forest 做异常检测基线。执行位置：二者均可。

```python
import numpy as np
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import IsolationForest
from sklearn.model_selection import cross_val_score, train_test_split
from sklearn.datasets import make_classification
from sklearn.metrics import classification_report

X, y = make_classification(n_samples=2000, n_features=20, n_informative=8, random_state=0)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.2, random_state=0, stratify=y)

pipe = Pipeline([
    ("scaler", StandardScaler()),
    ("clf", LogisticRegression(max_iter=1000, C=1.0)),
])
scores = cross_val_score(pipe, Xtr, ytr, cv=5, scoring="f1")
print("cv f1:", np.round(scores, 4), "mean=%.4f" % scores.mean())

pipe.fit(Xtr, ytr)
print(classification_report(yte, pipe.predict(Xte), digits=3))

# 无监督异常检测基线：只用正常样本拟合
iso = IsolationForest(n_estimators=200, contamination=0.05, random_state=0)
iso.fit(Xtr[ytr == 0])
pred = iso.predict(Xte)
print("预测为异常的样本数:", int((pred == -1).sum()), "/", len(pred))
```

预期输出：`cv f1: [0.9x ...] mean=0.9xxx`，一份 `classification_report`（precision/recall/f1 均在 0.9 上下），以及 `预测为异常的样本数: 20 / 400` 这类行。

#### 常用参数 / API

| API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `Pipeline([...])` | 串起预处理与模型 | 所有实验都用，避免数据泄漏 |
| `StandardScaler` | 零均值单位方差 | 树模型不需要，线性/距离模型必须 |
| `LogisticRegression(C=...)` | 线性基线 | `C=1.0`，`max_iter=1000` |
| `IsolationForest(contamination=...)` | 无监督异常检测 | `n_estimators=200`，`contamination` 按真实告警率设 0.01–0.05 |
| `cross_val_score(scoring="f1")` | 交叉验证 | 类别不平衡时用 `f1_macro` |
| `GridSearchCV(n_jobs=...)` | 网格搜索 | `n_jobs=4`，别设 -1 抢满 CPU 影响数据加载 |
| `joblib.dump/load` | 模型持久化 | 模型小于 1GB 都可以，别用 pickle 跨版本 |
| `class_weight="balanced"` | 类权重 | 异常检测/告警类数据必开 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ConvergenceWarning: lbfgs failed to converge` | 未标准化或迭代不足 | 加 `StandardScaler`，`max_iter=2000` |
| `ValueError: Input contains NaN, infinity or a value too large` | 脏数据 | 用 `SimpleImputer` 或 `np.nan_to_num` 先清洗 |
| `ValueError: Found unknown categories` | 训练集没有的类别出现在测试集 | 用 `OneHotEncoder(handle_unknown="ignore")` |
| `TypeError: fit() got an unexpected keyword` | API 版本变了 | 查 `sklearn.__version__`，按对应版本文档改参数名 |
| `n_jobs=-1` 后程序卡死 | Windows 上进程池与主进程冲突 | 改成 `n_jobs=1` 或把代码放进 `if __name__ == "__main__":` |

#### 8G 显存下的注意点

scikit-learn 全在 CPU，不占显存。它的价值在 8G 机器上是**「先建立强基线再上大模型」**：P4 的时序异常检测用 Isolation Forest + 统计特征就能拿到不错的 F1，再叠加 AutoEncoder 才有提升空间。不要在 8G 上跳过 sklearn 基线直接上 Transformer，那会让你无法判断提升到底来自模型还是来自数据。

#### 最小可用示例

这段代码用 MobileNetV3 预训练权重做一次前向与特征提取，并统计参数量与显存占用，是判断「这个模型我的 8G 能不能训练」的标准动作。执行位置：二者均可。

```python
import torch
import timm

device = "cuda" if torch.cuda.is_available() else "cpu"

# 列出可用的轻量主干，挑 8G 能完整微调的
light = [m for m in timm.list_models(pretrained=True) if any(k in m for k in ("mobilenetv3", "efficientnet_b0", "resnet18"))]
print("轻量候选示例:", light[:5])

model = timm.create_model("mobilenetv3_small_100", pretrained=True, num_classes=10).to(device)
model.eval()

x = torch.randn(8, 3, 224, 224, device=device)
with torch.no_grad():
    logits = model(x)
print("输出形状:", tuple(logits.shape))

params = sum(p.numel() for p in model.parameters())
trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
print(f"参数量={params/1e6:.2f}M 可训练={trainable/1e6:.2f}M")

# 用 timm 自带的预处理配置，避免自己猜 mean/std
cfg = timm.data.resolve_data_config({}, model=model)
print("预处理配置:", cfg)

if device == "cuda":
    torch.cuda.reset_peak_memory_stats()
    model.train()
    out = model(torch.randn(8, 3, 224, 224, device=device))
    out.sum().backward()
    print(f"前向+反向峰值显存={torch.cuda.max_memory_allocated()/1024**2:.0f}MB")
```

预期输出：5 个候选模型名、`输出形状: (8, 10)`、形如 `参数量=2.54M 可训练=2.54M` 的统计、一份含 `mean/std/input_size` 的配置，以及 `前向+反向峰值显存=xxxMB`（MobileNetV3-Small 在 224 分辨率下约 500–900MB）。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `timm.create_model(name, pretrained=True)` | 建模型并加载预训练 | 优先 `mobilenetv3_small_100` / `efficientnet_b0` |
| `num_classes=10` | 替换分类头 | 按任务改，二分类设 1 或 2 注意与损失匹配 |
| `timm.data.resolve_data_config` | 拿到官方 mean/std/size | 不要自己写 0.5/0.5/0.5 |
| `timm.data.create_transform` | 一键造预处理 | 训练用 `is_training=True` 自动加增强 |
| `features_only=True` | 只取多尺度特征图 | 做 U-Net / 检测头时用 |
| `global_pool=""` | 去掉池化 | 需要空间特征时设 |
| `drop_rate=0.1` | 分类头 dropout | 小数据集必开 0.1–0.3 |
| `model.set_grad_checkpointing(True)` | 梯度检查点 | ConvNeXt/ViT 类在 8G 上必须开 |
| `pretrained_cfg_overlay` | 覆盖官方配置 | 输入分辨率改成 128/160 省显存 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `RuntimeError: Error(s) in loading state_dict for MobileNetV3` | 分类头维度不一致 | 加 `num_classes=N` 或 `strict=False` |
| `urllib.error.URLError: <urlopen error [WinError 10054]>` | 下载预训练权重被重置 | 设 `HF_ENDPOINT=https://hf-mirror.com`，或手动下载放到 `~/.cache/torch/hub/checkpoints/` |
| `CUDA out of memory` 在 `create_model` 后立刻出现 | 分辨率或 batch 太大 | 把输入降到 160×160，batch 降到 4 |
| `ValueError: Unknown model (...)` | 模型名拼错或版本太老 | 用 `timm.list_models("*mobilenetv3*")` 查准确名字 |
| `RuntimeError: Input type (torch.cuda.FloatTensor) and weight type (torch.cuda.HalfTensor)` | 混合精度下输入没转 | 输入用 `x.half()` 或统一 autocast |

#### 8G 显存下的注意点

| 主干 | 224 分辨率训练显存（batch=8, AMP） | 8G 结论 |
| --- | --- | --- |
| MobileNetV3-Small | 约 0.9GB | 放心用，P3 首选 |
| ResNet18 | 约 1.5GB | 放心用 |
| EfficientNet-B0 | 约 2.0GB | 可用，batch 可到 16 |
| ConvNeXt-Tiny | 约 4.5GB | 开梯度检查点 + batch 4 |
| ViT-Base/16 | 约 9GB | 8G 跑不了，降到 ViT-Small 或降分辨率到 128 |

| `Export failure: Unsupported ONNX opset version: 21` | onnx 版本与 opset 不匹配 | 降 `opset=17`，并升级 `onnx` 到 1.16+ |

#### 最小可用示例

这段代码加载一个小模型做一次生成，并打印参数量与显存占用，同时演示 chat template 的正确用法。执行位置：二者均可，建议先在 WSL2 或 Windows 均可（无 bitsandbytes 依赖）。

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"
device = "cuda" if torch.cuda.is_available() else "cpu"

tok = AutoTokenizer.from_pretrained(MODEL_ID, trust_remote_code=True)
model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID,
    torch_dtype=torch.bfloat16 if device == "cuda" else torch.float32,
    device_map={"": device},
    trust_remote_code=True,
)
model.eval()

messages = [
    {"role": "system", "content": "你是一个简洁的助手，回答不超过两句话。"},
    {"role": "user", "content": "用一句话解释什么是 LoRA。"},
]
text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tok(text, return_tensors="pt").to(device)

with torch.inference_mode():
    out = model.generate(**inputs, max_new_tokens=64, do_sample=False, pad_token_id=tok.eos_token_id)

answer = tok.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)
print("回答:", answer.strip())
print("参数量: %.1fM" % (sum(p.numel() for p in model.parameters()) / 1e6))
if device == "cuda":
    print("显存峰值: %.0fMB" % (torch.cuda.max_memory_allocated() / 1024 ** 2))
```

预期输出：一句中文回答（形如 `LoRA 是一种低秩适配微调方法，只训练少量新增参数...`）、`参数量: 494.0M` 左右、`显存峰值: 1100–1400MB`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `torch_dtype` | 权重精度 | `torch.bfloat16`（Ada 支持）；bf16 加载 7B 约 14GB，8G 装不下 |
| `device_map` | 设备分配 | `{"": "cuda"}` 或 `"auto"`；8G 上不要用 `auto` 分片到 CPU，慢到不可用 |
| `load_in_4bit=True` | 4bit 量化加载 | 7B 必需，配合 `BitsAndBytesConfig` |
| `max_new_tokens` | 生成长度 | 测试用 64–128，正式 512 |
| `do_sample=False` | 贪心解码 | 评测/复现用；对话用 `temperature=0.7` |
| `attn_implementation="sdpa"` | 注意力实现 | Ada 上开 `sdpa` 比 eager 快 20–30% |
| `apply_chat_template` | 拼 chat 格式 | 微调与推理必须用同一个 template |
| `use_cache=True` | KV Cache | 推理开，训练关 |
| `tok.padding_side="right"` | 填充方向 | 训练 Qwen 系建议 `right` |
| `trust_remote_code=True` | 允许自定义代码 | 只对可信仓库开 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `OSError: We couldn't connect to 'https://huggingface.co'` | 网络不通 | `$env:HF_ENDPOINT="https://hf-mirror.com"` 或 `export HF_ENDPOINT=https://hf-mirror.com` |
| `torch.cuda.OutOfMemoryError` 加载 7B | fp16 权重就要 14GB | 用 `load_in_4bit=True` + `bnb_4bit_compute_dtype=torch.bfloat16` |
| `ValueError: Tokenizer class ... does not exist` | 需要 `trust_remote_code` | 加 `trust_remote_code=True` 或升级 transformers |
| `KeyError: 'qwen2'` / `Unrecognized model` | transformers 太老 | 升到 `>=4.46`（新模型需要新版本） |
| `RuntimeError: expected scalar type BFloat16 but found Float` | 输入 embedding 与权重精度不一致 | 统一 `torch_dtype`，或在 autocast 下前向 |
| `The following generation flags are not valid` | 采样参数冲突 | 用 `do_sample=True` 时才给 `temperature/top_p` |
| `Token indices sequence length is longer than ...` | 超过模型最大长度 | 截断 `truncation=True, max_length=512` |

#### 8G 显存下的注意点

| 任务 | 模型规模 | 8G 可行性 |
| --- | --- | --- |
| 微调 BERT-base（≤200M） | 110M | 可跑，batch 16 + seq 256 |
| 全量微调 | 0.5B | 极限，需梯度检查点 + batch 1 |
| QLoRA 微调 | 7B/8B | 可跑，seq 512 起步，峰值 6.5–7.8GB |
| 全量微调 | 1.5B–3B | 跑不了（需 24–48GB） |
| bf16 推理 | 7B | 跑不了（权重 14GB） |
| 4bit 推理 | 7B | 可以，但更推荐 llama.cpp/Ollama |

`attn_implementation="sdpa"` 在 4060（Ada，sm_89）上稳定可用；`flash_attention_2` 在 Windows 上安装麻烦，收益在短序列下有限，先不折腾。

#### 最小可用示例

这段代码从内存字典建数据集、做 tokenize 映射、切分并检查长度分布，是微调数据准备的最小闭环。执行位置：二者均可。

```python
import json
from datasets import Dataset, DatasetDict, load_dataset
from transformers import AutoTokenizer

# 1) 造一份指令数据并落成 JSONL（真实项目用你的 data/ 目录）
rows = [
    {"instruction": "把下面这句话改成被动语态", "input": "工程师修复了这台泵。", "output": "这台泵被工程师修复了。"},
    {"instruction": "给出该设备的可能故障原因", "input": "振动值连续 3 小时超阈", "output": "可能原因：轴承磨损、叶轮不平衡、联轴器松动。"},
    {"instruction": "总结告警", "input": "CPU 使用率 98%，持续 10 分钟", "output": "主机 CPU 长时间满负载，建议检查异常进程。"},
]
with open("sft.jsonl", "w", encoding="utf-8") as f:
    for r in rows:
        f.write(json.dumps(r, ensure_ascii=False) + "\n")

ds = load_dataset("json", data_files="sft.jsonl", split="train")
print(ds)
print("第一条:", ds[0])

# 2) 用 tokenizer 批量映射
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", trust_remote_code=True)
if tok.pad_token is None:
    tok.pad_token = tok.eos_token


def to_features(batch):
    prompts = [f"### 指令：{i}\n### 输入：{x}\n### 回答：" for i, x in zip(batch["instruction"], batch["input"])]
    full = [p + o for p, o in zip(prompts, batch["output"])]
    enc = tok(full, truncation=True, max_length=512, padding=False)
    enc["labels"] = [ids.copy() for ids in enc["input_ids"]]
    return enc


encoded = ds.map(to_features, batched=True, remove_columns=ds.column_names)
print("映射后字段:", encoded.column_names)
print("长度分布:", encoded.select(range(len(encoded))).map(lambda b: {"len": [len(i) for i in b["input_ids"]]}, batched=True, remove_columns=encoded.column_names)["len"])

# 3) 切分并保存到磁盘，训练时直接 from_disk
split = encoded.train_test_split(test_size=0.34, seed=0)
DatasetDict(split).save_to_disk("sft_ds")
print("已保存 sft_ds，训练集条数:", len(split["train"]))
```

预期输出：一段 `Dataset` 摘要（features 含 `instruction/input/output`）、第一条样本内容、`映射后字段: ['input_ids', 'attention_mask', 'labels']`、一个长度列表、以及 `已保存 sft_ds，训练集条数: 2`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `load_dataset("json", data_files=...)` | 从 JSONL 加载 | 本地文件，不用联网络 |
| `.map(fn, batched=True)` | 批量预处理 | `batched=True` 快 10 倍以上 |
| `remove_columns=` | 丢掉原始列 | 训练前必做，否则 collator 报错 |
| `num_proc=` | 并行处理 | Windows 设 1–2，WSL2 可设 4 |
| `train_test_split(test_size=...)` | 切分 | 5k 样本用 0.05，小样本用 0.2 |
| `streaming=True` | 流式读取 | 数据超过内存时用，但 `map` 不能随便用 |
| `save_to_disk / load_from_disk` | 本地缓存 | 预处理一次后落盘，训练直接读 |
| `Dataset.filter` | 过滤脏样本 | 过滤掉 `len(output) < 5` 的空回答 |
| `HF_DATASETS_CACHE` | 缓存目录 | 指到数据盘，避免占满 C 盘 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `FileNotFoundError: Cannot find data file` | `data_files` 路径不对 | 用绝对路径，Windows 用正斜杠 `C:/work/data/sft.jsonl` |
| `ArrowInvalid: JSON parse error` | JSONL 有坏行 | 用 `json.loads` 逐行校验并剔除坏行 |
| `ValueError: You must specify a split` | 没给 `split=` | 加 `split="train"`，或对返回的 `DatasetDict` 取键 |
| `TypeError: Object of type Tensor is not JSON serializable` | `map` 返回了张量 | 返回 Python list，`.tolist()` 转一下 |
| `RuntimeError: DataLoader worker ...` 与 datasets 同现 | `num_proc` 与 DataLoader 冲突 | 训练时设 `dataloader_num_workers=0` |
| 缓存占满磁盘（几十 GB） | 反复 `map` 生成新缓存 | `load_from_disk` 替代重复 map，定期清 `~/.cache/huggingface/datasets` |

#### 8G 显存下的注意点

`datasets` 不占显存，但决定**你能否用长序列**。8G 上 `max_length` 从 512 涨到 1024，激活显存大约翻倍，所以数据侧要主动做长度筛选：先用 tokenizer 统计长度分布，把超过 1024 的样本截断或过滤掉统计一下占比。5k 高质量样本、seq 512，是 8G QLoRA 最舒服的组合。

### 4.9 accelerate

#### 它是干什么的

`accelerate` 把设备放置、混合精度、梯度累积、分布式启动抽象成几行配置，让你同一份训练代码在 CPU、单卡 4060、多卡 A100 上都能跑。你 W13 之后的所有微调脚本都用它，将来上云改一个 `--num_processes` 就能用多卡。**什么时候不该用它**：只有一块卡、且你要精确控制每一步显存时，手写训练循环更透明；`accelerate` 的封装会让你看不清哪一步 OOM。


#### 最小可用示例

这段代码用 `Accelerator` 做设备放置、autocast、梯度累积与分片保存，是 8G 上写训练脚本的推荐骨架。执行位置：二者均可。

```python
import torch
import torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset
from accelerate import Accelerator

accelerator = Accelerator(
    gradient_accumulation_steps=4,
    mixed_precision="bf16",          # Ada 架构用 bf16
    log_with=None,                    # 需要 wandb 时改成 "wandb"
)
print("设备:", accelerator.device, "| 进程数:", accelerator.num_processes)


def make_loader(n=512, seq=64, vocab=1000, bs=8):
    x = torch.randint(0, vocab, (n, seq))
    y = torch.randint(0, 2, (n,))
    return DataLoader(TensorDataset(x, y), batch_size=bs, shuffle=True)


model = nn.Sequential(nn.Embedding(1000, 64), nn.Flatten(), nn.Linear(64 * 64, 2))
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)
loader = make_loader()

model, opt, loader = accelerator.prepare(model, opt, loader)
crit = nn.CrossEntropyLoss()

for epoch in range(2):
    model.train()
    total = 0.0
    for step, (xb, yb) in enumerate(loader):
        with accelerator.accumulate(model):
            out = model(xb)
            loss = crit(out, yb)
            accelerator.backward(loss)
            opt.step()
            opt.zero_grad(set_to_none=True)
        total += loss.item()
    print(f"epoch {epoch} avg_loss={total / len(loader):.4f}")

accelerator.wait_for_everyone()
unwrapped = accelerator.unwrap_model(model)
accelerator.save(unwrapped.state_dict(), "acc_model.pt")
print("已保存 acc_model.pt")
if accelerator.device.type == "cuda":
    print("峰值显存: %.0fMB" % (torch.cuda.max_memory_allocated() / 1024 ** 2))
```

预期输出：`设备: cuda | 进程数: 1`、两行 `epoch x avg_loss=0.69xx`、`已保存 acc_model.pt`、以及一行峰值显存。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `Accelerator(mixed_precision=...)` | 精度策略 | `"bf16"`（Ada 原生支持） |
| `gradient_accumulation_steps=` | 梯度累积 | 4–8，等效 batch 到 32 |
| `accelerator.accumulate(model)` | 累积上下文 | 必须包住 forward/backward |
| `accelerator.prepare(...)` | 设备放置与包装 | 模型、优化器、loader 全部传进去 |
| `accelerator.backward(loss)` | 反向传播 | 替代 `loss.backward()`，自动处理缩放 |
| `accelerator.save / save_state` | 保存权重与状态 | 续训必须用 `save_state` |
| `accelerator.load_state(path)` | 恢复训练状态 | 含优化器、scaler、步数 |
| `accelerator.gather_for_metrics` | 收集跨卡指标 | 单卡时是恒等变换，写了不影响 |
| `accelerate launch --num_processes=1 train.py` | 启动 | 本地单卡用它启动，将来上云改数字 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ValueError: bf16 mixed precision is not supported on this device` | 老卡不支持 bf16 | 4060 支持；若报错说明用了 CPU，检查 `cuda.is_available()` |
| `RuntimeError: optimizer got an empty parameter list` | `prepare` 前模型没参数 | 先建模型再传给 `prepare` |
| `You should call accelerator.accumulate() ...` | 没包累积上下文 | 把 forward/backward 包进 `with accelerator.accumulate(model):` |
| `accelerate launch` 卡在 `Waiting for all processes` | 上次进程没退干净 | 任务管理器杀掉残留 `python.exe`，或重启 WSL |
| `AttributeError: 'Accelerator' object has no attribute 'autocast'` | 旧 API | 新版用 `accelerator.accumulate` + `mixed_precision` 参数 |
| 续训后 loss 跳变 | 只 `save` 了模型 | 用 `accelerator.save_state()` 保存全量状态 |

#### 8G 显存下的注意点

`accelerate` 不改变显存公式，只降低你写错的可能性。8G 上的组合拳固定为：`mixed_precision="bf16"` + `gradient_accumulation_steps=4~8` + 模型侧梯度检查点 + `paged_adamw_8bit`。这样 7B QLoRA 峰值能压到 6.5–7.8GB。另外 `accelerate` 允许你把 `device_map="auto"` 用得更安全（会自动把放不下的层甩到 CPU），但在 8G 上 CPU offload 会让速度掉到原来的 1/10，**只在调试时用**。

### 4.10 peft（LoRA / QLoRA 配置解读）

#### 它是干什么的

`peft`（Parameter-Efficient Fine-Tuning）实现 LoRA、QLoRA、DoRA、IA3、Prompt Tuning 等参数高效微调方法，核心是给已有的 `nn.Linear` 挂上低秩旁路，只训练这些噪声矩阵。它是 8G 显存机器做 7B 微调的关键工具。**什么时候不该用它**：需要改变模型结构或词表（加特殊 token 时仍可配合 `resize_token_embeddings`）、或做全量微调追求极致精度时不用它。

#### 最小可用示例

这段代码给一个小模型挂上 LoRA，打印可训练参数占比，训练一步并演示合并与保存。执行位置：二者均可（仅 LoRA，不含 4bit）。

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model, TaskType, PeftModel

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(MODEL_ID, trust_remote_code=True)
if tok.pad_token is None:
    tok.pad_token = tok.eos_token
model = AutoModelForCausalLM.from_pretrained(MODEL_ID, torch_dtype=torch.float32, trust_remote_code=True)

lora_cfg = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                     # 低秩维度：8 省显存，32/64 表达力更强
    lora_alpha=32,            # 缩放系数，经验取 2*r
    lora_dropout=0.05,
    bias="none",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],  # Qwen 系命名
)
peft_model = get_peft_model(model, lora_cfg)
peft_model.print_trainable_parameters()

text = tok.apply_chat_template([{"role": "user", "content": "你好"}], tokenize=False, add_generation_prompt=True)
batch = tok(text, return_tensors="pt")
out = peft_model(**batch, labels=batch["input_ids"])
out.loss.backward()
print("loss=%.4f" % out.loss.item())

grad_norm = sum(p.grad.norm().item() ** 2 for p in peft_model.parameters() if p.grad is not None) ** 0.5
print("LoRA 梯度范数=%.4f" % grad_norm)

peft_model.save_pretrained("lora_out")
print("适配器已保存，目录大小约:", sum(p.numel() for p in peft_model.parameters() if p.requires_grad) * 4 // 1024, "KB")

# 加载基座 + 适配器，验证可复现
base = AutoModelForCausalLM.from_pretrained(MODEL_ID, torch_dtype=torch.float32, trust_remote_code=True)
loaded = PeftModel.from_pretrained(base, "lora_out")
merged = loaded.merge_and_unload()
print("合并后类型:", type(merged).__name__)
```

预期输出：`trainable params: 1,081,344 || all params: 495,032,xxx || trainable%: 0.21xx`、`loss=3.xxxx`、`LoRA 梯度范数=...`、`适配器已保存...`，以及 `合并后类型: Qwen2ForCausalLM`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `r` | 低秩维度 | 7B QLoRA 用 16；显存紧用 8；数据充足用 32 |
| `lora_alpha` | 缩放 | 取 `2*r`（r=16 → 32） |
| `lora_dropout` | 正则 | 小数据集 0.05–0.1，大数据集 0 |
| `target_modules` | 挂载位置 | Qwen2/Llama：`q,k,v,o,gate,up,down_proj` 全挂提升明显但更吃显存 |
| `bias="none"` | 是否训 bias | 一律 `none` |
| `use_rslora=True` | 秩稳定缩放 | 大 r（≥64）时开 |
| `task_type` | 任务类型 | 因果语言模型用 `TaskType.CAUSAL_LM` |
| `modules_to_save=["lm_head"]` | 额外保存的层 | 换词表/换分类头时必须加 |
| `merge_and_unload()` | 合并适配器 | 7B fp16 合并需 14GB，8G 上必须 CPU 合并 |
| `add_weighted_adapter` | 多适配器加权融合 | 有多个任务适配器时用 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ValueError: Target modules {'q_proj'} not found in the base model` | 模型层命名不同 | 打印 `[n for n,_ in model.named_modules()]` 找真实名字 |
| `RuntimeError: element 0 of tensors does not require grad` | 输入没传到 LoRA 层或模型被冻结错 | 确认 `requires_grad` 与 `target_modules` 正确 |
| `CUDA out of memory` 在 `merge_and_unload` | fp16 合并需要 2 倍权重显存 | 用 CPU 合并：`model.to("cpu")` 后再 merge，或转 GGUF 工具合并 |
| `KeyError: 'base_model.model....'` 加载适配器 | peft 版本不一致 | 用保存时同一 peft 版本加载 |
| `TypeError: LoraConfig.__init__() got an unexpected keyword argument 'fan_in_fan_out'` | 版本 API 差异 | 查当前版本参数集，去掉不支持的参数 |
| 训练 loss 不降 | `r`/`alpha` 太小或 target 太少 | 先把 `q,k,v,o,gate,up,down_proj` 全挂上验证能降，再逐步减 |

#### LoRA 与 QLoRA 配置对照

| 维度 | LoRA | QLoRA（8G 上 7B 的唯一选择） |
| --- | --- | --- |
| 基座精度 | fp16/bf16 | 4bit NF4（`load_in_4bit=True`） |
| 7B 权重显存 | 约 14GB，8G 装不下 | 约 3.9–4.3GB |
| 优化器 | `adamw_torch` | `paged_adamw_8bit` |
| 计算精度 | bf16 | `bnb_4bit_compute_dtype=torch.bfloat16` |
| 量化类型 | — | `bnb_4bit_quant_type="nf4"` |
| 双重量化 | — | `bnb_4bit_use_double_quant=True`，省约 0.4GB |
| 峰值显存（7B, seq512, bs1） | — | 6.5–7.8GB |

#### 8G 显存下的注意点

`target_modules` 是显存与效果的旋钮。只挂 `q_proj,v_proj`：可训练参数约 0.05%，7B 上约 4–8M 参数，显存最省但效果一般；全挂七个投影层：参数占 0.5–1%，效果明显更好，激活显存增加约 0.5GB。**8G 上的推荐顺序**：先全挂跑通看 loss 是否下降，再往下减；`r=16, alpha=32` 是稳妥起点。7B 的适配器合并绝不在 GPU 上做，用 CPU 内存合并（需要 16GB 以上内存）或直接导出 GGUF 用 llama.cpp 加载适配器。

```python
import torch
from datasets import Dataset
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(MODEL_ID, trust_remote_code=True)
if tok.pad_token is None:
    tok.pad_token = tok.eos_token
model = AutoModelForCausalLM.from_pretrained(MODEL_ID, torch_dtype=torch.float32, trust_remote_code=True)

rows = [
    {"messages": [{"role": "user", "content": "设备振动超标怎么排查？"},
                  {"role": "assistant", "content": "先看轴承与联轴器，再查叶轮平衡与安装基础。"}]},
    {"messages": [{"role": "user", "content": "什么是告警收敛？"},
                  {"role": "assistant", "content": "把同一根因引发的大量告警合并成一条根因告警。"}]},
] * 8
ds = Dataset.from_list(rows)

peft_cfg = LoraConfig(
    r=8, lora_alpha=16, lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
)
args = SFTConfig(
    output_dir="sft_out",
    num_train_epochs=2,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=4,
    learning_rate=2e-4,
    logging_steps=1,
    save_strategy="epoch",
    max_length=512,
    packing=False,
    bf16=torch.cuda.is_available(),
    report_to="none",
)
trainer = SFTTrainer(model=model, args=args, train_dataset=ds, peft_config=peft_cfg, processing_class=tok)
trainer.train()
trainer.save_model("sft_out/final")
print("已保存到 sft_out/final")

# 训练后推理验证
model.eval()
prompt = tok.apply_chat_template([{"role": "user", "content": "设备振动超标怎么排查？"}],
                                 tokenize=False, add_generation_prompt=True)
ids = tok(prompt, return_tensors="pt").to(model.device)
with torch.inference_mode():
    gen = model.generate(**ids, max_new_tokens=48, do_sample=False, pad_token_id=tok.eos_token_id)
print("回答:", tok.decode(gen[0][ids["input_ids"].shape[1]:], skip_special_tokens=True).strip())
```

预期输出：一段 trainer 日志（`loss` 从 2.x 降到 1.x 附近）、`已保存到 sft_out/final`，以及一句与训练数据风格接近的中文回答。

DPO 训练只需要换数据格式与 Trainer，其余配置相同。执行位置：二者均可。

```python
# DPO 数据格式：每条含 prompt / chosen / rejected
from datasets import Dataset
from trl import DPOTrainer, DPOConfig

dpo_rows = [
    {"prompt": "设备振动超标怎么排查？",
     "chosen": "先检查轴承磨损与联轴器对中，再看叶轮是否不平衡。",
     "rejected": "重启一下就好了。"},
] * 8
dpo_ds = Dataset.from_list(dpo_rows)

dpo_args = DPOConfig(
    output_dir="dpo_out",
    num_train_epochs=1,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=4,
    learning_rate=5e-5,
    beta=0.1,               # DPO 温度系数
    max_length=512,
    max_prompt_length=256,
    bf16=True,
    report_to="none",
)
# 注意：DPO 需要同时驻留策略模型与参考模型，显存约 2 倍，
# 8G 上只对 <=0.5B 模型可行；更大的模型改用 ORPO/SimPO。
print("DPO 配置就绪：", dpo_args.output_dir, "beta=", dpo_args.beta)
```

预期输出：`DPO 配置就绪： dpo_out beta= 0.1`。真正训练时把 `DPOTrainer(model=..., ref_model=None, args=dpo_args, train_dataset=dpo_ds, processing_class=tok)` 接上即可（传 `ref_model=None` 时 peft 配置下 trl 会自动用禁用适配器的基座作参考）。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `per_device_train_batch_size` | 单卡 batch | 8G 上用 1 |
| `gradient_accumulation_steps` | 累积步数 | 8–16，等效 batch 到 16 |
| `max_length` | 序列长度 | 512 起步，1024 是极限 |
| `packing` | 多短样本拼一条 | 短样本多时 `True` 提速，长样本 `False` |
| `learning_rate` | 学习率 | LoRA/QLoRA 用 1e-4 ~ 2e-4 |
| `optim` | 优化器 | QLoRA 用 `paged_adamw_8bit` |
| `gradient_checkpointing` | 梯度检查点 | `True`，8G 必开 |
| `bf16` | 混合精度 | `True`（Ada 支持） |
| `save_strategy="epoch"` | 保存策略 | 小数据按 epoch，大数据按 `steps` |
| `DPOConfig(beta=...)` | DPO 强度 | 0.1 起步，0.3 更保守 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `TypeError: SFTTrainer.__init__() got an unexpected keyword argument 'tokenizer'` | 新版改名 | 用 `processing_class=tok` 替代 `tokenizer=tok` |
| `TypeError: SFTConfig.__init__() got an unexpected keyword argument 'max_seq_length'` | 新版改名 | 用 `max_length` 替代 `max_seq_length` |
| `ValueError: You passed a dataset with no 'text' or 'messages' field` | 数据字段名不对 | 指令数据用 `messages`，纯文本用 `text` |
| `RuntimeError: stack expects each tensor to be equal size` | 没让 trainer 自己 padding | 不要预先 padding，交给 `DataCollatorForLanguageModeling` |
| `CUDA out of memory` 在 DPO 第一步 | 策略+参考双模型 | 换 `beta` 更小的 ORPO/SimPO，或降模型规模到 0.5B |
| `ImportError: cannot import name 'SFTTrainer' from 'trl'` | 版本过旧或过新目录结构调整 | 固定 `trl>=0.12`，用 `from trl import SFTTrainer` |
| `wandb.errors.UsageError: api_key not configured` | 没登录 wandb | 设 `report_to="none"` 或先 `wandb login` |

#### 8G 显存下的注意点

`SFTTrainer` 在 8G 上的可用配置只有一种组合：`per_device_train_batch_size=1` + `gradient_accumulation_steps=8` + `max_length=512` + `gradient_checkpointing=True` + 4bit 基座 + `paged_adamw_8bit`。`packing=True` 会把多条短样本拼到 512，提升吞吐但会让峰值显存更接近上限，短指令数据（长度 <200）时收益大、风险小，可以开。DPO 在 8G 上只对 ≤0.5B 模型可行，因为要同时驻留策略与参考模型；7B 的偏好对齐请用 ORPO 或 SimPO，它们不需要参考模型。

### 4.12 bitsandbytes（Windows 装不上的三种解法）

#### 它是干什么的

`bitsandbytes` 提供 8bit/4bit 量化算子，是 QLoRA 的底座：`load_in_4bit`、`bnb_4bit_quant_type="nf4"`、`paged_adamw_8bit` 都由它实现。它在 8G 显存上把 7B 的权重从 14GB 压到约 4GB，是你能否微调 7B 的决定性依赖。**什么时候不该用它**：只做推理时用 GGUF（llama.cpp）而不是 bnb 量化，GGUF 的 CPU/GPU 混合更成熟；纯 CPU 环境不需要它。

#### 安装

Windows 原生从 0.43 起有官方 CUDA wheel，但**仍有相当比例的机器装不上或运行时找不到 DLL**，所以给你三条路，按推荐顺序排列。执行位置：Windows PowerShell（方案 A/B）与 WSL2 Bash（方案 C）。

```powershell

uv pip install torch --index-url https://download.pytorch.org/whl/cu124
uv pip install bitsandbytes>=0.43.0
python -c "import bitsandbytes as bnb; print(bnb.__version__)"
```

```powershell
# 方案 B（Windows 原生兜底）：只有源码包，必须本地编译，需要 VS Build Tools + CUDA Toolkit
# 先装 https://visualstudio.microsoft.com/visual-cpp-build-tools/ 的「使用 C++ 的桌面开发」
# 再装 CUDA Toolkit 12.4，然后：
$env:BNB_CUDA_VERSION="124"
uv pip install bitsandbytes --no-binary bitsandbytes
```

```bash

sudo apt-get update && sudo apt-get install -y build-essential
uv pip install torch --index-url https://download.pytorch.org/whl/cu124
uv pip install bitsandbytes>=0.43.0
python -c "import bitsandbytes as bnb; print(bnb.__version__, bnb.__file__)"
```

#### 最小可用示例

这段代码验证 4bit 量化加载与 NF4 配置是否真的生效，并打印显存占用。执行位置：成功装上 bitsandbytes 的环境（Windows 或 WSL2）。

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"

bnb_cfg = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",                 # NF4 优于 fp4，8G 上固定用它
    bnb_4bit_use_double_quant=True,            # 双重量化，7B 省约 0.4GB
    bnb_4bit_compute_dtype=torch.bfloat16,     # 计算精度用 bf16
)

tok = AutoTokenizer.from_pretrained(MODEL_ID, trust_remote_code=True)
if tok.pad_token is None:
    tok.pad_token = tok.eos_token

model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID, quantization_config=bnb_cfg, device_map={"": "cuda"}, trust_remote_code=True
)
first_param = next(model.parameters())
print("首个权重类型:", first_param.dtype, "| 设备:", first_param.device)
print("已用显存: %.0fMB" % (torch.cuda.memory_allocated() / 1024 ** 2))

# 前向一次，确认 4bit 反量化算子可用
inputs = tok("量化验证：1+1=", return_tensors="pt").to("cuda")
with torch.inference_mode():
    logits = model(**inputs).logits
print("logits 形状:", tuple(logits.shape), "精度:", logits.dtype)

# 8bit 分页优化器（QLoRA 训练用）
import bitsandbytes as bnb
opt = bnb.optim.PagedAdamW8bit(model.parameters(), lr=1e-4)
print("优化器:", type(opt).__name__, "| 显存: %.0fMB" % (torch.cuda.memory_allocated() / 1024 ** 2))
```

预期输出：`首个权重类型: torch.uint8 | 设备: cuda:0`（4bit 打包后 dtype 显示为 uint8）、`已用显存: 400–600MB`（0.5B 4bit）、`logits 形状: (1, N, 151936)`、`优化器: PagedAdamW8bit`。

#### 三种解法对照

| 方案 | 前置条件 | 成功率 | 适用 |
| --- | --- | --- | --- |
| A. Windows 官方 wheel | torch cu124 + 磁盘 3GB | 中 | 日常 LoRA、0.5B–3B QLoRA |
| B. Windows 源码编译 | VS Build Tools + CUDA Toolkit 12.4 + 20 分钟编译 | 低但可控 | 必须留在 Windows 原生时 |
| C. WSL2 官方 wheel | WSL2 + 已装 CUDA 驱动（Windows 侧） | 高 | **7B QLoRA 一律走这条** |

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `load_in_4bit=True` | 4bit 加载 | QLoRA 固定开 |
| `bnb_4bit_quant_type` | 量化类型 | `"nf4"` |
| `bnb_4bit_use_double_quant` | 双重量化 | `True` |
| `bnb_4bit_compute_dtype` | 计算精度 | `torch.bfloat16` |
| `load_in_8bit=True` | 8bit 加载 | 3B 以下且不想 4bit 时用 |
| `bnb.optim.PagedAdamW8bit` | 分页优化器 | QLoRA 固定用它，省 1–2GB |
| `bnb.functional.quantize_4bit` | 手动量化张量 | 自定义量化流程时用 |
| `prepare_model_for_kbit_training` | 训练前处理 | QLoRA 必调用 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `The installed version of bitsandbytes was compiled without GPU support` | 装到了 CPU-only 轮子 | 卸载重装 `>=0.43.0`，或走方案 C |
| `OSError: [WinError 126] 找不到指定的模块。Error loading "...\bitsandbytes\libbitsandbytes_cuda124.dll"` | DLL 缺失或 CUDA 版本不匹配 | 设 `$env:BNB_CUDA_VERSION="124"`；仍失败就转 WSL2 |
| `UserWarning: Matplotlib...` 之外的 `CUDA Setup failed despite GPU being available` | bnb 找不到 CUDA | 确认 `torch.version.cuda` 与 `BNB_CUDA_VERSION` 一致 |
| `No module named 'bitsandbytes.cuda_setup'` | 装的是极老版本 | 升级到 0.43+ |
| `ImportError: cannot import name 'PagedAdamW8bit'` | 版本 API 调整 | 用 `bnb.optim.PagedAdamW8bit` 或升级 |
| 训练时 `CUDA error: an illegal memory access` | bnb 与 torch 版本不匹配 | 锁 `torch==2.6.*` + `bitsandbytes==0.45.*` |

#### 8G 显存下的注意点

| 模型规模 | fp16 权重 | 4bit NF4 权重 | 8G 结论 |
| --- | --- | --- | --- |
| 0.5B | 1GB | 0.3GB | 4bit 可选，全量微调也行 |
| 1.5B | 3GB | 0.9GB | 4bit + LoRA 可训 |
| 7B | 14GB | 3.9–4.3GB | **只能 4bit QLoRA** |
| 14B | 28GB | 7.9GB | 权重已贴上限，不可行 |

Windows 上如果连续三次尝试都失败，不要继续折腾：直接 `wsl --install -d Ubuntu-22.04`，在 WSL2 里 5 分钟装完。这是半年里最省时间的一个决定。

### 4.13 unsloth（可选，说明它在 WSL 更稳）

#### 它是干什么的

Unsloth 用自定义 Triton 内核重写 LoRA 的前向反向，宣称训练速度提升 2 倍、显存降低 50–70%，对 8G 显存机器很有吸引力。**什么时候不该用它**：生产训练流程要求可复现、可审计时不要用它（自定义内核有版本强耦合）；需要非 Llama/Qwen/Gemma 等它支持的架构之外模型时；以及你不愿意被绑定到特定 torch/triton 版本时。

#### 安装

官方明确说明 Windows 原生不受支持，必须 WSL2 或 Linux。执行位置：WSL2 Bash。

```bash
# WSL2 Bash：unsloth 会自带匹配的 torch/triton，不要预先装 torch
uv venv --python 3.11
uv pip install unsloth
uv pip install --no-deps trl peft accelerate bitsandbytes
python -c "import unsloth; print('unsloth ok')"
```

Windows 原生只能说「不推荐」，如果你偏要试，下面这条是社区做法，成功率不高。执行位置：Windows PowerShell。

```powershell
# Windows PowerShell：非官方路径，仅作记录，失败属正常
uv pip install unsloth
python -c "import unsloth" 2>&1 | Select-Object -First 5
```

#### 最小可用示例

这段代码用 Unsloth 加载 4bit 模型并挂 LoRA，打印显存节省与可训练参数。执行位置：WSL2 Bash。

```python
# WSL2 Bash 中运行
import torch
from unsloth import FastLanguageModel

max_seq_length = 1024
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen2.5-0.5B-Instruct-bnb-4bit",
    max_seq_length=max_seq_length,
    dtype=torch.bfloat16,
    load_in_4bit=True,
)

model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"],
    lora_alpha=16,
    lora_dropout=0.0,
    bias="none",
    use_gradient_checkpointing="unsloth",
    random_state=0,
    max_seq_length=max_seq_length,
)
trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
print("可训练参数: %.2fM" % (trainable / 1e6))
print("已用显存: %.0fMB" % (torch.cuda.memory_allocated() / 1024 ** 2))

FastLanguageModel.for_inference(model)
inputs = tokenizer(["用一句话说明什么是 RAG。"], return_tensors="pt").to("cuda")
```

预期输出：`可训练参数: 4.xxM`、`已用显存: 500–900MB`（0.5B 4bit + LoRA），以及一段关于 RAG 的中文回答。

:::warn unsloth 的取舍
Unsloth 会把 torch/triton/xformers 的版本钉死。一旦你以后想装 onnxruntime-gpu 或 TensorRT，冲突概率很高。建议单独开一个 `uv venv .venv-unsloth` 专门给它，不要和主微调环境混用。
:::

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `FastLanguageModel.from_pretrained` | 4bit 加载 | 用它提供的 `*-bnb-4bit` 仓库，省一次量化 |
| `max_seq_length` | 最大长度 | 1024（unsloth 声称长序列优势明显） |
| `use_gradient_checkpointing="unsloth"` | 优化版检查点 | 固定用它 |
| `r` / `lora_alpha` | LoRA 维度 | `r=16, alpha=16` |
| `FastLanguageModel.for_inference` | 切推理模式 | 推理前必调，提速 2 倍 |
| `model.save_pretrained_merged` | 合并导出 | 需要 CPU 内存 16GB+，或直接导 GGUF |
| `model.save_pretrained_gguf` | 导出 GGUF | 8G 上导 Q4_K_M 最实用 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ImportError: DLL load failed` 在 Windows | 官方不支持 Windows | 转 WSL2 |
| `RuntimeError: Unsloth cannot find a compatible Triton` | triton 版本不匹配 | 按 unsloth 文档指定的 triton 版本重装 |
| `torch._dynamo` 相关报错 | torch 版本太新/太旧 | 用它 README 里钉住的 torch 版本 |
| `CUDA out of memory` 在长序列 | `max_seq_length` 太大 | 降到 1024 或 512 |
| `xformers` 安装失败 | Python 版本无轮子 | 用 Python 3.11 |
| 与 `onnxruntime-gpu` 冲突 | CUDA 运行时重复 | 分环境装，别混 |

#### 8G 显存下的注意点

Unsloth 的价值在长序列：官方口径是 8G 上可以跑 `max_seq_length=2048` 以上的 QLoRA，而 peft+trl 原生在 1024 就已经很紧张。如果你的任务必须长上下文（如整篇手册问答），Unsloth 是可行路线；如果序列就是 512–1024，用 peft+trl 更可控、更容易排错。**先跑通 peft+trl，再考虑换 Unsloth 提速**，不要一开始就上 Unsloth，否则出问题你分不清是数据、配置还是内核。

### 4.14 wandb

#### 它是干什么的

Weights & Biases（wandb）做实验追踪：把 loss、学习率、显存、样本输出按 step 记录并画成在线曲线，支持不同 run 对比。你的每个训练项目都应该有实验记录，简历里的「训练曲线」图就来自它。**什么时候不该用它**：网络受限或要求数据不出内网时，用 TensorBoard 或 MLflow；只跑一次性脚本时不必接。

#### 安装

执行位置：二者均可。

```powershell
# Windows PowerShell
uv pip install wandb
wandb login
```

```bash
# WSL2 Bash
uv pip install wandb && wandb login
```

登录时会让你粘贴 API Key（在 wandb 官网账号设置页获取）。若不想联网，设 `$env:WANDB_MODE="offline"`（WSL：`export WANDB_MODE=offline`），记录会写到本地 `wandb/` 目录，之后再 `wandb sync` 上传。

#### 最小可用示例

这段代码跑一个带 wandb 记录的最小训练，同时把显存也记进去。执行位置：二者均可。

```python
import os
import torch
import torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

# 没有账号/不想联网时打开离线模式；CI 里常用
os.environ.setdefault("WANDB_MODE", "offline")
os.environ.setdefault("WANDB_PROJECT", "dsh-4060-demo")

import wandb

wandb.init(
    project=os.environ["WANDB_PROJECT"],
    name="tiny-mlp-amp",
    config={"lr": 3e-4, "batch": 8, "epochs": 3, "amp": True, "note": "4060 8G"},
)

device = "cuda" if torch.cuda.is_available() else "cpu"
x = torch.randn(512, 64)
y = torch.randint(0, 2, (512,))
loader = DataLoader(TensorDataset(x, y), batch_size=wandb.config.batch, shuffle=True)

model = nn.Sequential(nn.Linear(64, 128), nn.ReLU(), nn.Linear(128, 2)).to(device)
opt = torch.optim.AdamW(model.parameters(), lr=wandb.config.lr)
crit = nn.CrossEntropyLoss()

for epoch in range(wandb.config.epochs):
    model.train()
    for step, (xb, yb) in enumerate(loader):
        xb, yb = xb.to(device), yb.to(device)
        with torch.autocast(device_type="cuda", dtype=torch.bfloat16, enabled=(device == "cuda")):
            loss = crit(model(xb), yb)
        opt.zero_grad(set_to_none=True)
        loss.backward()
        opt.step()
        wandb.log({
            "train/loss": loss.item(),
            "train/lr": opt.param_groups[0]["lr"],
            "sys/gpu_mem_mb": torch.cuda.memory_allocated() / 1024 ** 2 if device == "cuda" else 0,
            "epoch": epoch,
        })

wandb.summary["final_loss"] = loss.item()
wandb.finish()
print("wandb 记录完成，mode=", os.environ["WANDB_MODE"], "| 最后一次 loss=%.4f" % loss.item())
```

预期输出：一串 wandb 初始化日志（含 `View run at ...` 或 `offline` 提示），最后 `wandb 记录完成，mode= offline | 最后一次 loss=0.6xxx`，并在当前目录生成 `wandb/` 文件夹。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `wandb.init(project=..., name=...)` | 起一次记录 | `name` 写清实验变量，如 `qlora-r16-seq512` |
| `config=` | 记录超参 | 把 `r/alpha/lr/seq` 全写进去 |
| `wandb.log({...}, step=)` | 按步记录 | 每 5–10 步记一次，别每步记 |
| `wandb.summary` | 记录最终指标 | 存 `final_loss`、`peak_mem_mb`、`tokens_per_s` |
| `WANDB_MODE=offline` | 离线模式 | 网络不稳或内网时用 |
| `WANDB_PROJECT` | 项目名环境变量 | 与 `transformers` 的 `report_to="wandb"` 配合 |
| `report_to="wandb"` | Trainer 集成 | `SFTConfig`/`TrainingArguments` 里设 |
| `wandb.log({"samples": wandb.Table(...)})` | 记录生成样本 | 每个 epoch 存几条生成结果，便于复看 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `wandb: ERROR api_key not configured` | 没登录 | `wandb login` 或设 `WANDB_MODE=offline` |
| `wandb: Network error (ConnectTimeout)` | 网络到 wandb 不通 | 用 `offline` 模式，事后 `wandb sync wandb/offline-run-*` |
| `wandb: WARNING Step is monotonically increasing` | `step` 重复或倒退 | 只用一个全局 step 计数 |
| `wandb` 让训练变慢 | 记录太频繁 | 降 `logging_steps`，图片/样本只在 epoch 级记 |
| `wandb` 上传占满磁盘 | 本地缓存堆积 | 定期删 `wandb/` 下已同步的 run |

#### 8G 显存下的注意点

wandb 本身不占显存，但**记录显存曲线是 8G 机器最重要的调试手段**：把 `torch.cuda.max_memory_allocated()` 每个 epoch 记一次，能提前发现显存缓慢上涨（通常是某个 cache 没释放或 KV 没清）。另外记录 `tokens/s` 和 `samples/s`，量化训练是否值得（QLoRA 比 LoRA 慢 20–40%）靠这个数据说话，而不是感觉。

### 4.15 sentence-transformers

#### 它是干什么的

`sentence-transformers` 把 BERT 类模型包装成「一句话 → 一个向量」的编码器，内置池化与归一化，支持 `bge-m3`、`bge-large-zh-v1.5`、`m3e` 等中文检索模型。你 W15 的 RAG 知识库、W16 的检索优化都以它为核心。**什么时候不该用它**：需要 token 级交叉编码（Rerank 用 `bge-reranker-v2-m3`，可以直接用 transformers 的 `AutoModelForSequenceClassification`）；已经有向量库自带 embedding 接口并且要统一管理时也可以不上它。

#### 安装

执行位置：二者均可，CPU 也能跑（小批量）。

```powershell

python -c "import sentence_transformers as st; print(st.__version__)"
```

```bash
# WSL2 Bash
uv pip install sentence-transformers && python -c "import sentence_transformers as st; print(st.__version__)"
```

#### 最小可用示例

这段代码用中文向量模型算相似度并做一次检索，是 RAG 检索端的核心 8 行。执行位置：二者均可。

```python
import numpy as np
from sentence_transformers import SentenceTransformer, util

# 中文小模型：首次运行会从 HF 下载约 100MB
model = SentenceTransformer("BAAI/bge-small-zh-v1.5", device="cuda" if __import__("torch").cuda.is_available() else "cpu")

corpus = [
    "设备振动超标时，优先检查轴承磨损与联轴器对中情况。",
    "告警收敛是指把同一根因引发的大量告警合并为一条。",
    "轴承温度超过 85 摄氏度会触发二级告警。",
    "日志模板挖掘使用 Drain3 算法对日志做聚类。",
    "RAG 的忠实度指标衡量答案是否被检索到的上下文支持。",
]
query = "振动大怎么排查？"

# bge 系列检索时建议给 query 加指令前缀
q_emb = model.encode("为这个句子生成表示以用于检索相关文章：" + query, normalize_embeddings=True)
c_emb = model.encode(corpus, normalize_embeddings=True, batch_size=16)

scores = util.cos_sim(q_emb, c_emb)[0].cpu().numpy()
order = np.argsort(-scores)
for i in order[:3]:
    print(f"{scores[i]:.4f}  {corpus[i]}")

import torch
print("embedding 维度:", c_emb.shape, "| 显存: %.0fMB" % (torch.cuda.memory_allocated() / 1024 ** 2 if torch.cuda.is_available() else 0))
```

预期输出：三行带分数的句子，第一行应是「设备振动超标时，优先检查轴承磨损与联轴器对中情况。」且分数约 0.6–0.75；最后一行 `embedding 维度: torch.Size([5, 512]) | 显存: 100–200MB`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `SentenceTransformer(model_name, device=...)` | 加载模型 | `bge-small-zh-v1.5`（CPU 也行）或 `bge-m3`（需 2GB 显存） |
| `model.encode(sentences, batch_size=...)` | 批量编码 | `batch_size=32`（small）/ `8`（m3） |
| `normalize_embeddings=True` | L2 归一化 | 检索一律开，配合余弦相似度 |
| `max_seq_length=512` | 最大长度 | 512，长文档先切块 |
| `show_progress_bar=True` | 进度条 | 大批量时开 |
| `util.cos_sim(a, b)` | 余弦相似度矩阵 | 小规模重排用；上万文档用 FAISS |
| `model.encode(..., convert_to_tensor=True)` | 返回张量 | 直接送回 GPU 做后续计算时用 |
| `CrossEncoder("BAAI/bge-reranker-v2-m3")` | 交叉编码重排 | 8G 可跑，batch 8 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `OSError: Can't load tokenizer for 'BAAI/bge-small-zh-v1.5'` | 网络不通 | `$env:HF_ENDPOINT="https://hf-mirror.com"` |
| `RuntimeError: CUDA out of memory` 用 bge-m3 | m3 模型较大且支持 8192 长度 | 降 `batch_size=8`，`max_seq_length=512` |
| 相似度分数普遍偏高（>0.9） | 忘了归一化或用了错误前缀 | 开 `normalize_embeddings=True`，检索 query 加前缀 |
| `TypeError: encode() got an unexpected keyword argument 'normalize_embeddings'` | 版本太老 | 升到 `>=2.7` |
| Rerank 速度慢 | CrossEncoder 逐对计算 | 先向量召回 top 50，再 rerank top 10 |

#### 8G 显存下的注意点

| 模型 | 参数 | 显存（batch 16） | 适用 |
| --- | --- | --- | --- |
| `bge-small-zh-v1.5` | 24M | <300MB | 首选，快 |
| `bge-base-zh-v1.5` | 102M | 约 600MB | 效果更好，仍很轻 |
| `bge-large-zh-v1.5` | 326M | 约 1.5GB | 8G 可用，召回质量最好 |
| `bge-m3` | 568M | 约 2.2GB | 可用，但和 7B LLM 同机时要注意排队 |

关键工程做法：**embedding 与 LLM 不要同时驻留显存**。索引阶段（跑 embedding）和问答阶段（跑 LLM）分开；问答阶段如果必须 rerank，用 `bge-reranker-base` 而不是 `v2-m3`，并且把 LLM 换成 Ollama 的 GGUF（llama.cpp 会按需分配显存）。

### 4.16 FAISS

#### 它是干什么的

FAISS 是 Meta 的向量检索库，提供 CPU 与 GPU 的近似最近邻索引（`IndexFlatIP`、`IndexIVFFlat`、`IndexHNSWFlat`）。数万到千万级向量用它做召回，速度比 NumPy 暴力计算快几十倍。**什么时候不该用它**：需要持久化、元数据过滤、增量删除时用 Chroma 或 Qdrant（FAISS 的删除是墓碑式，长期增删会退化）。

#### 安装

执行位置：二者均可。GPU 版要单独装 `faiss-gpu`，Windows 原生只有 CPU 轮子（用 `faiss-cpu` 即可，几万向量 CPU 完全够）。

```powershell
# Windows PowerShell：原生建议 CPU 版
uv pip install faiss-cpu
python -c "import faiss; print(faiss.__version__)"
```

```bash
# WSL2 Bash：需要 GPU 加速时用 conda 装 faiss-gpu（pip 的 GPU 轮子覆盖不全）
uv pip install faiss-cpu
python -c "import faiss; print('faiss', faiss.__version__)"
# 若要 GPU 版：
# conda install -c pytorch faiss-gpu=1.8.0
```

#### 最小可用示例

这段代码建一个内积索引、写入向量、查询并做元数据回查，是 RAG 召回端的标准写。执行位置：二者均可。

```python
import numpy as np
import faiss
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")
docs = [
    "振动超标排查顺序：轴承、联轴器、叶轮平衡、基础紧固。",
    "轴承温度超过 85 摄氏度触发二级告警。",
    "告警收敛把同根因告警合并为一条。",
    "Drain3 用于日志模板挖掘。",
    "RAGAS 评估忠实度、答案相关性与上下文召回率。",
    "QLoRA 用 4bit NF4 量化把 7B 权重压到约 4GB。",
]
emb = model.encode(docs, normalize_embeddings=True, convert_to_numpy=True).astype("float32")
dim = emb.shape[1]

index = faiss.IndexFlatIP(dim)          # 归一化后用内积等价于余弦相似度
index.add(emb)
print("索引向量数:", index.ntotal, "| 维度:", dim)

query = "轴承温度多少会告警？"
q = model.encode([query], normalize_embeddings=True, convert_to_numpy=True).astype("float32")
scores, idx = index.search(q, k=3)
for s, i in zip(scores[0], idx[0]):
    print(f"{s:.4f}  doc[{i}] {docs[i]}")

# 大规模时用 IVF 索引换取速度：nlist 约为 sqrt(N)
if index.ntotal > 10000:
    quantizer = faiss.IndexFlatIP(dim)
    ivf = faiss.IndexIVFFlat(quantizer, dim, 32, faiss.METRIC_INNER_PRODUCT)
    ivf.train(emb)
    ivf.add(emb)
    ivf.nprobe = 8
    print("IVF 索引就绪:", ivf.ntotal)
else:
    print("向量数较少，用 IndexFlatIP 已足够")

# 持久化
faiss.write_index(index, "kb.index")
loaded = faiss.read_index("kb.index")
print("重新载入后向量数:", loaded.ntotal)
```

预期输出：`索引向量数: 6 | 维度: 512`，三行分数与文档（第一条应为轴承温度那条，分数 0.6+），`向量数较少，用 IndexFlatIP 已足够`，`重新载入后向量数: 6`。

#### 常用参数 / API

| API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `IndexFlatIP(dim)` | 暴力内积索引 | <10 万向量首选，精确且简单 |
| `IndexIVFFlat(quantizer, dim, nlist)` | 倒排索引 | >10 万向量用，`nlist≈sqrt(N)` |
| `ivf.nprobe` | 探测簇数 | 8–16，越大越准越慢 |
| `IndexHNSWFlat(dim, 32)` | 图索引 | 内存换速度，百万级用 |
| `index.add(vectors)` | 写入 | 向量必须 `float32` 且 `C-contiguous` |
| `index.search(q, k)` | 查询 | 召回 `k=20`，再交给 reranker 取 top 5 |
| `faiss.write_index / read_index` | 落盘 | 索引文件按需重建，不入 Git |
| `index.ntotal` | 向量总数 | 作为健康检查打印 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `AssertionError: assert d == self.d` | 查询向量维度与索引不符 | 确认用同一个 embedding 模型 |
| `RuntimeError: The data type of the input is not supported` | 传了 float64 | `.astype("float32")` |
| `RuntimeError: Index not trained` | IVF/PQ 索引没 `train` | `ivf.train(vectors)` 后再 `add` |
| `ImportError: No module named 'faiss'`（装的是 faiss-cpu） | 包名与 import 名不同 | 正确 import 名是 `faiss`，包名才是 `faiss-cpu` |
| GPU 版报 `faiss::gpu::StandardGpuResources` 相关错误 | 混装了 CPU/GPU 版本 | 卸载两个后只装一个 |
| 查询结果比暴力计算差 | `nprobe` 太小 | 提到 16–32，或换 `IndexFlatIP` |

#### 8G 显存下的注意点

FAISS 的 GPU 版会把整个索引放进显存：`IndexFlatIP` 的显存约等于 `向量数 × 维度 × 4 字节`。10 万条 1024 维 = 约 400MB，可以接受；100 万条 = 约 4GB，和你的 LLM 抢显存，必须改用 CPU 索引或 IVF+PQ 压缩。**8G 上的建议是 FAISS 走 CPU**：10 万向量用 `IndexFlatIP` 在 CPU 上查询约 10–30ms，完全满足本地 RAG 的交互要求，把宝贵的显存全留给 LLM。

### 4.17 Chroma

Chroma 是一个轻量向量数据库，自带持久化、元数据过滤、集合（collection）管理与文档增删改，比裸 FAISS 多了「数据库」的部分。你 W15 的 RAG v1 用它最省事，几行代码就能建库、加文档、按 metadata 过滤。**什么时候不该用它**：千万级向量或需要分布式/高可用时用 Milvus、Qdrant、pgvector；需要极致召回速度时 FAISS 更直接。

#### 安装

执行位置：二者均可。

```powershell
# Windows PowerShell

python -c "import chromadb; print(chromadb.__version__)"
```

```bash
# WSL2 Bash
```

#### 最小可用示例

这段代码用自带的 embedding 函数建一个持久化集合，写入带元数据的文档并按条件过滤查询。执行位置：二者均可。

```python
import chromadb
from chromadb.utils import embedding_functions

client = chromadb.PersistentClient(path="./chroma_db")   # 落盘，重启不丢
ef = embedding_functions.SentenceTransformerEmbeddingFunction(model_name="BAAI/bge-small-zh-v1.5")

col = client.get_or_create_collection(
    name="kb_aiops",
    embedding_function=ef,
    metadata={"hnsw:space": "cosine"},
)

docs = [
    "振动超标排查顺序：轴承、联轴器、叶轮平衡、基础紧固。",
    "轴承温度超过 85 摄氏度触发二级告警。",
    "告警收敛把同根因告警合并为一条，减少噪声。",
    "Drain3 用固定深度解析树做日志模板挖掘。",
    "RAGAS 评估忠实度、答案相关性与上下文召回率。",
    "QLoRA 用 4bit NF4 量化把 7B 权重压到约 4GB。",
]
metas = [
    {"source": "手册A", "topic": "振动"},
    {"source": "手册A", "topic": "温度"},
    {"source": "手册B", "topic": "告警"},
    {"source": "手册B", "topic": "日志"},
    {"source": "论文C", "topic": "评测"},
    {"source": "论文C", "topic": "微调"},
]
col.upsert(ids=[f"doc{i}" for i in range(len(docs))], documents=docs, metadatas=metas)
print("集合内文档数:", col.count())

res = col.query(query_texts=["轴承温度多少会告警？"], n_results=3,
                where={"source": "手册A"}, include=["documents", "distances", "metadatas"])
for d, dist, m in zip(res["documents"][0], res["distances"][0], res["metadatas"][0]):
    print(f"dist={dist:.4f} [{m['source']}/{m['topic']}] {d}")

col.delete(ids=["doc3"])
print("删除后文档数:", col.count())
print("已有集合:", [c.name for c in client.list_collections()])
```

预期输出：`集合内文档数: 6`，三行带 `dist` 的结果（均来自「手册A」，最近的是轴承温度那条），`删除后文档数: 5`，`已有集合: ['kb_aiops']`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `PersistentClient(path=...)` | 落盘客户端 | 路径放项目 `data/` 下 |
| `get_or_create_collection(name, metadata={"hnsw:space": "cosine"})` | 建集合 | 中文检索固定 `cosine` |
| `embedding_functions.SentenceTransformerEmbeddingFunction` | 用 ST 模型编码 | `bge-small-zh-v1.5` |
| `col.upsert(ids, documents, metadatas)` | 幂等写入 | 可重复跑，不会产生重复 |
| `col.query(query_texts, n_results, where=...)` | 查询与过滤 | `n_results=5–20`，`where` 做来源过滤 |
| `col.count()` | 文档数 | 健康检查 |
| `col.delete(ids=...)` / `delete_collection` | 删除 | 重建知识库时用 |
| `client.list_collections()` | 列出集合 | 多知识库时用 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `sqlite3.OperationalError: unable to open database file` | 路径不存在或含中文 | 先 `mkdir`，路径用英文 |
| `ValueError: Expected metadata value to be a str, int, float, or bool` | metadata 里塞了 list | 列表用逗号拼成字符串 |
| `chromadb.errors.InvalidCollectionException: Collection ... does not exist` | 名字拼错或没建 | 用 `get_or_create_collection` |
| 查询报 `n_results` 超过集合大小 | 请求条数大于文档数 | `n_results=min(k, col.count())` |
| 首次运行卡在下载模型 | embedding 模型要联网 | 提前 `HF_ENDPOINT=https://hf-mirror.com` 或先缓存模型 |
| 写入慢 | 逐条 `add` | 用 `upsert` 批量传 list |

#### 8G 显存下的注意点

Chroma 的 embedding 默认在 CPU 上跑（除非你显式把 ST 模型放 GPU）。**这正是 8G 机器想要的**：建索引时让 embedding 走 CPU，问答时把显存全给 LLM。若改为 GPU embedding，`bge-small` 只占约 200MB，可以接受，但和 Ollama 的 GGUF 同时跑时容易触发 Ollama 卸载模型到 CPU，导致生成速度从 40 tok/s 掉到 5 tok/s。

### 4.18 rank-bm25

#### 它是干什么的

`rank-bm25` 是纯 Python 的 BM25 实现，做关键词稀疏检索，擅长精确术语、编号、型号匹配——这些恰恰是向量检索的弱项。你的 RAG 混合检索（BM25 + 向量 + Rerank）里 BM25 负责「召回准」。**什么时候不该用它**：语料超过几十万条时纯 Python 实现太慢，改用 Elasticsearch/OpenSearch 的 BM25 或 `bm25s`；同义改写的查询 BM25 完全无能，必须靠向量。

```python
import jieba

docs = [

    "QLoRA 用 4bit NF4 量化把 7B 权重压到约 4GB。",
]

# 中文必须分词；英文/代码术语保留原样
tokenized = [list(jieba.cut(d)) for d in docs]
bm25 = BM25Okapi(tokenized, k1=1.5, b=0.75)

query = "轴承温度 告警"
q_tokens = list(jieba.cut(query))
print("查询词元:", q_tokens)

scores = bm25.get_scores(q_tokens)
ranked = sorted(zip(scores, range(len(docs))), key=lambda x: -x[0])
for s, i in ranked[:3]:
    print(f"{s:.4f}  doc[{i}] {docs[i]}")

top = bm25.get_top_n(q_tokens, docs, n=2)
print("top_n:", top)

# 融合示例：BM25 与向量分数各归一化后加权，是混合检索的最小实现
def norm(scores):
    lo, hi = min(scores), max(scores)
    return [(s - lo) / (hi - lo + 1e-9) for s in scores]

bm_norm = norm(scores)
fake_vec = [0.72, 0.95, 0.31, 0.22, 0.66, 0.40]   # 实际换成 FAISS/Chroma 的相似度
fused = [0.5 * a + 0.5 * b for a, b in zip(bm_norm, norm(fake_vec))]
best = max(range(len(fused)), key=lambda i: fused[i])
print("融合后最佳文档:", docs[best], "| 分数=%.4f" % fused[best])
```

预期输出：`查询词元: ['轴承', '温度', ' ', '告警']`（jieba 版本不同可能略有差别）、三行 BM25 分数（轴承温度那条最高）、`top_n: [...]`，以及一行融合结果。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `BM25Okapi(corpus, k1=1.5, b=0.75)` | Okapi BM25 | `k1=1.2–2.0`，`b=0.75` 默认即好 |
| `bm25.get_scores(tokens)` | 全库打分 | 语料 <10 万条时可用 |
| `bm25.get_top_n(tokens, docs, n=k)` | 直接取 top-k | `k=20` 作为混合检索的候选 |
| `BM25L` / `BM25Plus` | 变体 | 长文档多时试 `BM25L` |
| `jieba.cut(text)` | 中文分词 | 加自定义词典放设备名、型号 |
| `jieba.load_userdict("dict.txt")` | 加载领域词典 | 工业术语必须加，否则被切碎 |
| `bm25.get_batch_scores` | 批量查询 | 评测集批量跑时用 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| 分数全为 0 | 查询词元不在语料里 | 检查分词结果，加领域词典 |
| 中文检索效果极差 | 没分词，按字符切 | 用 jieba 分词后再建索引 |
| `ZeroDivisionError` | 空文档或空查询 | 过滤空文档，查询为空时不调 BM25 |
| 内存暴涨 | 语料太大 | 换 `bm25s`（基于稀疏矩阵，快得多）或 ES |
| `AttributeError: 'BM25Okapi' object has no attribute 'get_top_n'` | 版本太老 | 升级 `rank-bm25>=0.2.2` |
| 每次查询都重新建索引 | 没缓存 BM25 对象 | 用 `pickle` 存 `tokenized` 与 BM25 对象 |

#### 8G 显存下的注意点

BM25 完全在 CPU 与内存里，零显存占用，是 8G 机器做混合检索的最佳搭档。工程上要注意**时序**：BM25 打分、向量召回都在 CPU/小显存上完成后，只把 top-k 上下文交给 LLM，这样 LLM 的显存不会被检索阶段切碎。缓存策略：把 `tokenized` 与 BM25 对象 pickle 到 `data/bm25.pkl`，避免每次启动重新分词。

### 4.19 ragas

#### 它是干什么的

RAGAS 是 RAG 评测框架，用 LLM 当裁判算四个核心指标：忠实度（faithfulness）、答案相关性（answer relevancy）、上下文召回率（context recall）、上下文精确率（context precision）。你 W16 的「RAG 优化与评测体系」和 P7/P11 都靠它产出可写进简历的数字。**什么时候不该用它**：没有可靠 LLM 可用（评测本身要花 API 钱）；或者你的场景有确定的正确答案集，用传统的 EM/F1 更便宜可靠。

#### 安装

执行位置：二者均可。

```powershell
# Windows PowerShell
uv pip install ragas datasets
python -c "import ragas; print(ragas.__version__)"
```

```bash
# WSL2 Bash
uv pip install ragas datasets && python -c "import ragas; print(ragas.__version__)"
```

#### 最小可用示例

这段代码构造评测集、用 DeepSeek 的 OpenAI 兼容接口当裁判、算指标并打印。执行位置：二者均可（需要能联网调 API）。

```python
import os
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_recall, context_precision
from langchain_openai import ChatOpenAI
from ragas.llms import LangchainLLMWrapper

# 用 OpenAI 兼容接口，把 base_url 指向 DeepSeek
os.environ.setdefault("DEEPSEEK_API_KEY", "sk-你的key")
judge_llm = ChatOpenAI(
    model="deepseek-chat",
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com/v1",
    temperature=0.0,
)
ragas_llm = LangchainLLMWrapper(judge_llm)

data = {
    "question": [
        "轴承温度超过多少会触发二级告警？",
        "告警收敛的目的是什么？",
    ],
    "answer": [
        "轴承温度超过 85 摄氏度会触发二级告警。",
        "把同一根因引发的大量告警合并成一条根因告警，减少噪声。",
    ],
    "contexts": [
        ["轴承温度超过 85 摄氏度触发二级告警。"],
        ["告警收敛把同根因告警合并为一条，减少噪声。"],
    ],
    "ground_truth": [
        "85 摄氏度。",
        "减少告警噪声，让运维聚焦根因。",
    ],
}
ds = Dataset.from_dict(data)

result = evaluate(
    ds,
    metrics=[faithfulness, answer_relevancy, context_recall, context_precision],
    llm=ragas_llm,
    embeddings=None,          # answer_relevancy 需要 embedding 时可传 ST 模型
    raise_exceptions=False,
)
print(result)
print({k: round(float(v), 4) for k, v in result.items() if isinstance(v, (int, float))})
```

预期输出：一份评测表（每条样本的四个指标）与汇总字典，形如 `{'faithfulness': 1.0, 'answer_relevancy': 0.93, 'context_recall': 1.0, 'context_precision': 0.95}`。注意裁判是 LLM，**同一份数据两次运行结果会有小幅波动**，写简历时报告三次平均。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `faithfulness` | 答案是否被上下文支持 | 最重要，防止幻觉 |
| `answer_relevancy` | 答案与问题相关性 | 需要 embedding 模型 |
| `context_recall` | 该召回的是否召回 | 需要 `ground_truth` |
| `context_precision` | 召回的排名质量 | 需要 `ground_truth` |
| `evaluate(dataset, metrics, llm=...)` | 跑评测 | 样本 20–50 条即可出趋势 |
| `raise_exceptions=False` | 单条失败不中断 | 批量评测建议 `False` |
| `LangchainLLMWrapper` | 接任意 LLM | 用 DeepSeek/Qwen API 省钱 |
| `result.to_pandas()` | 导出明细 | 存 CSV 写进实验报告 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ImportError: cannot import name 'faithfulness' from 'ragas.metrics'` | 版本 API 变更 | 查版本：0.2 用 `ragas.metrics`，旧版用 `ragas.metrics.answer_relevance` 等 |
| `ValidationError: answer_relevancy requires embeddings` | 没传 embedding | 传 `embeddings=SentenceTransformerEmbeddings(...)` |
| `openai.AuthenticationError` | key 没设或 base_url 错 | 确认 `base_url="https://api.deepseek.com/v1"` |
| `RateLimitError` | 调用太密 | 加 `time.sleep`，或降样本量到 20 条 |
| 指标全为 NaN | 裁判输出无法解析 | 换更强的裁判模型（如 `deepseek-chat` 而非小模型），`temperature=0` |
| 评测花钱超预算 | 每条样本多次调用 LLM | 20 条样本约 20–100 元；先用 5 条试跑 |

#### 8G 显存下的注意点

RAGAS 本身不需要本地 GPU——用 API 当裁判是 8G 机器的正确选择，本地跑 7B 当裁判既慢又不稳。**但要注意预算纪律**：完整评测报 20 条样本 × 4 指标 ≈ 60–100 次 LLM 调用，用 DeepSeek 约几块钱；用 GPT-4 级模型会到几十元。建议流程：先用 5 条样本调通评测脚本，再扩到 20–50 条。评测得到的数字（如忠实度从 0.72 提到 0.91）是简历和答辩里最有说服力的证据。

### 4.20 LangGraph

#### 它是干什么的

LangGraph 用「状态图」组织 Agent：节点是函数、边是跳转条件、状态是共享的 TypedDict，天然支持循环、条件分支、检查点（checkpoint）与人工介入（interrupt）。你的 P9 多智能体（Planner–Executor–Critic）和 P10 工具网关都用它。**什么时候不该用它**：单轮 prompt 调用或线性 chain（用普通函数甚至 LangChain LCEL 就够）；团队已经在用 LlamaIndex Workflows 或 AutoGen 时不要重复引入。

#### 安装

执行位置：二者均可。

```powershell
# Windows PowerShell
uv pip install langgraph langchain-core
python -c "import langgraph; print('langgraph ok')"
```

```bash
# WSL2 Bash
uv pip install langgraph langchain-core && python -c "import langgraph; print('langgraph ok')"
```

#### 最小可用示例

这段代码建一个带条件分支与循环上限的图，先用假 LLM 跑通流程，再演示如何换成真实 API。执行位置：二者均可。

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
import operator


class State(TypedDict):
    question: str
    drafts: Annotated[list, operator.add]     # 累加式字段
    score: int
    rounds: int


def planner(state: State) -> dict:
    return {"drafts": [f"计划：针对「{state['question']}」先检索知识库再作答"], "rounds": state["rounds"] + 1}


def executor(state: State) -> dict:
    return {"drafts": [f"执行第 {state['rounds']} 轮：召回 3 条文档并生成草稿"]}


def critic(state: State) -> dict:
    # 用长度当“打分”，真实项目换成 LLM Judge
    text = "".join(state["drafts"])
    return {"score": min(10, len(text) // 20)}


def should_continue(state: State) -> str:
    if state["score"] >= 8 or state["rounds"] >= 3:
        return "end"
    return "again"


builder = StateGraph(State)
builder.add_node("planner", planner)
builder.add_node("executor", executor)
builder.add_node("critic", critic)
builder.add_edge(START, "planner")
builder.add_edge("planner", "executor")
builder.add_edge("executor", "critic")
builder.add_conditional_edges("critic", should_continue, {"again": "executor", "end": END})

graph = builder.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "demo-1"}}
out = graph.invoke({"question": "轴承振动超标怎么排查？", "drafts": [], "score": 0, "rounds": 0}, config)
print("轮数:", out["rounds"], "| 打分:", out["score"])
for d in out["drafts"]:
    print(" -", d)

# 检查点：同一 thread_id 可恢复，读取最后状态
snapshot = graph.get_state(config)
print("最后状态节点数:", len(snapshot.values["drafts"]), "| 下一节点:", snapshot.next)

# 真实 LLM 版本只需替换节点内部实现：
# from langchain_openai import ChatOpenAI
# llm = ChatOpenAI(model="deepseek-chat", base_url="https://api.deepseek.com/v1", api_key="sk-xxx")
# def planner(state): return {"drafts": [llm.invoke(f"为问题制定计划：{state['question']}").content], "rounds": state["rounds"]+1}
```

预期输出：`轮数: 2 | 打分: 8`（或轮数 3）、若干条计划与执行文本、以及 `最后状态节点数: N | 下一节点: ()`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `StateGraph(State)` | 定义状态图 | 状态用 `TypedDict`，累加字段用 `Annotated[list, operator.add]` |
| `add_conditional_edges(node, fn, mapping)` | 条件分支 | Critic 不通过就回到 Executor |
| `compile(checkpointer=MemorySaver())` | 编译并加内存检查点 | 本地开发用它 |
| `SqliteSaver` | 落盘检查点 | 需要重启恢复时用 `sqlite:///agent.db` |
| `interrupt_before=[...]` | 人工介入 | 花钱/危险操作前停下等确认 |
| `graph.invoke(state, config)` | 同步执行 | `thread_id` 唯一标识一次会话 |
| `graph.stream(state, config)` | 流式输出 | 接 SSE 给前端时用 |
| `graph.get_state(config)` | 读检查点 | 调试与恢复 |
| `recursion_limit` | 最大步数 | 设 20–50，防止死循环烧 token |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `GraphRecursionError: Recursion limit of 25 reached` | 图里有死循环 | 加显式轮数上限，或调 `recursion_limit` |
| `InvalidUpdateError: Expected dict, got str` | 节点返回类型不对 | 节点必须返回 dict（状态增量） |
| `KeyError: 'thread_id'` | 没传 config | `graph.invoke(state, {"configurable": {"thread_id": "x"}})` |
| 累加字段被覆盖 | 没加 `Annotated[list, operator.add]` | 状态定义里加注解 |
| `InvalidUpdateError: At key 'drafts': Can receive only one value per step` | 同一节点重复更新同一 channel | 合并到一次返回 |
| 接 SSE 后无输出 | 用了 `invoke` 而不是 `stream` | 改用 `graph.stream(..., stream_mode="updates")` |

#### 8G 显存下的注意点

LangGraph 本身是纯 Python 编排，不吃显存；它决定的是**你的 Agent 调多少次 LLM**。8G 机器的正确姿势是：编排在本地，LLM 用 Ollama 的 7B GGUF Q4_K_M（约 30–50 tok/s）或 API。Critic 节点最容易失控——每轮都调一次 LLM 会让回合数翻倍，必须设 `rounds <= 3` 的硬上限，并把 token 用量记进 trace（见 4.33），否则一个 bug 能烧掉你一天的 API 预算。

### 4.21 MCP Python SDK

#### 它是干什么的

MCP（Model Context Protocol）是给 LLM 提供工具与资源的开放协议，官方 Python SDK 让你用几十行代码写一个 MCP Server，把「查数据库」「读文件」「调运维 API」暴露成标准工具。写自己的 MCP Server 是 P10 的加分项，也是 2026 年 Agent 岗位的高频要求。**什么时候不该用它**：只是自己项目内部调用两个函数时，直接写 JSON Schema 工具注册表更简单；不需要跨客户端复用时也不必上 MCP。

#### 安装

执行位置：二者均可。

```powershell

uv pip install "mcp[cli]"
python -c "import mcp; print('mcp ok')"
```

```bash
# WSL2 Bash
uv pip install "mcp[cli]" && python -c "import mcp; print('mcp ok')"
```

#### 最小可用示例

这段代码是一个完整可运行的 MCP Server，暴露一个「查设备告警」的工具和一个「手册片段」资源。执行位置：二者均可，保存为 `mcp_server.py`。

```python
# mcp_server.py —— 用 stdio 传输的 MCP Server
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("aiops-tools")

ALARMS = [
    {"id": "A-1001", "device": "pump-a", "level": 2, "msg": "轴承温度 88C 超阈"},
    {"id": "A-1002", "device": "fan-c", "level": 1, "msg": "振动值 4.6mm/s 偏高"},
    {"id": "A-1003", "device": "pump-b", "level": 3, "msg": "主电源掉电"},
]


@mcp.tool()
def list_alarms(device: str = "", min_level: int = 1) -> list[dict]:
    """按设备与最低等级查询当前告警。

    Args:
        device: 设备名，空字符串表示全部设备。
        min_level: 最低告警等级（1=提示，2=重要，3=严重）。
    """
    return [a for a in ALARMS if (not device or a["device"] == device) and a["level"] >= min_level]


@mcp.tool()
def alarm_summary(device: str) -> str:
    """对指定设备的告警做一句话摘要。"""
    items = [a for a in ALARMS if a["device"] == device]
    if not items:
        return f"{device} 当前无告警。"
    worst = max(items, key=lambda a: a["level"])
    return f"{device} 共 {len(items)} 条告警，最高等级 {worst['level']}：{worst['msg']}"


@mcp.resource("manual://pump/vibration")
def vibration_manual() -> str:
    """返回振动排查手册片段。"""
    return "振动排查顺序：1) 轴承磨损 2) 联轴器对中 3) 叶轮平衡 4) 基础紧固。"


if __name__ == "__main__":
    mcp.run()          # 默认 stdio；HTTP 用 mcp.run(transport="streamable-http")
```

启动与自测：先直接运行服务器（会等待 stdin 上的 JSON-RPC，不会打印内容）。执行位置：Windows PowerShell。


#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `FastMCP("name")` | 建服务器 | 名字用项目名，客户端会显示 |
| `@mcp.tool()` | 注册工具 | 函数签名 + docstring 自动生成 JSON Schema |
| `@mcp.resource("scheme://path")` | 注册资源 | 手册、配置等只读内容 |
| `@mcp.prompt()` | 注册提示模板 | 固定工作流提示 |
| `mcp.run()` | 启动（stdio） | 本地客户端调用首选 |
| `mcp.run(transport="streamable-http")` | HTTP 传输 | 远程/多客户端时用 |
| `session.call_tool(name, args)` | 客户端调用 | 写测试时用 |
| 类型注解 `device: str` | 参数 schema | 必须写类型，否则 schema 推断失败 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'mcp.server.fastmcp'` | 版本太老或装的是裸 `mcp` | `pip install -U "mcp[cli]"` |
| `RuntimeError: FastMCP.run() cannot be called from a running event loop` | 在 async 上下文里调 `run()` | 用 `await mcp.run_async()` 或放到 `if __name__ == "__main__"` |
| 客户端连不上（stdio） | stdout 被 print 污染 | **严禁在 MCP Server 里 print**，日志写 stderr 或文件 |
| `ValidationError: 1 validation error for CallToolRequest` | 工具参数名不匹配 | 检查函数参数名与客户端传参一致 |
| Windows 上客户端启动服务器报编码错误 | 默认编码非 UTF-8 | 启动命令加 `$env:PYTHONUTF8="1"` |
| 工具列表为空 | 装饰器没生效或没 import | 确认 `@mcp.tool()` 在被 import 的模块顶层 |

#### 8G 显存下的注意点

MCP Server 本身零显存占用，它是「让弱模型也能干重活」的关键：把统计、查库、聚合这类确定性工作放进 Server 的工具里，LLM 只做路由与措辞。在 8G 机器上这一点尤其重要——7B GGUF 的推理能力有限，如果让模型自己算数、自己拼 SQL，错误率会很高；把它降级成「选工具 + 填参数」成功率会明显上升。另外 stdio 模式的 Server 与 Ollama 同时跑只占内存不占显存，可以放心常驻。

#### 最小可用示例

这段代码用同一套 SDK 分别调 DeepSeek、Qwen、本地 Ollama，并做一次带重试的流式输出。执行位置：二者均可（本地 Ollama 需先 `ollama serve`）。

```python
import os
import time
from openai import OpenAI

PROVIDERS = {
    "deepseek": {
        "base_url": "https://api.deepseek.com/v1",
        "api_key": os.environ.get("DEEPSEEK_API_KEY", "sk-你的key"),
        "model": "deepseek-chat",
    },
    "qwen": {
        "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
        "api_key": os.environ.get("DASHSCOPE_API_KEY", "sk-你的key"),
        "model": "qwen-plus",
    },
    "ollama": {
        "base_url": "http://localhost:11434/v1",
        "api_key": "ollama",          # 本地不需要真 key，但不能为空
        "model": "qwen2.5:7b-instruct-q4_K_M",
    },
}


def make_client(name: str) -> tuple[OpenAI, str]:
    cfg = PROVIDERS[name]
    return OpenAI(base_url=cfg["base_url"], api_key=cfg["api_key"], timeout=60.0), cfg["model"]


def ask(name: str, prompt: str, stream: bool = False) -> str:
    client, model = make_client(name)
    messages = [{"role": "system", "content": "回答不超过两句话。"},
                {"role": "user", "content": prompt}]
    if not stream:
        t0 = time.time()
        resp = client.chat.completions.create(model=model, messages=messages, temperature=0.0, max_tokens=128)
        dt = time.time() - t0
        usage = resp.usage
        print(f"[{name}] {dt:.2f}s prompt={usage.prompt_tokens} completion={usage.completion_tokens}")
        return resp.choices[0].message.content

    first_token_at = None
    t0 = time.time()
    chunks = []
    for ev in client.chat.completions.create(model=model, messages=messages, temperature=0.0,
                                             max_tokens=128, stream=True):
        delta = ev.choices[0].delta.content or ""
        if delta and first_token_at is None:
            first_token_at = time.time() - t0
        chunks.append(delta)
    print(f"[{name}] TTFT={first_token_at:.2f}s 总耗时={time.time() - t0:.2f}s")
    return "".join(chunks)


# 逐个试：没配 key 的服务会抛异常，这里捕获后跳过，便于只跑通本地
for name in ("ollama", "deepseek", "qwen"):
    try:
        print(name, "->", ask(name, "什么是 KV Cache？"))
    except Exception as e:
        print(f"{name} 调用失败（跳过）：{type(e).__name__}: {str(e)[:120]}")

# 流式（本地 Ollama 一定可用）
try:
    print("流式输出:", ask("ollama", "用一句话说明 RAG 的检索阶段做了什么。", stream=True))
except Exception as e:
    print("流式调用失败:", type(e).__name__)
```

预期输出：形如 `[ollama] 0.42s prompt=25 completion=38` 与答案文本；DeepSeek/Qwen 若没配 key 则打印 `调用失败（跳过）：AuthenticationError...`；流式部分打印 `[ollama] TTFT=0.31s 总耗时=2.10s`。

带重试与超时的生产写法如下，直接抄进你的服务代码。执行位置：二者均可。

```python
import time
from openai import OpenAI, APITimeoutError, RateLimitError, APIConnectionError

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama", timeout=120.0, max_retries=0)


def chat_with_retry(messages, model="qwen2.5:7b-instruct-q4_K_M", retries=3, **kw):
    last = None
    for i in range(retries):
        try:
            return client.chat.completions.create(model=model, messages=messages, **kw)
        except (APITimeoutError, RateLimitError, APIConnectionError) as e:
            last = e
            wait = 2 ** i
            print(f"第 {i+1} 次失败（{type(e).__name__}），{wait}s 后重试")
            time.sleep(wait)
    raise RuntimeError(f"重试 {retries} 次仍失败：{last}")


resp = chat_with_retry([{"role": "user", "content": "只回复两个字：收到"}], max_tokens=8)
print("回复:", resp.choices[0].message.content)
```

预期输出：`回复: 收到`（若首次失败会先打印重试行）。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `base_url` | 服务地址 | 云 `https://api.deepseek.com/v1`；本地 `http://localhost:11434/v1` |
| `api_key` | 鉴权 | 本地随便填非空字符串 |
| `model` | 模型名 | 本地用 Ollama 的完整标签（含量化后缀） |
| `temperature` | 随机性 | 评测/抽取用 `0.0`，对话 `0.7` |
| `max_tokens` | 生成长度 | 测试 128，正式 1024 |
| `stream=True` | 流式 | 接 SSE/FastAPI 时必开 |
| `timeout` | 超时 | 本地 120s（首次加载模型慢），云 60s |
| `max_retries=0` + 自己重试 | 重试策略 | 自己控制退避，便于打日志 |
| `response_format={"type": "json_object"}` | JSON 输出 | 结构化抽取用，需模型支持 |
| `usage` | token 统计 | 用来算成本和做预算控制 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `openai.AuthenticationError: Error code: 401` | key 错/没设 | 检查环境变量名与 base_url 是否配套 |
| `openai.APIConnectionError: Connection error` | 本地服务没起或端口错 | `ollama serve`；确认 11434 端口 |
| `openai.NotFoundError: Error code: 404` | 路径少了 `/v1` | base_url 必须以 `/v1` 结尾 |
| `model not found` | Ollama 里没有这个标签 | `ollama list` 查准确名字 |
| `RateLimitError` / `429` | 云服务限流 | 退避重试，或降并发 |
| 中文乱码 | 编码问题 | 统一 UTF-8；Windows 设 `$env:PYTHONUTF8="1"` |
| 流式下 `delta.content` 为 None | 首个 chunk 只有 role | 用 `delta.content or ""` |
| 长回答被截断 | `max_tokens` 太小 | 提到 1024，并检查模型的上下文上限 |

#### 8G 显存下的注意点

| 方案 | 显存 | 速度（7B） | 8G 结论 |
| --- | --- | --- | --- |
| 本地 Ollama Q4_K_M | 约 6GB（含 KV） | 30–50 tok/s | **首选**，可离线 |
| 本地 transformers 4bit | 约 5.5GB | 15–25 tok/s | 可用于需要自定义 logits 的场景 |
| 云 API（DeepSeek/Qwen） | 0 | 30–80 tok/s | 评测、造数据、当裁判用 |
| 本地 14B Q4_K_M | 约 9GB | — | 跑不了 |

工程建议：**开发期用 Ollama 本地，批量任务用 API**。用 API 时把 `usage` 累加打印，设一个日预算（如 5 元）并写进脚本，避免调试循环把预算烧光。

#### 最小可用示例

这是一个完整可运行的服务，包含健康检查、同步推理、SSE 流式三个接口。执行位置：二者均可，保存为 `app.py`。

```python
# app.py —— 最小推理服务，含健康检查与 SSE 流式
import asyncio
import json
import time
from typing import AsyncGenerator

from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field
import uvicorn

app = FastAPI(title="4060 Inference Service", version="0.1.0")
STARTED_AT = time.time()
CALLS = {"total": 0, "errors": 0}


class ChatRequest(BaseModel):
    prompt: str = Field(..., min_length=1, max_length=4096)
    max_tokens: int = Field(128, ge=1, le=1024)
    temperature: float = Field(0.0, ge=0.0, le=2.0)


class ChatResponse(BaseModel):
    text: str
    tokens: int
    latency_ms: float


def fake_llm(prompt: str, max_tokens: int) -> str:
    # 换成 openai SDK 调 Ollama 即可（见 4.22）
    return f"针对「{prompt[:30]}」的回答：" + "这是模型生成的占位内容。" * min(3, max_tokens // 16 + 1)


@app.get("/healthz")
async def healthz():
    return {
        "status": "ok",
        "uptime_s": round(time.time() - STARTED_AT, 1),
        "calls": CALLS["total"],
        "errors": CALLS["errors"],
    }


@app.post("/v1/chat", response_model=ChatResponse)
async def chat(req: ChatRequest):
    t0 = time.perf_counter()
    CALLS["total"] += 1
    try:
        # 真实项目里用 await asyncio.to_thread(...) 包住同步推理，避免阻塞事件循环
        text = fake_llm(req.prompt, req.max_tokens)
    except Exception as e:
        CALLS["errors"] += 1
        raise HTTPException(status_code=500, detail=str(e))
    return ChatResponse(text=text, tokens=len(text), latency_ms=round((time.perf_counter() - t0) * 1000, 1))


async def token_stream(req: ChatRequest) -> AsyncGenerator[str, None]:
    for i in range(min(req.max_tokens, 32)):
        await asyncio.sleep(0.02)                 # 模拟逐 token 生成
        payload = {"delta": f"t{i} ", "index": i}
        yield f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"


@app.post("/v1/chat/stream")
async def chat_stream(req: ChatRequest):
    return StreamingResponse(
        token_stream(req),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )


if __name__ == "__main__":
    uvicorn.run(app, host="127.0.0.1", port=8000, log_level="info")
```

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `Field(..., max_length=4096)` | 请求校验 | 限制输入长度，防 OOM |
| `StreamingResponse(gen, media_type="text/event-stream")` | SSE 流式 | 对话类接口必用 |
| `asyncio.to_thread(sync_fn)` | 把同步推理放线程 | **必须用**，否则阻塞事件循环 |
| `--workers 1` | 进程数 | 8G 显存只够 1 个模型实例，固定 1 |
| `--host 127.0.0.1` | 监听地址 | 本地服务不要开 `0.0.0.0` |
| `HTTPException(status_code=500)` | 错误返回 | 统一 5xx 并计入错误计数 |
| `response_model=` | 响应结构 | 上线前必须有，方便前端对接 |
| `X-Accel-Buffering: no` | 关闭缓冲 | 反向代理后流式必需 |
| `/healthz` | 健康检查 | 压测脚本与 Docker 健康检查都依赖它 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ERROR: [WinError 10013] 以一种访问权限不允许的方式做了一个访问套接字的尝试` | 端口被占用或被排除 | 换端口：`--port 8010` |
| `RuntimeError: no running event loop` | 在同步函数里用了 async | 用 `async def` 或 `asyncio.run` 包住 |
| 流式返回一次性吐出全部内容 | 中间有缓冲 | 加 `X-Accel-Buffering: no`，uvicorn 不要加 `--proxy-headers` 之外的缓冲 |
| `pydantic_core._pydantic_core.ValidationError` | 请求体字段不合法 | 看报错里的 `loc` 字段，对照 `ChatRequest` |
| OOM 后服务不返回 | 推理异常吞掉了 | 用 `try/except` 包住推理并返回 500 |
| `--reload` 下显存不释放 | 每次改动重载模型 | 开发时用小模型，或加载一次后常驻 |
| 高并发下延迟暴涨 | 单模型串行 | 加请求队列与超时，不要靠加 worker |

#### 8G 显存下的注意点

**`--workers 1` 是硬约束**：每个 worker 会加载一份模型，2 个 worker 就把 7B Q4 的 6GB 变成 12GB，直接失败。并发能力靠「单实例 + 异步队列」而不是多进程：用一个全局 `asyncio.Queue` + 单消费者协程包住推理，能平稳扛住 5–10 个并发请求而不 OOM，TTFT 会随排队上升，要在压测报告里诚实体现（见第16.9节的压测脚本）。加载模型用启动事件（`@app.on_event("startup")` 或 lifespan）只做一次，绝不在请求里加载。

```python
# gradio_app.py —— 调本地 Ollama 的聊天界面
import gradio as gr
from openai import OpenAI
from concurrent.futures import ThreadPoolExecutor

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama", timeout=120.0)
MODEL = "qwen2.5:7b-instruct-q4_K_M"
POOL = ThreadPoolExecutor(max_workers=1)     # 8G 只允许一个请求同时跑


def respond(message, history):
    messages = [{"role": "system", "content": "你是工业设备运维助手，回答简洁，必要时给出排查步骤。"}]
    for user_msg, bot_msg in history:
        messages.append({"role": "user", "content": user_msg})
        messages.append({"role": "assistant", "content": bot_msg})
    messages.append({"role": "user", "content": message})

    def run():
        stream = client.chat.completions.create(model=MODEL, messages=messages,
                                                temperature=0.3, max_tokens=512, stream=True)
        acc = ""
        for ev in stream:
            acc += ev.choices[0].delta.content or ""
            yield acc

    # 排队执行，保证显存里只有一个推理在跑
    fut = POOL.submit(lambda: list(run()))
    for partial in run():
        pass
    yield from fut.result()[-1:]


demo = gr.ChatInterface(
    fn=respond,
    title="工业运维助手（本地 7B Q4）",
    description="基于 Ollama + Qwen2.5-7B-Instruct-Q4_K_M，8G 显存本地运行。",
    examples=["轴承温度 88 度报警怎么处理？", "什么是告警收敛？"],
)

if __name__ == "__main__":
    demo.queue(max_size=8).launch(server_name="127.0.0.1", server_port=7860, show_api=False)
```

| `st.progress / st.metric` | 进度与指标 | 展示评测结果 |
| `st.download_button` | 导出结果 | 把 CSV 交给简历/报告 |
| `streamlit run --server.port` | 指定端口 | 8501 默认，冲突就换 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| Gradio 打不开页面 | 防火墙或端口占用 | 换端口，检查 `netstat -ano | findstr 7860` |
| `OSError: Cannot find empty port in range` | 端口区间被占 | `server_port=7861` |
| Streamlit 点按钮后整页重跑 | Streamlit 执行模型如此 | 用 `st.session_state` 保存状态 |
| 并发两个请求后 OOM | 没有排队 | Gradio 用 `demo.queue()`，Streamlit 用 `st.session_state` 锁 |
| 中文显示为方框 | 浏览器字体问题，一般无 | 换浏览器或指定字体 |
| WSL2 里浏览器打不开 localhost | WSL 网络转发问题 | 用 Windows 侧浏览器访问 `http://localhost:7860` |
| 上传大文件卡死 | 未限制大小 | Gradio `gr.File` 配 `max_file_size`，Streamlit 设 `server.maxUploadSize` |

#### 8G 显存下的注意点

这两个框架都只是界面，不吃显存，但**默认的并发行为会害死你**：Gradio 不加 `.queue()`、Streamlit 不控制重跑，两个并发请求就会让 7B Q4 的 6GB 变成 12GB。固定做法：Gradio 用 `ThreadPoolExecutor(max_workers=1)` + `demo.queue(max_size=8)`；Streamlit 把模型加载放进 `@st.cache_resource` 只加载一次。演示录屏时先关掉浏览器其他标签页，能多出 0.3–0.8GB 可用显存。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `ollama pull <tag>` | 下载模型 | 认准 `q4_k_m` |
| `ollama run` / `ollama serve` | 交互 / 启动服务 | 服务默认 11434 |
| `ollama ps` | 查看已加载模型与显存 | 确认 `100% GPU` |
| `PARAMETER num_ctx` | 上下文长度 | **4096**；8192 会让 KV 翻倍 |
| `PARAMETER num_predict` | 最大生成 token | 512 |
| `PARAMETER temperature` | 随机性 | 0.3（抽取/运维问答） |
| `--cache-type-k q8_0 --cache-type-v q8_0` | KV 量化 | 需要长上下文时把 KV 砍半 |
| `OLLAMA_KEEP_ALIVE=5m` | 模型驻留时间 | 长驻内存，避免反复加载 |
| `OLLAMA_NUM_PARALLEL=1` | 并发数 | **固定 1**，8G 上并发只会 OOM |
| `ollama create -f Modelfile` | 自定义模型 | 固化 system prompt 与参数 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `Error: model requires more system memory` | 内存不足 | 换更小的量化标签（`q4_0`）或关掉浏览器 |
| `ollama ps` 显示 `100% CPU` | 没识别到 GPU | 更新显卡驱动；WSL 里确认 `nvidia-smi` 可用 |
| `Error: pull model manifest: file does not exist` | 标签名写错 | `ollama list` 或官网库确认标签 |
| 端口被占用 `bind: address already in use` | 已有 ollama 实例 | 杀掉旧进程或改用其他端口 |
| 生成速度只有几 tok/s | 模型被卸载到 CPU | 降 `num_ctx`，关掉其它占显存程序 |
| `CUDA error: out of memory` | KV cache 太大 | `num_ctx 2048`，加 KV 量化参数 |
| Windows 上首次运行很慢 | 模型从磁盘加载 | 正常，加载后常驻；设 `OLLAMA_KEEP_ALIVE` 延长 |

#### 8G 显存下的注意点

三个数字决定你的体验：`num_ctx`、量化标签、并发数。8G 上的推荐组合是 `q4_k_m` + `num_ctx 4096` + `OLLAMA_NUM_PARALLEL=1`，此时 `ollama ps` 的 SIZE 应在 5.5–6.5GB，`PROCESSOR` 为 `100% GPU`。若必须要 8192 上下文，加 `--cache-type-k q8_0 --cache-type-v q8_0` 把 KV 从约 2GB 降到约 1GB。**绝对不要让 Ollama 和其它吃显存的程序同时跑**：Python 训练脚本还占着 3GB 时，Ollama 会把模型部分卸载到 CPU，速度从 40 tok/s 掉到 5 tok/s，而 `ollama ps` 会显示 `PROCESSOR` 里出现 CPU 比例。

### 4.26 llama.cpp 与 llama-cpp-python（Windows wheel 与 WSL 源码编译两条路）

#### 最小可用示例

这段代码用 `llama-cpp-python` 加载 GGUF 模型做一次生成，并打印速度与显存。执行位置：二者均可（先准备一个 GGUF 文件，可用 Ollama 的 blob 或用 `ollama pull` 后从 `~/.ollama/models` 复制）。

```python
from llama_cpp import Llama
import time
import os

MODEL_PATH = os.environ.get("GGUF_PATH", "qwen2.5-7b-instruct-q4_k_m.gguf")

llm = Llama(
    model_path=MODEL_PATH,
    n_gpu_layers=-1,          # -1 = 全部层上 GPU；显存不够就设 20/28 这样的部分值
    n_ctx=4096,               # 上下文长度
    n_batch=512,              # 提示词批处理大小
    flash_attn=True,          # Ada 架构支持
    type_k=8,                 # KV Cache K 量化到 q8_0（8 = Q8_0）
    type_v=8,                 # KV Cache V 量化到 q8_0
    verbose=False,
)

prompt = "用三句话说明什么是 QLoRA。"
t0 = time.time()
out = llm.create_chat_completion(
    messages=[{"role": "system", "content": "回答简洁。"},
              {"role": "user", "content": prompt}],
    max_tokens=128,
    temperature=0.0,
)
dt = time.time() - t0
text = out["choices"][0]["message"]["content"]
usage = out["usage"]
print("回答:", text.strip()[:200])
print(f"耗时={dt:.2f}s 生成 {usage['completion_tokens']} tokens，速度={usage['completion_tokens']/dt:.1f} tok/s")
print("显存信息:", llm.metadata.get("general.name", "n/a"))
```

预期输出：一段中文回答，`耗时=3.x s 生成 xx tokens，速度=30–45 tok/s`。若速度低于 10 tok/s，说明 `n_gpu_layers` 没生效，检查 CUDA 编译选项。

用命令行做一次标准 benchmark（P6 报告的数据来源）。执行位置：WSL2 Bash。

```bash
# WSL2 Bash：llama-bench 输出 prompt 处理与生成速度
./build/bin/llama-bench -m qwen2.5-7b-instruct-q4_k_m.gguf -ngl 99 -p 512 -n 128 -r 3
```

预期输出：一张表格，含 `pp512`（提示处理 tokens/s）与 `tg128`（生成 tokens/s），4060 Laptop 上 `tg128` 约 30–45 tok/s、`pp512` 约 400–800 tok/s。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `n_gpu_layers=-1` | 全部层上 GPU | 7B Q4_K_M 用 -1；更大的模型用 20–28 部分卸载 |
| `n_ctx` | 上下文长度 | 4096；8192 需 KV 量化 |
| `n_batch` | 提示处理批 | 512（显存紧张降到 256） |
| `type_k / type_v = 8` | KV Cache q8_0 | 长上下文时必开，KV 减半 |
| `flash_attn=True` | FlashAttention | Ada 支持，提速 10–20% |
| `-DCMAKE_CUDA_ARCHITECTURES=89` | 编译目标架构 | 4060 是 sm_89，写错会回落到 CPU |
| `verbose=True` | 打印加载日志 | 排查是否用上 GPU |
| `llm.create_chat_completion` | Chat 接口 | 自动套 chat template |
| `llama-bench -p/-n/-r` | 基准测试 | `-p 512 -n 128 -r 3` |
| `llama-server` | OpenAI 兼容 HTTP 服务 | 替代 Ollama 做压测 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ImportError: libcudart.so.12: cannot open shared object file` | CUDA 运行时找不到 | WSL：`export LD_LIBRARY_PATH=/usr/lib/wsl/lib:$LD_LIBRARY_PATH` |
| `error: command 'cmake' failed` | 没装 CMake 或 VS Build Tools | `winget install Kitware.CMake`，装 VS Build Tools 的 C++ 组件 |
| `llama_model_load: error loading model: unknown model architecture` | GGUF 版本太新 | 升级 llama.cpp 到最新 |
| 速度只有 3–8 tok/s | 编译时没开 CUDA 或架构不对 | 重编译并确认 `-DGGML_CUDA=on -DCMAKE_CUDA_ARCHITECTURES=89` |
| `CUDA error: out of memory` 加载时 | 模型太大或 n_ctx 太大 | 降 `n_ctx=2048`，或换 `q3_k_m` |
| `ValueError: Failed to load model from file` | 路径或文件损坏 | 检查路径（Windows 用正斜杠），校验文件大小 |
| Windows 上 pip 装到 CPU 版还不报错 | wheel 索引没生效 | 加 `--index-strategy unsafe-best-match`，或直接用方案 C |

#### Windows 预编译与 WSL 源码编译对照

| 维度 | Windows 预编译 wheel | WSL2 源码编译 |
| --- | --- | --- |
| 耗时 | 1–2 分钟 | 10–20 分钟 |
| 前置依赖 | 无 | build-essential + cmake |
| CUDA 支持 | 有（cu124 索引） | 有，可自定义优化开关 |
| 首次成功率 | 高 | 高（但需要会看编译报错） |
| 可调项 | 无 | `-DGGML_CUDA`、架构、FlashAttention 等 |
| 8G 结论 | 日常首选 | 需要 `llama-bench`/`llama-server` 时用 |

#### 8G 显存下的注意点

显存账：7B Q4_K_M 权重 4.4GB + KV（`n_ctx=4096`，q8_0 量化后约 1GB）+ 计算缓冲约 0.5GB ≈ 5.9GB，安全。若 `n_ctx=8192` 且 KV 用 fp16，KV 会到约 4GB，总量超 8GB 直接失败——**长上下文必须配 `type_k=8, type_v=8`**。`n_gpu_layers` 是另一个旋钮：7B 用 -1，14B Q4_K_M（约 9GB）用 20–24 层部分卸载（速度会降到 8–15 tok/s，属于能跑但不实用）。

### 4.27 ONNX 导出与 onnxruntime-gpu

#### 它是干什么的

ONNX 是跨框架的模型交换格式，`onnxruntime-gpu` 是它的高性能推理引擎，支持图优化、INT8 量化、CUDA/TensorRT EP。它是 P3（边缘图像分类）与 P6（三后端对比）的跨平台首选：导出一次，Windows/Linux/CPU/GPU 都能跑。**什么时候不该用它**：NVIDIA 专属场景追求极致延迟时用 TensorRT；只做 LLM 文本推理时 GGUF 生态更成熟。

#### 安装

执行位置：Windows PowerShell（原生支持良好）。**注意：onnxruntime-gpu 必须装在独立环境里**，不要和 torch 混装。

```powershell
# Windows PowerShell：部署专用环境，不装 torch
uv venv .venv-deploy --python 3.11
uv pip install onnx onnxruntime-gpu onnxconverter-common
python -c "import onnxruntime as ort; print(ort.__version__, ort.get_available_providers())"
```

```bash
# WSL2 Bash：等价做法
uv venv .venv-deploy --python 3.11
uv pip install onnx onnxruntime-gpu
python -c "import onnxruntime as ort; print(ort.get_available_providers())"
```

预期输出必须包含 `CUDAExecutionProvider`。若只有 `CPUExecutionProvider`，说明装成了 CPU 版。

#### 最小可用示例

这段代码用 PyTorch 导出一个模型到 ONNX，再用 onnxruntime 推理并对比两者的数值一致性。执行位置：训练环境（含 torch）导出 + 部署环境（含 onnxruntime）推理。为方便单文件运行，这里写在一个脚本里，实际项目分两个环境。

```python
# export_and_check.py —— 导出 + 校验（需要 torch 与 onnx 在同一环境）
import numpy as np
import torch
import torch.nn as nn
import onnx

class SmallNet(nn.Module):
    def __init__(self, in_dim=64, n_cls=10):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(in_dim, 128), nn.ReLU(), nn.Linear(128, n_cls))

    def forward(self, x):
        return self.net(x)


model = SmallNet().eval()
dummy = torch.randn(1, 64)

torch.onnx.export(
    model, dummy, "smallnet.onnx",
    input_names=["input"], output_names=["logits"],
    opset_version=17,
    dynamic_axes={"input": {0: "batch"}, "logits": {0: "batch"}},
    do_constant_folding=True,
)
print("导出完成，模型大小:", __import__("os").path.getsize("smallnet.onnx"), "bytes")

onnx_model = onnx.load("smallnet.onnx")
onnx.checker.check_model(onnx_model)
print("ONNX 校验通过，opset:", onnx_model.opset_import[0].version)

with torch.no_grad():
    torch_out = model(dummy).numpy()

import onnxruntime as ort
print("可用 provider:", ort.get_available_providers())
providers = [p for p in ("CUDAExecutionProvider", "CPUExecutionProvider") if p in ort.get_available_providers()]
sess = ort.InferenceSession("smallnet.onnx", providers=providers)
onnx_out = sess.run(["logits"], {"input": dummy.numpy()})[0]

print("最大绝对误差:", float(np.abs(torch_out - onnx_out).max()))
print("使用的 provider:", sess.get_providers())

# 动态 batch 验证
batch = np.random.randn(8, 64).astype("float32")
out8 = sess.run(["logits"], {"input": batch})[0]
print("batch=8 输出形状:", out8.shape)
```

预期输出：`导出完成，模型大小: 3xxxx bytes`、`ONNX 校验通过，opset: 17`、`可用 provider: ['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']`、`最大绝对误差: 1e-06 量级`、`使用的 provider: ['CUDAExecutionProvider', ...]`、`batch=8 输出形状: (8, 10)`。

ONNX INT8 动态量化（P3 的量化对比实验）。执行位置：二者均可。

```python

from onnxruntime.quantization import quantize_dynamic, QuantType
import os

quantize_dynamic(
    model_input="smallnet.onnx",
    model_output="smallnet_int8.onnx",
    weight_type=QuantType.QInt8,
)
print("INT8 模型大小:", os.path.getsize("smallnet_int8.onnx"), "bytes",
```

预期输出：`INT8 模型大小: ... bytes | 压缩比: 3.5x–4.0x`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `torch.onnx.export(opset_version=17)` | 导出 | `17`，兼容性好 |
| `dynamic_axes` | 动态维度 | batch 动态，便于压测不同并发 |
| `do_constant_folding=True` | 常量折叠 | 开，减小图 |
| `ort.InferenceSession(providers=[...])` | 建会话 | 优先 `CUDAExecutionProvider` |
| `sess.intra_op_num_threads` | 算子内并行线程 | CPU 推理时设物理核数 |
| `sess.graph_optimization_level` | 图优化 | `ORT_ENABLE_ALL` |
| `quantize_dynamic(weight_type=QInt8)` | 动态量化 | INT8 权重，CPU 加速 2–4× |
| `onnx.checker.check_model` | 图校验 | 导出后必做 |
| `provider_options` | provider 参数 | 指定 `device_id=0` |
| `sess.get_providers()` | 查看实际 provider | 部署后第一件事就是打印它 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `ImportError: DLL load failed while importing onnxruntime_pybind11_state` | 与 torch 的 CUDA DLL 冲突 | 用独立环境装 onnxruntime-gpu |
| `onnxruntime::cuda::... CUDA failure` | CUDA/cuDNN 版本不匹配 | 装与 CUDA 12.x 匹配的 onnxruntime-gpu |
| `RuntimeError: Non-zero status code returned while running ...` | 不支持的算子或输入形状错 | 提高 `opset_version`，检查 `dynamic_axes` |
| `TypeError: export() got an unexpected keyword argument 'verbose'` | torch 版本 API 变化 | 去掉该参数或升级 torch |
| 只有 `CPUExecutionProvider` | 装了 CPU 版 | `uv pip uninstall onnxruntime && uv pip install onnxruntime-gpu` |
| INT8 后精度掉很多 | 量化过激 | 用静态量化 + 校准集，或只量化部分层 |
| 动态 batch 推理报形状错 | 导出时未声明动态轴 | 加 `dynamic_axes` |

#### 8G 显存下的注意点

ONNX Runtime 的显存占用与 torch 不同：它会预分配 arena，小模型上反而比 torch 多用 100–200MB，但**峰值更可控、无碎片问题**。8G 上做 P6 三后端对比时，ONNX FP32 的 YOLOv8n 约 1.2GB、INT8 约 0.7GB，都比 torch 版的小。LLM 的 ONNX 导出（如 `optimum` 导出的 7B）需要约 15GB 显存，8G 跑不了，LLM 一律走 GGUF。

### 4.28 TensorRT（engine 与显卡架构绑定、Windows 与 WSL 差异）

#### 它是干什么的

TensorRT 是 NVIDIA 的推理优化器，通过层融合、精度校准（FP16/INT8）、kernel 自动调优把延迟压到最低。你 P6 的三后端对比里它代表「NVIDIA 专属最优」。**什么时候不该用它**：需要跨平台部署（用 ONNX）；模型结构频繁变动（每次都要重编译 engine）；只有 8G 且模型本身已经很小（收益不明显）。

:::danger engine 与显卡架构强绑定
TensorRT 生成的 `.engine` 文件**不能跨显卡架构使用**。在 4060 Laptop（sm_89）上编译的 engine 拿到 T4（sm_75）或 A100（sm_80）上会直接报错。云端编译的 engine 也不要拿回本地用。换机器必须重新编译。
:::

#### 安装

执行位置：Windows PowerShell（TensorRT 有 Windows zip 包）或 WSL2 Bash（推荐，与 CUDA 集成更顺）。

```powershell
# Windows PowerShell：TensorRT 通过 pip 安装（TRT 10.x 起官方提供 wheel）
uv pip install tensorrt tensorrt_llm --extra-index-url https://pypi.nvidia.com
python -c "import tensorrt as trt; print(trt.__version__)"
```

```bash
# WSL2 Bash：pip 安装 + 检查 CUDA 版本匹配
uv pip install tensorrt --extra-index-url https://pypi.nvidia.com
python -c "import tensorrt as trt; print('TRT', trt.__version__)"
nvcc --version || echo "无 nvcc 也可用，TRT 自带 CUDA runtime"
```

#### 最小可用示例

这段代码把一个 ONNX 模型编译成 FP16 engine 并推理，输出延迟对比。执行位置：二者均可（需要 GPU 与已导出的 ONNX）。

```python
import time
import numpy as np

TRT_LOGGER_LEVEL = None
try:
    import tensorrt as trt
    import pycuda.driver as cuda
    import pycuda.autoinit  # noqa: F401  必须 import 以初始化 CUDA context
    TRT_AVAILABLE = True
except ImportError as e:
    TRT_AVAILABLE = False
    print("TensorRT 不可用，跳过编译:", e)

import onnxruntime as ort

if TRT_AVAILABLE:
    logger = trt.Logger(trt.Logger.WARNING)
    builder = trt.Builder(logger)
    network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
    parser = trt.OnnxParser(network, logger)

    with open("smallnet.onnx", "rb") as f:
        if not parser.parse(f.read()):
            for i in range(parser.num_errors):
                print("解析错误:", parser.get_error(i))
            raise RuntimeError("ONNX 解析失败")

    config = builder.create_builder_config()
    config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30)   # 1GB workspace，8G 上不要给太多
    config.set_flag(trt.BuilderFlag.FP16)                                 # FP16 精度

    serialized = builder.build_serialized_network(network, config)
    with open("smallnet.engine", "wb") as f:
        f.write(serialized)
    print("engine 编译完成，大小:", len(serialized), "bytes")

    runtime = trt.Runtime(logger)
    engine = runtime.deserialize_cuda_engine(serialized)
    context = engine.create_execution_context()
    print("engine 输入数:", engine.num_io_tensors, "| 绑定名:", [engine.get_tensor_name(i) for i in range(engine.num_io_tensors)])
    print("当前显卡 compute capability:", cuda.Device(0).compute_capability())
    print("提示：这个 engine 只能在相同 major.minor 架构的显卡上使用")

# onnxruntime 基线对比
sess = ort.InferenceSession("smallnet.onnx", providers=["CPUExecutionProvider"])
x = np.random.randn(1, 64).astype("float32")
t0 = time.perf_counter()
for _ in range(50):
    sess.run(None, {"input": x})
ort_ms = (time.perf_counter() - t0) / 50 * 1000
print(f"ONNX Runtime CPU 平均延迟: {ort_ms:.3f} ms")
```

预期输出：`engine 编译完成，大小: xxxxx bytes`、`engine 输入数: 2 | 绑定名: ['input', 'logits']`、`当前显卡 compute capability: (8, 9)`、`提示：这个 engine 只能在相同 major.minor 架构的显卡上使用`、`ONNX Runtime CPU 平均延迟: 0.0xx ms`。

用 `trtexec` 做标准 benchmark（P6 报告用）。执行位置：WSL2 Bash。

```bash
# WSL2 Bash：trtexec 做 FP32/FP16 延迟对比（TensorRT 自带该工具）
trtexec --onnx=smallnet.onnx --saveEngine=smallnet_fp16.engine --fp16 --shapes=input:1x64 --iterations=200 --avgRuns=100
```

预期输出：末尾一段 `[I] === Performance summary ===`，含 `Throughput: xxx qps` 与 `GPU Compute Time: x.xxx ms`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `NetworkDefinitionCreationFlag.EXPLICIT_BATCH` | 显式 batch 维度 | TRT 10 固定用它 |
| `set_flag(trt.BuilderFlag.FP16)` | FP16 精度 | 必开，4060 上提速 1.5–2× |
| `set_flag(trt.BuilderFlag.INT8)` | INT8 精度 | 需校准集；先用 FP16 |
| `set_memory_pool_limit(WORKSPACE, ...)` | workspace 上限 | 1GB（8G 上不要给 4GB） |
| `build_serialized_network` | 编译并序列化 | 结果落盘 `.engine` |
| `runtime.deserialize_cuda_engine` | 加载 engine | 启动时一次，不要每次请求重载 |
| `context.set_input_shape` | 动态 shape | 压测不同 batch 时用 |
| `--fp16 / --int8`（trtexec） | 精度开关 | FP16 起步 |
| `--shapes=input:1x64` | 指定输入形状 | 与导出时的动态轴一致 |
| `--avgRuns=100` | 平均次数 | 100，减少抖动 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `[TRT] Error Code 3: API Usage Error ... serialized engine does not match` | engine 与当前显卡架构不符 | 在当前机器上重新编译 |
| `ModuleNotFoundError: No module named 'pycuda'` | 没装 pycuda | `uv pip install pycuda`（Windows 上可能需要编译） |
| `pycuda._driver.LogicError: cuInit failed: CUDA_ERROR_UNKNOWN` | 驱动太旧 | 升级显卡驱动到 550+ |
| `[TRT] Error Code 1: Cuda Runtime (out of memory)` | workspace 或 batch 太大 | 降 workspace 到 1GB，batch 到 1 |
| `AttributeError: module 'tensorrt' has no attribute 'Logger'` | 装的是 `tensorrt-libs` 之类不完整包 | 重装完整的 `tensorrt` |
| ONNX 解析失败 `Unsupported operator` | opset 太新或算子不支持 | 降 `opset_version=17`，或让 TRT 用插件 |
| Windows 上 import tensorrt 报 DLL 缺失 | CUDA 版本不匹配 | 换用 WSL2，或装与 CUDA 12.x 匹配的 TRT 版本 |

#### Windows 与 WSL2 差异对照

| 维度 | Windows 原生 | WSL2 |
| --- | --- | --- |
| 安装方式 | pip wheel（TRT 10+） | pip wheel 或 tar 包 |
| pycuda | 需要编译，常失败 | 有 wheel，成功率高 |
| engine 可移植性 | 不能与 WSL 混用（架构同但环境不同版本会报错） | 同上 |
| `trtexec` | 在 TensorRT zip 包 `bin/` 下 | pip 安装后通常在 PATH |
| 8G 结论 | 能用但坑多 | **推荐**，尤其配合 ONNX 导出流程 |

#### 8G 显存下的注意点

编译期显存是运行期的 2–4 倍：编译 YOLOv8s 的 INT8 engine 时 workspace + 中间张量可能瞬时占 4–6GB，8G 机器上**必须在没有其他程序占显存时编译**，并把 `set_memory_pool_limit(WORKSPACE, 1<<30)` 限制到 1GB，否则编译阶段就 OOM。运行期收益：YOLOv8n 640 分辨率，torch 约 12ms、ONNX 约 8ms、TensorRT FP16 约 4–5ms，这是 P6 报告里最漂亮的一组数字。

### 4.29 OpenVINO

#### 它是干什么的

OpenVINO 是 Intel 的推理优化工具包，主打 CPU、集成显卡（iGPU）、NPU 上的推理加速，能把 ONNX 转成 IR 格式并做 INT8 量化。你的价值点在「没有独显也能部署」这条叙事上——很多工业现场只有 Intel 平台。**什么时候不该用它**：目标是 NVIDIA GPU 时没有意义；模型含大量自定义算子时转换容易失败。

#### 安装

执行位置：二者均可（Windows 上对 Intel 平台支持好）。

```powershell

python -c "import openvino as ov; print(ov.__version__); print(ov.Core().available_devices)"
```

```bash
# WSL2 Bash：等价做法
uv pip install openvino openvino-dev
python -c "import openvino as ov; print(ov.__version__, ov.Core().available_devices)"
```

#### 最小可用示例

这段代码把 ONNX 转成 OpenVINO IR，在 CPU 与（若有）iGPU 上推理并对比延迟。执行位置：二者均可。

```python
import time
import numpy as np

try:
    import openvino as ov
except ImportError:
    raise SystemExit("请先 uv pip install openvino openvino-dev")

core = ov.Core()
print("可用设备:", core.available_devices)

# 1) 转换 ONNX -> IR（生成 smallnet.xml 与 smallnet.bin）
ov_model = core.read_model("smallnet.onnx")
ov_model.reshape({0: [1, 64]})                     # 静态形状，利于优化
ov.save_model(ov_model, "smallnet_ir.xml")
print("IR 转换完成: smallnet_ir.xml + smallnet_ir.bin")

# 2) 在 CPU 上编译并推理
x = np.random.randn(1, 64).astype("float32")

for device in ["CPU"] + [d for d in core.available_devices if d.startswith("GPU")]:
    compiled = core.compile_model(ov_model, device)
    infer = compiled.create_infer_request()
    # 预热
    for _ in range(5):
        infer.infer({0: x})
    t0 = time.perf_counter()
    for _ in range(50):
        out = infer.infer({0: x})
    ms = (time.perf_counter() - t0) / 50 * 1000
    result = out[compiled.output(0)]
    print(f"[{device}] 平均延迟={ms:.3f} ms 输出形状={result.shape} 首值={float(result[0][0]):.4f}")

# 3) 性能提示（可选，用于给出优化建议）
if "GPU" in core.available_devices:
    print("可用性能提示:", list(core.get_property("GPU", "SUPPORTED_PROPERTIES"))[:5])
```

预期输出：`可用设备: ['CPU', 'GPU']`（有 Intel iGPU 时）、`IR 转换完成: ...`、若干行 `[CPU] 平均延迟=0.0xx ms ...`，以及可选的属性列表。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `core.read_model("x.onnx")` | 读 ONNX | 先 `reshape` 固定形状 |
| `ov.save_model(model, "x.xml")` | 保存 IR | 部署时加载 IR 更快 |
| `core.compile_model(model, "CPU")` | 编译到设备 | `CPU` / `GPU`（iGPU） |
| `ov_model.reshape({0: [1, 64]})` | 固定输入形状 | 静态形状优化效果最好 |
| `compiled.create_infer_request()` | 建推理请求 | 循环内复用，不要每次新建 |
| `infer.infer({0: x})` | 执行 | 预热 5 次再计时 |
| `core.available_devices` | 设备列表 | 部署前必查 |
| `ov.convert_model(pytorch_model, example_input=...)` | 直接从 PyTorch 转 | 不想走 ONNX 时用 |
| `NNCF` 量化 | INT8 量化 | `import nncf; nncf.quantize(model, calib_loader)` |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `RuntimeError: Cannot find the plugin for device GPU` | 没有 Intel GPU 或驱动缺失 | 只用 `CPU`，或装 Intel 显卡驱动 |
| `Exception: Model is not supported` | 存在不支持的算子 | 降 opset 或替换算子；查 OpenVINO 支持算子列表 |
| `openvino.tools.mo` 相关报错 | 新版把转换器挪到了 `openvino` 主包 | 用 `ov.convert_model` 而不是 `mo` |
| 延迟比 ONNX Runtime 还慢 | 没固定输入形状或没预热 | `reshape` 固定形状 + 预热 |
| INT8 量化精度掉太多 | 校准集不代表真实分布 | 用 300–500 张真实样本做校准 |
| pip 装 openvino-dev 太慢/失败 | 包很大 | 只装 `openvino`，转换用 `ov.convert_model` |

#### 8G 显存下的注意点

OpenVINO 在 NVIDIA 独显上没有意义（它不会用 CUDA），跑在 CPU 或 Intel iGPU 上，**不占你的 8GB 显存**。它的真正用途是叙事与兼容性：P6 报告里给出「同一个 ONNX 模型在 4060（TensorRT）、CPU（OpenVINO）、CPU（ONNX Runtime）三种后端上的延迟对比表」，能证明你懂「部署要按目标硬件选后端」这件事，这比多跑一个 CUDA 后端更有说服力。注意在只有 16GB 内存的机器上，OpenVINO 的 CPU 推理会和你的训练脚本抢内存，别同时跑。

| `docker system prune -a` | 大扫除 | 磁盘紧张时用，会删所有未使用镜像 |
| `host.docker.internal` | 容器访问宿主机 | Windows/WSL 通用写法 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `error during connect: ... The system cannot find the file specified` | Docker Desktop 没启动 | 启动 Docker Desktop 等待鲸鱼图标变绿 |
| `Ports are not available: bind: address already in use` | 端口冲突 | 改宿主端口，如 `"8001:8000"` |
| `no matching manifest for linux/amd64` | 镜像没有对应架构 | 换镜像 tag，或加 `platform: linux/amd64` |
| 容器起来就退出 | 配置错误 | `docker compose logs <svc>` 看具体报错 |
| WSL2 里 docker 命令找不到 | 未开 WSL Integration | Docker Desktop → Settings → Resources → WSL Integration |
| 磁盘被镜像占满 | 长期未清理 | `docker system df` 看占用，再 `docker system prune -a` |
| 卷里权限错误（Permission denied） | 容器内用户与宿主用户 UID 不同 | 加 `user: "${UID}:${GID}"` 或改卷目录权限 |

#### 8G 显存下的注意点

Docker 容器默认不占显存，但**不要在容器里跑 LLM**：Windows 上 Docker Desktop 的 GPU 直通需要 WSL2 后端且配置复杂，性能还有损耗，直接在 WSL2 原生装 Ollama 更好。Docker 的正确用途是「无 GPU 依赖的基础设施」——Chroma、Prometheus、Grafana、Langfuse、Postgres。另外它们会吃内存（每个 100–500MB），16GB 内存的机器上同时起 5 个容器后，训练脚本的 `num_workers` 要降到 0，否则容易触发内存交换把训练拖慢。

```python
# src/metrics.py —— 被测试的模块
def recall_at_k(retrieved_ids: list[str], relevant_ids: list[str], k: int = 5) -> float:
    """召回率：前 k 个结果里覆盖了多少比例的相关文档。"""
    if not relevant_ids:
        raise ValueError("relevant_ids 不能为空")
    topk = set(retrieved_ids[:k])
    return len(topk & set(relevant_ids)) / len(set(relevant_ids))


def mrr(retrieved_ids: list[str], relevant_ids: list[str]) -> float:
    """平均倒数排名：第一个相关结果位置的倒数。"""
    relevant = set(relevant_ids)
    for i, doc_id in enumerate(retrieved_ids, 1):
        if doc_id in relevant:
            return 1.0 / i
    return 0.0
```

#### 最小可用示例

这段代码是一个带 `/metrics` 的 FastAPI 服务，同时暴露自定义业务指标与 GPU 显存指标。执行位置：二者均可，保存为 `metrics_app.py`。

```python
# metrics_app.py —— 暴露 /metrics 供 Prometheus 抓取
import time
import random
from fastapi import FastAPI
from fastapi.responses import PlainTextResponse
from prometheus_client import Counter, Histogram, Gauge, generate_latest, CONTENT_TYPE_LATEST
import uvicorn

app = FastAPI(title="metrics demo")

REQUESTS = Counter("infer_requests_total", "推理请求总数", ["endpoint", "status"])
LATENCY = Histogram("infer_latency_seconds", "推理延迟", ["endpoint"],
                    buckets=(0.05, 0.1, 0.25, 0.5, 1, 2, 5, 10))
QUEUE = Gauge("infer_queue_depth", "等待中的请求数")
GPU_MEM = Gauge("gpu_memory_used_mb", "显存占用 MB")

try:
    import pynvml
    pynvml.nvmlInit()
    HANDLE = pynvml.nvmlDeviceGetHandleByIndex(0)
except Exception:
    HANDLE = None


def refresh_gpu_metric():
    if HANDLE is None:
        return
    info = pynvml.nvmlDeviceGetMemoryInfo(HANDLE)
    GPU_MEM.set(info.used / 1024 ** 2)


@app.get("/healthz")
async def healthz():
    return {"status": "ok"}


@app.post("/infer")
async def infer():
    QUEUE.inc()
    t0 = time.perf_counter()
    time.sleep(random.uniform(0.05, 0.4))       # 替换成真实推理
    LATENCY.labels(endpoint="/infer").observe(time.perf_counter() - t0)
    QUEUE.dec()
    REQUESTS.labels(endpoint="/infer", status="200").inc()
    return {"ok": True}


@app.get("/metrics")
async def metrics():
    refresh_gpu_metric()
    return PlainTextResponse(generate_latest(), media_type=CONTENT_TYPE_LATEST)


if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8001)
```

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `Counter(name, doc, [labels])` | 单调计数 | 请求数、错误数 |
| `Histogram(name, doc, buckets=...)` | 分布统计 | 延迟；桶含 0.05–10s |
| `Gauge(name, doc)` | 瞬时值 | 显存、队列深度 |
| `generate_latest()` | 输出文本 | `/metrics` 端点 |
| `scrape_interval: 15s` | 抓取间隔 | 15s，够用且省资源 |
| `--storage.tsdb.retention.time=15d` | 数据保留 | 15 天，够做对比报告 |
| `promql: histogram_quantile(0.95, ...)` | P95 延迟 | 报告里必给 P95 而非均值 |
| `rate(infer_requests_total[5m])` | QPS | 压测时看 |
| `host.docker.internal:8001` | 容器抓宿主机 | Windows/WSL 通用 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| Prometheus 目标 `down` | 地址不可达 | 用 `host.docker.internal`，确认服务监听 `0.0.0.0` |
| `/metrics` 404 | 没注册路由 | 确认 `@app.get("/metrics")` 存在 |
| 指标名带 `_total` 重复 | Counter 自动加后缀 | 不要自己再写 `_total` |
| `pynvml.NVMLError_LibraryNotFound` | 没装 NVIDIA 驱动或 nvidia-ml-py | `uv pip install nvidia-ml-py`，WSL 里确认 `nvidia-smi` 可用 |
| Grafana 查不到数据 | 数据源没配或时间范围错 | 加 Prometheus 数据源 `http://prometheus:9090`，时间范围调 Today |
| 计数为 0 | 没有请求 | 用 `curl` 打几次 `/infer` |
| 多进程下计数不准 | 每个 worker 独立内存 | 单 worker（8G 本来就用 1 个） |

#### 8G 显存下的注意点

监控栈自身在 Docker 里吃约 300–600MB 内存、零显存，可以常驻。**其价值是把「8G 能不能扛住并发」变成数据**：用 4.x 的压测脚本打 1/2/4/8 并发，在 Grafana 上看 `infer_latency_seconds` 的 P50/P95 与 `gpu_memory_used_mb` 曲线，写进 P6 报告。注意 Histogram 的桶要覆盖真实范围（本地 7B Q4 生成 512 token 可能 10–20s），桶设太小会让 P95 全部落在 `+Inf` 桶里失去意义。

### 4.33 Langfuse 或自建 trace（Agent 可观测）

#### 最小可用示例

方案一：用 Langfuse 记录一次带工具调用的 Agent trace。执行位置：二者均可（需先登录 langfuse 拿 key，或自托管后在界面里创建 project）。

```python
# langfuse_trace.py —— 记录一次 Agent 运行的完整 trace
import os
import time
from langfuse import Langfuse

os.environ.setdefault("LANGFUSE_PUBLIC_KEY", "pk-lf-你的公钥")
os.environ.setdefault("LANGFUSE_SECRET_KEY", "sk-lf-你的私钥")
os.environ.setdefault("LANGFUSE_HOST", "http://localhost:3000")   # 自托管地址；云端用 https://cloud.langfuse.com

langfuse = Langfuse()


def fake_llm(prompt: str, tokens: int = 42) -> str:
    time.sleep(0.05)
    return f"针对「{prompt[:20]}」的回答（占位）"


def run_agent(question: str) -> dict:
    trace = langfuse.trace(name="aiops-agent", input={"question": question},
                           metadata={"model": "qwen2.5:7b-instruct-q4_K_M", "device": "4060-8G"})
    total_cost = 0.0

    # 节点 1：规划
    plan_span = trace.span(name="planner")
    plan = fake_llm(f"为问题制定计划：{question}")
    plan_span.end(output=plan)

    # 节点 2：工具调用
    tool_span = trace.span(name="tool:list_alarms", input={"device": "pump-a"})
    alarms = [{"id": "A-1001", "level": 2, "msg": "轴承温度 88C 超阈"}]
    tool_span.end(output=alarms)

    # 节点 3：生成（记录为 generation，便于统计 token 与成本）
    gen = trace.generation(
        name="final_answer",
        model="qwen2.5:7b-instruct-q4_K_M",
        input=[{"role": "user", "content": question}],
        model_parameters={"temperature": 0.3, "max_tokens": 512},
    )
    answer = fake_llm(f"{question} | 上下文：{alarms}", tokens=88)
    gen.end(output=answer, usage={"input": 320, "output": 88, "unit": "TOKENS"})

    trace.update(output={"answer": answer}, tags=["local", "aiops"])
    langfuse.flush()
    return {"answer": answer, "alarms": alarms, "cost_usd": total_cost}


result = run_agent("pump-a 轴承温度 88 度报警怎么处理？")
print("Agent 输出:", result["answer"])
print("trace 已上报，去 Langfuse 界面查看 trace 名称 aiops-agent")
```

方案二：不想依赖第三方时，用 SQLite 自建 trace 表，40 行搞定。执行位置：二者均可，保存为 `trace_store.py`。

```python
# trace_store.py —— 自建最小 trace 存储与查询
import json
import sqlite3
import time
import uuid

DB = "agent_trace.db"


def init_db() -> None:
    with sqlite3.connect(DB) as conn:
        conn.execute("""
            CREATE TABLE IF NOT EXISTS span (
                span_id     TEXT PRIMARY KEY,
                trace_id    TEXT NOT NULL,
                parent_id   TEXT,
                name        TEXT NOT NULL,
                kind        TEXT NOT NULL,        -- agent / tool / llm / chain
                started_at  REAL NOT NULL,
                ended_at    REAL,
                latency_ms  REAL,
                in_tokens   INTEGER DEFAULT 0,
                out_tokens  INTEGER DEFAULT 0,
                cost_usd    REAL DEFAULT 0,
                status      TEXT DEFAULT 'ok',
                error       TEXT,
                payload     TEXT
            )
        """)
        conn.execute("CREATE INDEX IF NOT EXISTS idx_trace ON span(trace_id)")
        conn.execute("""
            CREATE TABLE IF NOT EXISTS feedback (
                trace_id TEXT, score REAL, comment TEXT, created_at REAL
            )
        """)


def start_span(trace_id: str, name: str, kind: str, parent_id: str | None = None, payload: dict | None = None) -> str:
    span_id = str(uuid.uuid4())
    with sqlite3.connect(DB) as conn:
        conn.execute(
            "INSERT INTO span (span_id, trace_id, parent_id, name, kind, started_at, payload) VALUES (?,?,?,?,?,?,?)",
            (span_id, trace_id, parent_id, name, kind, time.time(), json.dumps(payload or {}, ensure_ascii=False)),
        )
    return span_id


def end_span(span_id: str, in_tokens: int = 0, out_tokens: int = 0, cost_usd: float = 0.0,
             status: str = "ok", error: str | None = None, output: dict | None = None) -> None:
    with sqlite3.connect(DB) as conn:
        row = conn.execute("SELECT started_at, payload FROM span WHERE span_id=?", (span_id,)).fetchone()
        started = row[0]
        payload = json.loads(row[1] or "{}")
        payload["output"] = output or {}
        conn.execute(
            "UPDATE span SET ended_at=?, latency_ms=?, in_tokens=?, out_tokens=?, cost_usd=?, status=?, error=?, payload=? WHERE span_id=?",
            (time.time(), (time.time() - started) * 1000, in_tokens, out_tokens, cost_usd, status, error,
             json.dumps(payload, ensure_ascii=False), span_id),
        )


def trace_summary(trace_id: str) -> list[tuple]:
    with sqlite3.connect(DB) as conn:
        return conn.execute(
            "SELECT name, kind, ROUND(latency_ms,1), in_tokens, out_tokens, status FROM span WHERE trace_id=? ORDER BY started_at",
            (trace_id,),
        ).fetchall()


if __name__ == "__main__":
    init_db()
    tid = str(uuid.uuid4())
    s1 = start_span(tid, "planner", "agent", payload={"question": "轴承温度 88 度怎么处理"})
    time.sleep(0.05)
    end_span(s1, in_tokens=120, out_tokens=40, cost_usd=0.0, output={"plan": "查告警→查手册→生成建议"})

    s2 = start_span(tid, "tool:list_alarms", "tool", parent_id=s1, payload={"device": "pump-a"})
    time.sleep(0.02)
    end_span(s2, output={"count": 1})

    s3 = start_span(tid, "final_answer", "llm", parent_id=s1, payload={"model": "qwen2.5:7b-q4_k_m"})
    time.sleep(0.8)
    end_span(s3, in_tokens=320, out_tokens=88, cost_usd=0.0, output={"answer": "先检查轴承与冷却系统。"})

    print("trace_id:", tid)
    for row in trace_summary(tid):
        print("name=%-18s kind=%-6s latency=%-7s in=%-4s out=%-4s status=%s" % row)
    total_ms = sum(r[2] for r in trace_summary(tid))
    print("总链路耗时: %.1f ms" % total_ms)
```

预期输出：`trace_id: <uuid>`，三行 span 明细（`planner` 约 50ms、`tool:list_alarms` 约 20ms、`final_answer` 约 800ms），以及 `总链路耗时: 87x.x ms`。

#### 常用参数 / API

| 参数 / API | 作用 | 8G 场景下的推荐值 |
| --- | --- | --- |
| `langfuse.trace(name=..., input=...)` | 起一次 trace | 每次 Agent 运行一个 |
| `trace.span(name=..., input=...)` | 记录节点/工具 | 每个工具调用一个 span |
| `trace.generation(model=..., input=...)` | 记录 LLM 调用 | 必填 model 便于成本统计 |
| `gen.end(usage={"input":..,"output":..})` | 上报 token | 用于算成本与预算 |
| `trace.score(name, value)` | 打分 | 人工或 LLM Judge 打分 |
| `langfuse.flush()` | 强制上报 | 脚本结束前必调 |
| `LANGFUSE_HOST` | 自托管地址 | `http://localhost:3000` |
| 自建 `span` 表 | 最小可观测 | 字段：trace_id/name/kind/latency/tokens/status |
| `CREATE INDEX ON span(trace_id)` | 查询加速 | 有索引才能按 trace 快速拉全链 |

#### 常见报错与解决

| 报错原文 | 原因 | 解决 |
| --- | --- | --- |
| `AuthenticationError: Invalid public key` | key 错或 host 不对 | 自托管确认 `LANGFUSE_HOST`，云端用 `https://cloud.langfuse.com` |
| 界面上看不到 trace | 没 flush | 结束前调 `langfuse.flush()`；异步上报有延迟 |
| `docker compose up` 后 3000 端口冲突 | Grafana 也占 3000 | 改 Langfuse 映射端口，如 `3001:3000` |
| 自建表查询慢 | 没建索引 | `CREATE INDEX ON span(trace_id)` |
| trace 里 token 为 0 | 没传 usage | 从 OpenAI 兼容接口的 `resp.usage` 取值填进去 |
| 上报拖慢主流程 | 同步上报 | Langfuse 默认异步；自建表用后台线程或批量写 |
| 数据量增长快 | 全量记录 payload | 大文本只记摘要与前 500 字符 |

#### 8G 显存下的注意点

Langfuse 自托管在 Docker 里，不吃显存但吃内存（约 500MB–1GB），16GB 内存机器上和训练脚本同时跑要留神。**在 8G 机器上 trace 的最大价值是「算清 Agent 的 token 账」**：一个 Planner–Executor–Critic 循环跑 3 轮的 Agent，单次任务可能调用 LLM 6–10 次、消耗 3k–8k token；用 trace 表把每次调用的 `in_tokens/out_tokens/cost_usd` 记下来，你才能在面试里回答「这个 Agent 一次任务成本多少、延迟多少、瓶颈在哪个节点」——这是 P9 报告里最有分量的部分。

### 版本兼容矩阵

下面这套组合是 2026 年 10 月在 Windows 11 + WSL2 Ubuntu 22.04、RTX 4060 Laptop 8GB 上验证可用的搭配。**半年内不要换**，换任何一个大版本都要重跑一遍最小示例。

| trl | 0.12.x | 0.11–0.13 | ≥0.12 用 `processing_class`/`max_length` |
| bitsandbytes | 0.45.x | 0.43–0.46 | Windows 需 ≥0.43；WSL 更稳 |
| accelerate | 1.0.x | 0.34–1.2 | 与 trl 版本配套 |
| datasets | 3.1.x | 2.20–3.2 | ≥3.0 与 pyarrow 15+ 配套 |

:::warn 三个最容易踩的版本坑
- `transformers` 升到 4.50+ 后 `trl` 的 `SFTConfig` 参数名仍在变，锁版本比追新省时间。

- `onnxruntime-gpu` 与 `torch` 同环境时容易 DLL 冲突，这是「微调与部署环境必须分开」的直接原因。
:::

### 「微调环境与部署环境必须分开」的操作步骤
