#### D1（周一，2.5h）｜把 LoRA 的数学手推一遍，手写最小实现

先用 40 分钟把论文公式抄一遍并解释：冻结 `W0 ∈ R^{d×k}`，只训练 `B ∈ R^{d×r}`、`A ∈ R^{r×k}`，前向为 `h = W0 x + (alpha / r) · B A x`，`A` 用高斯初始化、`B` 初始化为全零（所以训练开始时 `ΔW = 0`，不破坏预训练权重）。

```python
# 手写 LoRA 层，验证「可训练参数只占原层 0.5% 左右」
import math
import torch
import torch.nn as nn


class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r: int = 8, alpha: int = 16, dropout: float = 0.05):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False          # 冻结原权重
        self.r = r
        self.scaling = alpha / r
        self.lora_A = nn.Parameter(torch.empty(r, base.in_features))
        self.lora_B = nn.Parameter(torch.zeros(base.out_features, r))
        nn.init.kaiming_uniform_(self.lora_A, a=math.sqrt(5))
        self.drop = nn.Dropout(dropout)

    def forward(self, x):
        out = self.base(x)
        delta = self.drop(x) @ self.lora_A.T @ self.lora_B.T
        return out + delta * self.scaling


base = nn.Linear(4096, 4096, bias=False)
layer = LoRALinear(base, r=8, alpha=16)
trainable = sum(p.numel() for p in layer.parameters() if p.requires_grad)
total = sum(p.numel() for p in layer.parameters())
print(f"trainable={trainable:,} total={total:,} ratio={trainable / total:.4%}")
```

预期输出：`trainable=65,536 total=16,842,752 ratio=0.3891%`。记住这个量级——它解释了为什么 LoRA 优化器状态几乎不占显存，而 QLoRA 省的是**权重**那一份。

#### D2（周二，2.5h）｜QLoRA 原理拆解：NF4、双重量化、分页优化器

写一份 1 页的原理笔记（推 GitHub，作为本周文档化动作），必须覆盖四个点：

1. **NF4（4-bit NormalFloat）**：假设预训练权重近似零均值正态分布，把分位数作为量化台阶，对正态数据是信息论最优；对比 `fp4`（等距量化）。
2. **双重量化（double quantization）**：第一层 4bit 量化后每个 block（典型 64 个权重）需要一个 fp32 的 scale，双重量化把这个 scale 再 8bit 量化一次，平均每个参数从 32/64 bit 降到 8/64 + 8/(64×256) bit。
3. **分页优化器（paged optimizer）**：优化器状态放在 pinned memory，显存吃紧时自动换出到内存，避免 OOM 直接崩掉。
4. **计算精度**：`bnb_4bit_compute_dtype=torch.bfloat16` 决定反量化后用什么精度算矩阵乘，这是吞吐的关键。

```python
# 量化前后显存占用对比（只加载，不训练，验证 NF4 的 0.5 byte/param 口径）
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

MODEL = "Qwen/Qwen3-8B"

cfg = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
tok = None
model = AutoModelForCausalLM.from_pretrained(MODEL, quantization_config=cfg, device_map={"": 0})
torch.cuda.synchronize()
print("4bit 加载后显存:", round(torch.cuda.memory_allocated() / 1024**3, 3), "GB")
# 8B × 0.5 byte ≈ 4.0GB，加双重量化 scale 与 CUDA context，落在 4.3–5.0GB 区间
```

预期输出：`4bit 加载后显存: 4.4` 左右 GB。**注意 Qwen3-8B 是 8B 而不是 7B，简报里「7B ≈ 3.9–4.3GB」的口径对应的是 7B 模型；8B 会各高约 15%。** 如果你的可用显存只有 7.0GB，D3 的训练峰值必须靠梯度检查点压住。

#### D3（周三，3h）｜第一次 7B QLoRA：把超参按 8GB 定死

这一天的目标不是效果好，是**不 OOM 地跑完 200 步**。超参全部按 8GB 定死：

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 模型 | `Qwen/Qwen3-8B`（或 7B 级 `Qwen/Qwen2.5-7B-Instruct`） | 4bit 权重约 4.4GB |

| 优化器 | `paged_adamw_8bit` | 状态按 8bit 存 + 可分页换出 |
| LoRA `r` / `alpha` / `dropout` | 16 / 32 / 0.05 | alpha=2r 是安全起点 |
| 学习率 | 1e-4，cosine，warmup 10 步 | QLoRA 常用区间 1e-4 ~ 2e-4 |
| `PYTORCH_CUDA_ALLOC_CONF` | `expandable_segments:True` | 缓解碎片导致的假 OOM |

```python
# prepare_sft.py：把 Alpaca 格式转成 Qwen3 的 chat 模板，只留 2000 条做首跑
import json
from datasets import load_dataset
from transformers import AutoTokenizer

MODEL = "Qwen/Qwen3-8B"
tok = AutoTokenizer.from_pretrained(MODEL, trust_remote_code=True)

ds = load_dataset("json", data_files="data/alpaca_zh.jsonl", split="train").select(range(2000))

def to_text(ex):
    msgs = [{"role": "user", "content": (ex["instruction"] + "\n" + ex.get("input", "")).strip()}]
    msgs.append({"role": "assistant", "content": ex["output"]})
    return {"text": tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=False)}

ds = ds.map(to_text, remove_columns=ds.column_names)
ds.to_json("data/sft_train.jsonl", orient="records", lines=True, force_ascii=False)
print("样本数:", len(ds))
print(ds[0]["text"][:400])
```

#### D4（周四，3h）｜正式训练 200 步并记录峰值显存与耗时

```python
# train_qlora.py：8GB 显存上的 7B/8B QLoRA 最小可运行脚本
import os
os.environ["PYTORCH_CUDA_ALLOC_CONF"] = "expandable_segments:True"

import torch
from datasets import load_dataset
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from trl import SFTConfig, SFTTrainer

MODEL = "Qwen/Qwen3-8B"
OUT = "outputs/qwen3-8b-qlora-w13"

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
tok = AutoTokenizer.from_pretrained(MODEL, trust_remote_code=True)
if tok.pad_token is None:
    tok.pad_token = tok.eos_token

model = AutoModelForCausalLM.from_pretrained(
    MODEL, quantization_config=bnb, device_map={"": 0}, torch_dtype=torch.bfloat16
)
model = prepare_model_for_kbit_training(model, use_gradient_checkpointing=True)
model.config.use_cache = False

lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"],
)
model = get_peft_model(model, lora)
model.print_trainable_parameters()

ds = load_dataset("json", data_files="data/sft_train.jsonl", split="train")

args = SFTConfig(
    output_dir=OUT,
    max_steps=200,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    gradient_checkpointing=True,
    gradient_checkpointing_kwargs={"use_reentrant": False},
    learning_rate=1e-4,
    lr_scheduler_type="cosine",
    warmup_steps=10,
    logging_steps=10,
    save_steps=100,
    bf16=True,
    optim="paged_adamw_8bit",
    max_length=512,
    packing=False,
    report_to="none",
    seed=42,
)
trainer = SFTTrainer(model=model, args=args, train_dataset=ds, processing_class=tok)

torch.cuda.reset_peak_memory_stats()
trainer.train()
peak = torch.cuda.max_memory_allocated() / 1024**3
print(f"峰值显存 allocated = {peak:.2f} GB")
print(f"峰值显存 reserved  = {torch.cuda.max_memory_reserved() / 1024**3:.2f} GB")
```

预期输出：训到第 10 步左右打印 loss（通常在 1.5–2.5 之间波动），200 步耗时约 **35–70 分钟**（4060 Laptop 约 115W 时快，电池模式或降频会明显变慢）。程序末尾打印 `峰值显存 allocated = 6.6~7.4 GB`。**如果超过 7.4GB，先降 `max_length` 到 384、把 `lora_dropout` 设 0，再不行就换 `Qwen/Qwen3-4B`。**

```python
# vram_utils.py：统一显存读取口径
import gc
import torch


def reset_vram():
    gc.collect()
    torch.cuda.empty_cache()
    torch.cuda.reset_peak_memory_stats()


def vram_report(tag: str = ""):
    alloc = torch.cuda.memory_allocated() / 1024**3
    peak = torch.cuda.max_memory_allocated() / 1024**3
    reserved = torch.cuda.memory_reserved() / 1024**3
    print(f"[{tag}] allocated={alloc:.2f}GB peak={peak:.2f}GB reserved={reserved:.2f}GB")
```

### 自检题

1. **LoRA 里 `B` 为什么初始化为零？** 答案要点：保证训练开始时 `ΔW = BA = 0`，模型行为与预训练权重完全一致，训练曲线从基座水平起步，不会因为随机扰动先掉一大截。
2. **`lora_alpha` 和 `r` 的关系是什么？** 答案要点：有效缩放系数是 `alpha / r`；改 `r` 会同时改参数量和缩放，改 `alpha` 只改缩放，所以调参通常固定 `alpha = 2r` 再动学习率。
3. **NF4 相比 fp4 的优势前提是什么？** 答案要点：前提是权重近似零均值正态分布；NF4 用分位数当台阶，对大权重区间的分辨率更高，而 fp4 是等距的，尾部误差大。
4. **双重量化具体省了什么？** 答案要点：省的是每个 block 的 fp32 scale；把它再 8bit 量化后，平均每参数的开销从 32/64 bit 降到约 8/64 + 8/(64×256) bit，7B 模型上省约 0.3–0.5GB。
5. **为什么必须 `use_gradient_checkpointing=True` 且 `model.config.use_cache=False`？** 答案要点：检查点用重算换显存，把中间激活量级压下来；而 KV Cache 与检查点机制冲突，不关会报警甚至结果异常。
6. **`paged_adamw_8bit` 在什么情况下会变慢？** 答案要点：显存吃紧触发换页时，优化器状态在 pinned memory 与显存之间来回拷，PCIe 带宽成为瓶颈；显存宽松时它和 `adamw_torch` 差不多。

### 踩坑提醒

:::warn bitsandbytes 在 Windows 原生装不上
报错原文：`RuntimeError: CUDA Setup failed despite GPU being available. Please run the following command to get more information: python -m bitsandbytes`，或 `ImportError: DLL load failed while importing _bitsandbytes`。解法：**不要在 Windows 原生跑 QLoRA**，进 WSL2 Ubuntu 22.04，用 `uv pip install bitsandbytes>=0.43.0`；确认 `python -m bitsandbytes` 输出里 `Device: cuda` 且能列出 4060 Laptop。
:::

:::warn 8bit 优化器与 bf16 参数的 dtype 冲突
报错原文：`ValueError: Attempting to use 8-bit optimizer with fp16/bf16 parameters. Please pass a model with fp32 parameters.`。解法：这正是 `prepare_model_for_kbit_training` 的作用——它会把 LayerNorm 等非量化层升到 fp32；确保你在 `get_peft_model` **之前**调用了它，并且 `bnb_4bit_compute_dtype` 仍是 bf16（计算精度不等于参数精度）。
:::

:::warn 训练 loss 不降，输出变成复读机
现象：loss 稳定在 0.9 以下不动、生成时无限重复一句话。原因通常是 chat 模板没对齐——`apply_chat_template` 生成的文本里 assistant 部分被截断，或 `add_generation_prompt=True` 用在了训练数据上。解法：训练数据必须 `add_generation_prompt=False`，推理时才用 `True`；打印第一条样本全文肉眼确认 `<|im_start|>assistant` 段落存在。
:::

:::warn OOM 发生在第 1 步但不是模型太大
报错原文：`torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate 1.20 GiB. GPU 0 has a total capacity of 8.00 GiB of which 1.05 GiB is free`。先看是不是浏览器/本地 LLM 占了显存：关掉 Chrome 硬件加速、退出 Ollama（`ollama stop` 或直接结束进程），再用 `nvidia-smi` 确认空闲显存回到 7.0GB 以上；然后设 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 并在脚本开头 `torch.cuda.empty_cache()`。
:::

#### D1（周一，2.5h）｜定数据规范：格式、字段、长度分布

统一数据 schema 为 `{"instruction": str, "input": str, "output": str, "source": str, "domain": str}`。写一个校验脚本，把不合格样本单独落到 `data/rejected.jsonl`。

```python
# validate_sft.py：指令数据质量校验，输出统计与拒收原因
import json
import re
from collections import Counter

BAD_PATTERNS = [r"作为(一个)?(AI|人工智能)语言模型", r"我无法", r"对不起", r"未知错误"]

def load(path):
    with open(path, "r", encoding="utf-8") as f:
        for line in f:
            line = line.strip()
            if line:
                yield json.loads(line)

reasons = Counter()
kept, rejected = [], []
for ex in load("data/domain_raw.jsonl"):
    out = (ex.get("output") or "").strip()
    ins = (ex.get("instruction") or "").strip()
    if len(ins) < 4:
        reasons["instruction 过短"] += 1; continue
    if len(out) < 20:
        reasons["output 过短"] += 1; continue
    if len(out) > 4000:
        reasons["output 过长"] += 1; continue
    if any(re.search(p, out) for p in BAD_PATTERNS):
        reasons["模板拒答"] += 1; continue
    if out.count("\n") > 40:
        reasons["换行异常"] += 1; continue
    kept.append(ex)

with open("data/domain_clean.jsonl", "w", encoding="utf-8") as f:
    for ex in kept:
        f.write(json.dumps(ex, ensure_ascii=False) + "\n")

print(f"保留 {len(kept)} 条，拒收 {sum(reasons.values())} 条")
for k, v in reasons.most_common():
    print(f"  {k}: {v}")
lens = [len(ex["output"]) for ex in kept]
lens.sort()
print("output 长度 P50/P90/P99:",
      lens[len(lens)//2], lens[int(len(lens)*0.9)], lens[int(len(lens)*0.99)])
```

预期输出：保留/拒收计数与三类拒收原因分布，以及输出长度的分位数。**P99 超过 3000 字符的样本先考虑截断，因为 seq 512 装不下。**

#### D2（周二，2.5h）｜去重：MinHash 近重复检测

精确去重只能去掉完全相同的串，指令数据里大量是「同义改写」，所以用 MinHash + LSH。

```python
# dedup_minhash.py：近重复指令去除（阈值 0.85）
import json
from datasketch import MinHash, MinHashLSH

THRESHOLD = 0.85
NUM_PERM = 128

def minhash(text: str) -> MinHash:
    m = MinHash(num_perm=NUM_PERM)
    for token in set(text):
        m.update(token.encode("utf-8"))
    return m

rows = [json.loads(l) for l in open("data/domain_clean.jsonl", encoding="utf-8") if l.strip()]
lsh = MinHashLSH(threshold=THRESHOLD, num_perm=NUM_PERM)
kept, dropped = [], 0
for i, ex in enumerate(rows):
    m = minhash(ex["instruction"])
    if lsh.query(m):
        dropped += 1
        continue
    lsh.insert(str(i), m)
    kept.append(ex)

with open("data/domain_dedup.jsonl", "w", encoding="utf-8") as f:
    for ex in kept:
        f.write(json.dumps(ex, ensure_ascii=False) + "\n")
print(f"去重前 {len(rows)} → 去重后 {len(kept)}，删除 {dropped}")
```

预期输出：例如 `去重前 8421 → 去重后 6180，删除 2241`。先装依赖：`uv pip install datasketch`。**字符级 shingle 对中文够用；如果发现删太多（>40%），把阈值降到 0.9。**

#### D5（周五，2.5h）｜before/after 对比评测：写一个可复用的评测脚本

这是本周最重要的工程化动作。评测不给分数，微调就没有意义。

```python
# eval_compare.py：基座 vs 微调，用固定测试集做规则化打分
import json
import re
import torch
from peft import PeftModel
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

BASE = "Qwen/Qwen3-8B"
ADAPTER = "outputs/qwen3-8b-domain-w14/final"
TEST = "data/test.jsonl"
N = 100

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16)
tok = AutoTokenizer.from_pretrained(BASE)


def build(adapter: bool):
    m = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb, device_map={"": 0})
    if adapter:
        m = PeftModel.from_pretrained(m, ADAPTER)
    m.eval()
    return m


def keyword_score(answer: str, gold: str) -> float:
    """极简打分：答案命中 gold 中关键实体/数字的比例，范围 0–1。"""
    keys = set(re.findall(r"[0-9]+(?:\.[0-9]+)?|[A-Za-z_]{3,}|[\u4e00-\u9fa5]{2,4}", gold))
    if not keys:
        return 0.0
    hit = sum(1 for k in keys if k in answer)
    return hit / len(keys)


def run(model, tag):
    rows = [json.loads(l) for l in open(TEST, encoding="utf-8") if l.strip()][:N]
    scores, records = [], []
    for ex in rows:
        msgs = [{"role": "user", "content": ex["instruction"]}]
        ids = tok.apply_chat_template(msgs, add_generation_prompt=True,
                                     return_tensors="pt").to("cuda")
        with torch.no_grad():
            out = model.generate(ids, max_new_tokens=160, do_sample=False,
                                 pad_token_id=tok.eos_token_id)
        ans = tok.decode(out[0][ids.shape[1]:], skip_special_tokens=True)
        s = keyword_score(ans, ex["output"])
        scores.append(s)
        records.append({"tag": tag, "q": ex["instruction"], "pred": ans,
                        "gold": ex["output"], "score": s})
    avg = sum(scores) / len(scores)
    print(f"[{tag}] n={len(scores)} 平均关键词命中率={avg:.3f}")
    with open(f"docs/w14_eval_{tag}.jsonl", "w", encoding="utf-8") as f:
        for r in records:
            f.write(json.dumps(r, ensure_ascii=False) + "\n")
    return avg


base_score = run(build(adapter=False), "base")
ft_score = run(build(adapter=True), "finetuned")
print(f"提升 = {ft_score - base_score:+.3f}")
```

预期输出：两行分数和提升值。**口语化的「看起来更专业了」不算结果；这个差值才是写进简历的东西。** 抽 20 条人工复核 keyword_score 是否合理，若不合理的样本超过 1/3，改用 D6 的 LLM Judge。

#### D6（周六，2h）｜加上 LLM Judge 与数据质量报告

```python
# llm_judge.py：用强模型 API 做 1–5 分打分（离线用本地 Qwen3-8B 兜底）
import json
import os
import httpx

JUDGE_PROMPT = """你是严格的中文答案评审。给定问题、参考答案、模型答案，从「事实正确性、完整性、领域术语准确性」三项各打 1-5 分，只输出 JSON：
{"fact": 1-5, "complete": 1-5, "terminology": 1-5, "reason": "一句话"}"""

def judge(question: str, gold: str, pred: str) -> dict:
    payload = {
        "model": "deepseek-chat",
        "messages": [{"role": "user", "content":
                      f"{JUDGE_PROMPT}\n\n问题：{question}\n参考答案：{gold}\n模型答案：{pred}"}],
        "temperature": 0.0,
        "response_format": {"type": "json_object"},
    }
    r = httpx.post("https://api.deepseek.com/chat/completions",
                   headers={"Authorization": f"Bearer {os.environ['DEEPSEEK_API_KEY']}"},
                   json=payload, timeout=60)
    r.raise_for_status()
    return json.loads(r.json()["choices"][0]["message"]["content"])

rows = [json.loads(l) for l in open("docs/w14_eval_finetuned.jsonl", encoding="utf-8")]
totals = {"fact": 0, "complete": 0, "terminology": 0}
for r in rows[:30]:
    s = judge(r["q"], r["gold"], r["pred"])
    for k in totals:
        totals[k] += s[k]
print({k: round(v / 30, 2) for k, v in totals.items()})
```

预期输出：三项平均分，例如 `{'fact': 4.1, 'complete': 3.6, 'terminology': 4.3}`。**规则打分为主、LLM Judge 为辅，两者结论矛盾时以人工抽检为准。**

### 自检题

1. **为什么按 source 分组划分而不是随机划分？** 答案要点：同一份 PDF/同一批模板生成的问答高度同源，随机划分会造成训练集与测试集泄漏，评测分数虚高而线上无效。
2. **LIMA 的结论对 8GB 显存的学生意味着什么？** 答案要点：数据质量优先于数量，5k 条干净数据可能胜过 50k 条噪声数据；这正好缓解了显存不足导致无法大 batch 的劣势。
3. **`DataCollatorForCompletionOnlyLM` 里 `response_template` 写错了会怎样？** 答案要点：匹配不到就所有 token 的 label 都是 -100，loss 变成 `nan` 或恒为 0；必须先打印一条 collate 后的 `labels` 确认非 -100 的位置正好是答案段。
4. **keyword_score 这类规则评测的失效场景？** 答案要点：答案正确但换了同义表述、数字格式不同（`1.5MPa` vs `1.5 MPa`）、gold 里关键词过于通用，都会低估；所以要配合 LLM Judge 与人工抽检。
5. **微调后模型开始胡编领域参数，怎么排查？** 答案要点：先看训练数据里是否有冲突答案（同一问题多个不同数值），冲突数据会让模型学会「随便给一个数」；再检查是否 overfit（eval loss 上升而 train loss 持续下降），对策是减 epoch、加 dropout、加数据多样性。
6. **为什么工业手册领域推荐自建数据？** 答案要点：公开数据集同质化严重、面试官见过；自建数据的清洗与评测过程本身可讲，且能直接和后续 AIOps 项目共享同一批文档。

### 踩坑提醒

:::warn 数据里的全角/半角与不可见字符导致模型学坏
报错/现象：loss 正常下降但生成里混入 `\u200b`、全角空格、PDF 抽出的连字符断行。解法：清洗阶段统一处理 `unicodedata.normalize("NFKC", text)`，再用正则去掉 `[\u200b-\u200f\ufeff]`；PDF 抽取的文本额外合并「行尾为中文且下一行首为中文」的换行。
:::

:::warn eval loss 一直 `nan`
报错原文：`ValueError: The model did not return a loss from the inputs` 或日志里 `eval_loss: nan`。原因通常是 `DataCollatorForCompletionOnlyLM` 没匹配上模板导致整条样本 label 全为 -100，除以 0 得 nan。解法：单独跑一次 collator 检查 `(labels != -100).sum().item() > 0`，并确认 `response_template` 与 tokenizer 的 chat 模板逐字符一致（注意 `\n` 的个数）。
:::

:::warn MinHash 去掉了一半以上的数据
现象：`去重前 8421 → 去重后 3100`。原因是字符级 shingle 在中文里对短句过于敏感，或 `instruction` 本身模板化（例如全是「请回答以下问题：」）。解法：对 `instruction + input` 拼接后去重、阈值提到 0.9、或改用 `jieba` 分词后的词级 shingle，再复核 20 组被判重的样本是否真重复。
:::

:::warn 租云训练前忘记先本地跑通
后果：A100 按小时计费，配置错误白烧 2 小时约 30–100 元。纪律：本地把 `max_steps=20` 的冒烟测试跑通、数据与脚本一起打包上传、训练脚本里加 `EarlyStoppingCallback` 与固定 `max_steps` 上限、开完训练立刻 `shutdown` 实例。**不要在云上调试代码。**
:::

```python
# chunk.py：两套切块策略，产出 chunk 级数据并保留溯源信息
import json
import re
from pathlib import Path

CHUNK = 480          # 字符数，约等于 300–400 个中文 token
OVERLAP = 80


def split_fixed(text: str, size=CHUNK, overlap=OVERLAP):
    out, i = [], 0
    while i < len(text):
        out.append(text[i:i + size])
        i += size - overlap
    return out


def split_structural(text: str, size=CHUNK, overlap=OVERLAP):
    """按标题/编号/空行优先切，再对超长段二次定长切。"""
    parts = re.split(r"\n(?=\s*(?:\d+(?:\.\d+)*[、.．]|第[一二三四五六七八九十]+[章节条]))|\n{2,}", text)
    chunks, buf = [], ""
    for p in parts:
        p = p.strip()
        if not p:
            continue
        if len(buf) + len(p) + 1 <= size:
            buf = f"{buf}\n{p}".strip()
        else:
            if buf:
                chunks.append(buf)
            if len(p) <= size:
                buf = p
            else:
                chunks.extend(split_fixed(p, size, overlap))
                buf = ""
    if buf:
        chunks.append(buf)
    return chunks


rows = [json.loads(l) for l in open("data/parsed/pages.jsonl", encoding="utf-8")]
for name, fn in (("fixed", split_fixed), ("struct", split_structural)):
    out = []
    for r in rows:
        for j, c in enumerate(fn(r["text"])):
            out.append({
                "id": f"{r['doc']}#p{r['page']}#c{j}",
                "doc": r["doc"], "page": r["page"],
                "strategy": name, "text": c, "n_char": len(c),
            })
    Path(f"data/chunks_{name}.jsonl").write_text(
        "\n".join(json.dumps(x, ensure_ascii=False) for x in out), encoding="utf-8")
    lens = sorted(x["n_char"] for x in out)
    print(f"{name}: {len(out)} chunks, P50={lens[len(lens)//2]}, max={lens[-1]}")
```

预期输出：两套策略的 chunk 数与长度分布。**结构感切的 chunk 数更少、P50 更接近目标，通常检索效果更好；W16 会用同一批问题对比两套策略的召回率。**

#### D4（周四，3h）｜混合检索：BM25 + 向量 + RRF 融合

```python
# hybrid_search.py：BM25 与向量召回用 RRF 融合
import json
import jieba
import numpy as np
import chromadb
from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer

EMB_MODEL = "BAAI/bge-m3"
rows = [json.loads(l) for l in open("data/chunks_struct.jsonl", encoding="utf-8")]
docs = [r["text"] for r in rows]
ids = [r["id"] for r in rows]

corpus = [list(jieba.cut(d)) for d in docs]
bm25 = BM25Okapi(corpus, k1=1.5, b=0.75)

model = SentenceTransformer(EMB_MODEL, device="cuda")
client = chromadb.PersistentClient(path="data/chroma")
coll = client.get_collection("manual_struct")


def rrf(rank_lists, k=60):
    """Reciprocal Rank Fusion：多路召回的排名融合，无需归一化分数。"""
    score = {}
    for lst in rank_lists:
        for rank, doc_id in enumerate(lst):
            score[doc_id] = score.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(score.items(), key=lambda x: -x[1])


def search(query: str, topk_dense=20, topk_bm25=20, topk_final=5):
    q_emb = model.encode([query], normalize_embeddings=True)[0]
    res = coll.query(query_embeddings=[q_emb.tolist()], n_results=topk_dense,
                     include=["documents", "metadatas", "distances"])
    dense_ids = res["ids"][0]
    dense_map = {i: (d, m, dist) for i, d, m, dist
                 in zip(res["ids"][0], res["documents"][0], res["metadatas"][0], res["distances"][0])}

    scores = bm25.get_scores(list(jieba.cut(query)))
    bm25_idx = np.argsort(-scores)[:topk_bm25]
    bm25_ids = [ids[i] for i in bm25_idx]

    fused = rrf([dense_ids, bm25_ids])[:topk_final]
    out = []
    for doc_id, s in fused:
        if doc_id in dense_map:
            d, m, dist = dense_map[doc_id]
        else:
            j = ids.index(doc_id)
            d, m, dist = docs[j], {"doc": rows[j]["doc"], "page": rows[j]["page"]}, None
        out.append({"id": doc_id, "score": round(s, 5), "doc": m["doc"],
                    "page": m["page"], "text": d})
    return out


if __name__ == "__main__":
    for r in search("设备报 E05 代码时先检查什么？"):
        print(f"[{r['score']}] {r['doc']} p{r['page']}\n{r['text'][:120]}\n---")
```

预期输出：5 条按融合分数排序的结果，含文档名与页码。**RRF 的好处是不用把 BM25 分数和余弦距离归一化到同一量纲，直接融合排名。**

```python
# rag_answer.py：检索 + 生成，输出带页码引用的答案
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from hybrid_search import search

LLM = "Qwen/Qwen3-8B"
tok = AutoTokenizer.from_pretrained(LLM)
model = AutoModelForCausalLM.from_pretrained(
    LLM, torch_dtype=torch.bfloat16, device_map={"": 0},
    load_in_4bit=True,
).eval()

SYS = ("你是工业设备手册问答助手。只依据【资料】回答，每个结论后用 [文档名 p页码] 标注来源；"
       "资料中没有的信息直接回答「手册未提及」，不要编造。")


def answer(question: str, topk: int = 5):
    hits = search(question, topk_final=topk)
    ctx = "\n\n".join(f"【资料{i+1}】({h['doc']} p{h['page']})\n{h['text']}"
                      for i, h in enumerate(hits))
    msgs = [{"role": "system", "content": SYS},
            {"role": "user", "content": f"【资料】\n{ctx}\n\n【问题】{question}"}]
    ids = tok.apply_chat_template(msgs, add_generation_prompt=True,
                                 return_tensors="pt").to("cuda")
    with torch.no_grad():
        out = model.generate(ids, max_new_tokens=300, do_sample=False,
                             pad_token_id=tok.eos_token_id)
    return tok.decode(out[0][ids.shape[1]:], skip_special_tokens=True), hits


if __name__ == "__main__":
    ans, hits = answer("设备报 E05 代码时先检查什么？")
    print(ans)
    print("\n引用来源:", [f"{h['doc']} p{h['page']}" for h in hits])
```

### 本周核心代码与命令

把混合检索封装成可复用类，W16 的评测脚本会直接 import 它：

```python
# retriever.py：混合检索统一接口（W16 评测与 Rerank 都基于它）
import json
import jieba
import numpy as np
import chromadb
from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer


class HybridRetriever:
    def __init__(self, chunks_path="data/chunks_struct.jsonl",
                 db_path="data/chroma", coll_name="manual_struct",
                 emb_model="BAAI/bge-m3", device="cpu"):
        self.rows = [json.loads(l) for l in open(chunks_path, encoding="utf-8")]
        self.ids = [r["id"] for r in self.rows]
        self.docs = [r["text"] for r in self.rows]
        self.bm25 = BM25Okapi([list(jieba.cut(d)) for d in self.docs], k1=1.5, b=0.75)
        self.model = SentenceTransformer(emb_model, device=device)
        self.coll = chromadb.PersistentClient(path=db_path).get_collection(coll_name)

    def dense(self, query, k=20):
        emb = self.model.encode([query], normalize_embeddings=True)[0]
        res = self.coll.query(query_embeddings=[emb.tolist()], n_results=k,
                              include=["documents", "metadatas"])
        return [{"id": i, "text": d, "meta": m} for i, d, m
                in zip(res["ids"][0], res["documents"][0], res["metadatas"][0])]

    def sparse(self, query, k=20):
        scores = self.bm25.get_scores(list(jieba.cut(query)))
        idx = np.argsort(-scores)[:k]
        return [{"id": self.ids[i], "text": self.docs[i],
                 "meta": {"doc": self.rows[i]["doc"], "page": self.rows[i]["page"]}}
                for i in idx]

    def search(self, query, k=5, kb=20, kd=20, rrf_k=60):
        rank = {}
        for lst in (self.dense(query, kd), self.sparse(query, kb)):
            for r, item in enumerate(lst):
                key = item["id"]
                if key not in rank:
                    rank[key] = {"item": item, "score": 0.0}
                rank[key]["score"] += 1.0 / (rrf_k + r + 1)
        top = sorted(rank.values(), key=lambda x: -x["score"])[:k]
        return [{"id": t["item"]["id"], "text": t["item"]["text"],
                 "meta": t["item"]["meta"], "score": round(t["score"], 5)} for t in top]
```

### 自检题

1. **为什么混合检索要加 BM25？** 答案要点：向量检索对型号、错误码、专有名词这类低频精确词不敏感（它们在嵌入空间里区分度低），BM25 的词面匹配正好补上，两者互补。
2. **RRF 为什么不需要归一化分数？** 答案要点：它只用各路召回的排名位置，`1/(k+rank)` 把所有来源映射到同一尺度，避开了 BM25 无上界与余弦距离量纲不同的问题。
3. **chunk 太小/太大分别有什么后果？** 答案要点：太小导致语义不完整、召回多但答案缺上下文；太大导致一个 chunk 混入多个主题、噪声稀释向量表示且挤占 prompt 长度（seq 512 下 480 字符已占约 300–400 token）。
4. **`get_text` 返回空串说明什么？** 答案要点：该页没有文字层，是扫描图片；必须 OCR 或放弃，硬塞空 chunk 会让向量库里出现无意义条目。
5. **bge 模型查询侧要不要加指令前缀？** 答案要点：`bge-large-zh-v1.5` 等检索模型需要固定中文指令前缀；`bge-m3` 使用多任务训练，通常不加前缀也可，但**入库与查询必须保持一致**。
6. **为什么检索建议放 CPU、生成放 GPU？** 答案要点：8GB 显存同时驻留 4bit 生成模型（约 4.4–5GB）和 bge-m3（约 2GB fp16）会顶到上限；单条查询在 CPU 上只多花 0.2–0.4 秒，而生成是主要耗时。

```python
# rerank.py：召回 30 条 → Cross-Encoder 重排 → 取 Top5
import torch
from sentence_transformers import CrossEncoder
from retriever import HybridRetriever

RERANKER = "BAAI/bge-reranker-v2-m3"

retriever = HybridRetriever(device="cpu")
reranker = CrossEncoder(RERANKER, max_length=512, device="cuda")


def search_rerank(query: str, recall_k: int = 30, top_k: int = 5):
    cands = retriever.search(query, k=recall_k, kb=recall_k, kd=recall_k)
    if not cands:
        return []
    pairs = [(query, c["text"]) for c in cands]
    with torch.no_grad():
        scores = reranker.predict(pairs, batch_size=8)
    for c, s in zip(cands, scores):
        c["rerank_score"] = float(s)
    ranked = sorted(cands, key=lambda x: -x["rerank_score"])[:top_k]
    return ranked


if __name__ == "__main__":
    q = "液压系统压力不足时应检查哪些部件？"
    for c in search_rerank(q):
        print(f"{c['rerank_score']:.4f}  {c['meta']['doc']} p{c['meta']['page']}")
        print("   ", c["text"][:100].replace("\n", " "))
```

```python
# citation.py：把【资料i】替换为真实来源，并校验引用是否可支撑
import re
from typing import List, Dict


def attach_citations(answer: str, hits: List[Dict]) -> Dict:
    used = sorted({int(m) for m in re.findall(r"【资料(\d+)】", answer)})
    cites = []
    for i in used:
        if 1 <= i <= len(hits):
            h = hits[i - 1]
            cites.append({"idx": i, "doc": h["meta"]["doc"], "page": h["meta"]["page"]})
    clean = answer
    for c in cites:
        h = hits[c["idx"] - 1]
        clean = clean.replace(f"【资料{c['idx']}】", f"[{h['meta']['doc']} p{h['meta']['page']}]")
    return {"answer": clean, "citations": cites,
            "n_used": len(used), "n_provided": len(hits),
            "coverage": round(len(used) / max(1, len(hits)), 3)}
```

同时算检索指标（Hit@5 与 MRR），这是判断「是检索不行还是生成不行」的关键：

```python
# retrieval_metrics.py
def hit_at_k(retrieved, gold, k=5):
    got = {(c["doc"], c["page"]) for c in retrieved[:k]}
    want = {(g["doc"], g["page"]) for g in gold}
    return 1.0 if got & want else 0.0


def mrr(retrieved, gold):
    want = {(g["doc"], g["page"]) for g in gold}
    for i, c in enumerate(retrieved, 1):
        if (c["doc"], c["page"]) in want:
            return 1.0 / i
    return 0.0
```

```python
# rerank_cpu.py：不占显存的 Rerank 配置（8GB 友好）
import torch
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3", max_length=512, device="cpu")


def rerank_cpu(query, cands, top_k=5, batch_size=16):
    pairs = [(query, c["text"]) for c in cands]
    with torch.no_grad():
        scores = reranker.predict(pairs, batch_size=batch_size)
    for c, s in zip(cands, scores):
        c["rerank_score"] = float(s)
    return sorted(cands, key=lambda x: -x["rerank_score"])[:top_k]
```

### 自检题

1. **RAGAS 的 `faithfulness` 衡量什么？** 答案要点：答案是检索上下文里可被支撑的论断比例，衡量「有没有编」，不衡量「答得全不全」；它需要 LLM 做论断拆解，所以有成本也有噪声。
2. **`context_recall` 低但 `faithfulness` 高说明什么？** 答案要点：模型老实（不编），但检索没把该有的内容捞回来——问题在检索侧（切块、召回、Rerank），改 prompt 没用。
3. **为什么必须做未优化基线的评测？** 答案要点：没有 before 就没有「提升 X%」这个可写进简历的数字；而且基线能暴露评测脚本自身的 bug（例如 gold_docs 写错导致所有配置都是 0 分）。
4. **Cross-Encoder 为什么不能直接用于召回？** 答案要点：它必须把 query 与每个候选拼在一起过一遍完整模型，复杂度是候选数 × 前向，无法离线建索引；所以只能对召回后的 20–50 条重排。
5. **引用溯源怎么做到「代码可验证」？** 答案要点：让模型只输出 `【资料i】` 编号，页码由代码映射；进一步把答案里的关键论断与被引 chunk 做字符串/子串包含检查，命中率低于阈值就标记为可疑引用。
6. **Rerank 带来延迟上升值不值？** 答案要点：CPU 上 batch 16 重排 30 条约 1–3 秒，换来 `context_recall` 通常 +5 到 +15 个百分点；如果业务要求 <1 秒首字，就把召回数从 30 降到 15、或改用量化后的 reranker。

### 踩坑提醒

:::warn RAGAS 的 API 在 0.1 与 0.2 之间不兼容
报错原文：`ImportError: cannot import name 'LangchainLLMWrapper' from 'ragas.llms'` 或 `TypeError: evaluate() got an unexpected keyword argument 'llm'`。解法：先 `pip show ragas` 看版本；0.2.x 用 `LangchainLLMWrapper` + `metrics` 列表，0.1.x 用 `ragas.llms` 里的 `ChatOpenAI` 包装类。锁版本进 `requirements.txt`，别让它自由升级。
:::

:::warn Reranker 与生成模型抢显存导致 OOM
报错原文：`torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate 512.00 MiB`。原因：4bit Qwen3-8B（约 4.4GB）+ bge-m3 fp16（约 2GB）+ reranker fp16（约 1.5GB）三者同时驻留超过 7GB。解法：**分时使用 GPU**——先做检索与重排，`del model; torch.cuda.empty_cache()` 后再加载生成模型；或让 reranker 固定在 CPU。
:::

:::warn 评测集 gold_docs 页码写错导致指标全 0
现象：所有配置的 `hit@5` 都是 0。原因：PDF 页码是 0-based 还是 1-based 不统一（`fitz` 的 `page.number` 从 0 开始，打印时通常 +1）。解法：入库时统一用 `page.number + 1`，并在 `build_evalset.py` 里断言 gold_docs 的页码能在 `pages.jsonl` 里找到对应记录。
:::

:::warn 查询改写让召回变差
现象：加了改写后 `context_recall` 反而下降。原因：小模型改写引入幻觉词（把「E05」改成了「E5」或凭空加了不存在的部件名）。解法：保留原始查询一定参与融合（融合时给原始查询更高权重），或用 0.6B 只做「同义词扩展」并在 prompt 里禁止增删型号与数字。
:::

```python
from enum import Enum
from typing import List, Optional
from pydantic import BaseModel, Field, field_validator


class Unit(str, Enum):
    celsius = "celsius"
    fahrenheit = "fahrenheit"


class SearchManualArgs(BaseModel):
    query: str = Field(..., min_length=2, max_length=200, description="检索关键词或问题")
    top_k: int = Field(5, ge=1, le=20, description="返回条数")
    doc_filter: Optional[str] = Field(None, description="只检索指定文档名")


class QueryAlarmArgs(BaseModel):
    device_id: str = Field(..., pattern=r"^[A-Z]{2}-\d{4}$", description="设备编号，如 QZ-2000")
    hours: int = Field(24, ge=1, le=720, description="回看小时数")
    level: Optional[str] = Field(None, description="告警级别")

    @field_validator("level")
    @classmethod
    def check_level(cls, v):
        if v is not None and v not in {"info", "warning", "critical"}:
            raise ValueError("level 必须是 info/warning/critical 之一")
        return v


class ConvertUnitArgs(BaseModel):
    value: float
    from_unit: Unit
    to_unit: Unit


TOOL_SCHEMAS = [

        "name": "search_manual",

        "parameters": SearchManualArgs.model_json_schema()}},
    {"type": "function", "function": {
        "name": "query_alarm",
        "description": "查询某台设备最近若干小时的告警记录",
```

#### D3（周三，3h）｜参数校验、并行调用、错误回灌

三个必须处理的现实情况：（a）模型给的 JSON 不符合 schema；（b）一次返回多个 `tool_calls` 要并行执行；（c）工具抛异常时不能中断整个循环，要把错误当结果喂回去让模型自我纠正。

```python
# executor.py：并行执行工具调用 + 结构化错误回灌
import json
from concurrent.futures import ThreadPoolExecutor
from pydantic import ValidationError
from tools_schema import SearchManualArgs, QueryAlarmArgs, ConvertUnitArgs

MODEL_BY_NAME = {
    "search_manual": SearchManualArgs,
    "query_alarm": QueryAlarmArgs,
    "convert_unit": ConvertUnitArgs,
}


def run_one(name: str, raw_args: str) -> dict:
    model = MODEL_BY_NAME.get(name)
    if model is None:
        return {"ok": False, "error": f"未知工具 {name}", "hint": "可用工具: " + ", ".join(MODEL_BY_NAME)}
    try:
        args = model.model_validate_json(raw_args)
    except ValidationError as e:
        return {"ok": False, "error": "参数校验失败",
                "detail": e.errors(include_url=False), "hint": "请按 schema 重新给参数"}
    try:
        return {"ok": True, "data": TOOLS_IMPL[name](**args.model_dump())}
    except Exception as e:
        return {"ok": False, "error": f"{type(e).__name__}: {e}", "hint": "换一种参数或换工具"}


def run_parallel(tool_calls) -> list[dict]:
    with ThreadPoolExecutor(max_workers=4) as pool:
        futures = [pool.submit(run_one, tc.function.name, tc.function.arguments)
                   for tc in tool_calls]
        return [f.result() for f in futures]


def as_tool_messages(tool_calls, results) -> list[dict]:
    out = []
    for tc, res in zip(tool_calls, results):
        out.append({"role": "tool", "tool_call_id": tc.id,
                    "content": json.dumps(res, ensure_ascii=False)[:4000]})
    return out
```

#### D4（周四，3h）｜重试与降级：三层防御

```python
# resilience.py：重试 / 降级 / 兜底三层结构
import json
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
import httpx


class TransientLLMError(Exception):
    pass


@retry(stop=stop_after_attempt(3),
       wait=wait_exponential(multiplier=1, min=1, max=8),
       retry=retry_if_exception_type((TransientLLMError, httpx.TimeoutException)),
       reraise=True)
def call_llm_with_retry(client, **kwargs):
    resp = client.chat.completions.create(**kwargs)
    if not resp.choices:
        raise TransientLLMError("空 choices")
    return resp


def tool_call_with_fallback(user_msg: str, client, tools: list) -> dict:
    """第一层：正常 function calling；第二层：强制 JSON 输出并自行解析；第三层：纯文本答复。"""
    try:
        resp = call_llm_with_retry(client, model="deepseek-chat",
                                  messages=[{"role": "user", "content": user_msg}],
                                  tools=tools, tool_choice="auto", temperature=0.0)
        msg = resp.choices[0].message
        if msg.tool_calls:
            return {"mode": "tool_call", "tool_calls": msg.tool_calls}
        return {"mode": "text", "content": msg.content}
    except Exception as e:
        print("第一层失败:", type(e).__name__, e)

    try:
        resp = call_llm_with_retry(
            client, model="deepseek-chat",
            messages=[{"role": "user", "content":
                       user_msg + "\n只输出 JSON：{\"tool\": \"<名字>\", \"arguments\": {...}}"}],
            response_format={"type": "json_object"}, temperature=0.0)
        parsed = json.loads(resp.choices[0].message.content)
        return {"mode": "json_fallback", "parsed": parsed}
    except Exception as e:
        print("第二层失败:", type(e).__name__, e)

    resp = call_llm_with_retry(client, model="deepseek-chat",
                              messages=[{"role": "user", "content": user_msg}],
                              temperature=0.0)
    return {"mode": "plain", "content": resp.choices[0].message.content}
```

**降级的价值在统计上：`mode` 分布本身就是指标——如果 `json_fallback` 占比超过 10%，说明你的工具 schema 描述写得不够清楚。**

```python
# metrics.py：把每次调用的结果落盘并计算成功率
import json
import time
from pathlib import Path

LOG = Path("logs/tool_calls.jsonl")
LOG.parent.mkdir(exist_ok=True)


def log_call(case_id: str, name: str, args_raw: str, ok: bool, err: str | None,
             latency_ms: float, retries: int = 0, mode: str = "tool_call"):
    rec = {"ts": time.time(), "case_id": case_id, "tool": name, "args": args_raw,
           "ok": ok, "error": err, "latency_ms": round(latency_ms, 1),
           "retries": retries, "mode": mode}
    with LOG.open("a", encoding="utf-8") as f:
        f.write(json.dumps(rec, ensure_ascii=False) + "\n")


def summarize():
    rows = [json.loads(l) for l in LOG.open(encoding="utf-8") if l.strip()]
    by_tool = {}
    for r in rows:
        b = by_tool.setdefault(r["tool"], {"n": 0, "ok": 0, "lat": [], "err": {}})
        b["n"] += 1
        b["ok"] += int(r["ok"])
        b["lat"].append(r["latency_ms"])
        if not r["ok"]:
            key = (r["error"] or "unknown").split(":")[0]
            b["err"][key] = b["err"].get(key, 0) + 1
    total = len(rows)
    ok_all = sum(1 for r in rows if r["ok"])
    print(f"总调用 {total}，成功 {ok_all}，成功率 {ok_all/max(1,total):.1%}")
    for name, b in sorted(by_tool.items(), key=lambda x: -x[1]["n"]):
        lat = sorted(b["lat"])
        print(f"  {name}: n={b['n']} 成功率={b['ok']/b['n']:.1%} "
              f"P50={lat[len(lat)//2]:.0f}ms P95={lat[int(len(lat)*0.95)]:.0f}ms "
              f"错误={b['err']}")
```

### 自检题

1. **`tool_choice` 的 `auto` / `required` / 指定函数三种取值分别什么时候用？** 答案要点：`auto` 让模型决定是否调用；`required` 强制至少调一个（用于确定性流程）；指定函数用于「已经很确定要调哪个」的场景，能省一次往返并提高格式稳定性。
2. **工具参数校验失败后为什么不直接报错给用户？** 答案要点：校验错误对模型是可纠正信息——把 `ValidationError` 的 `detail` 回灌，模型通常能在下一轮给出合法参数；直接报错会让成功率无谓下降。
3. **为什么要用 `ThreadPoolExecutor` 并行执行 tool_calls？** 答案要点：并行调用是模型一次返回多个独立调用，串行执行会把延迟累加；三者互不依赖时并行能把延迟从「之和」降到「最大值」。
4. **`mode` 分布能说明什么？** 答案要点：`json_fallback` 占比高说明 tool schema 描述不清或模型不支持稳定 function calling；`plain` 占比高说明模型认为不需要工具，可能是 prompt 引导不足。
5. **什么异常该重试、什么不该？** 答案要点：超时、429、5xx、空响应该重试（指数退避）；400 参数错误、401 鉴权、schema 不匹配不该重试，重试只是浪费配额。
6. **`additionalProperties` 与 `extra="forbid"` 的区别？** 答案要点：前者写在 JSON Schema 里约束服务端校验行为；后者是 pydantic 本地校验策略。**两边都要设**，否则模型塞进的多余字段会在本地被静默丢弃或直接抛错。

### 踩坑提醒

:::warn 回传 assistant 消息时带上 `None` 字段导致 400
报错原文：`Error code: 400 - {'error': {'message': 'Invalid parameter: messages with role tool must be a response to a preceding message with tool_calls'}}`。解法：把 `msg` 转成 dict 时用 `model_dump(exclude_none=True)`，并确保每个 `tool_call_id` 都有对应的 `role="tool"` 消息，顺序与 `tool_calls` 一致。
:::

:::warn 模型给的参数是字符串而不是数字
现象：`top_k` 被模型填成 `"5"`，pydantic 默认会强制转换所以看不出问题，但一旦接了 `pattern` 校验的字段（如 `device_id`）就会失败。解法：在 schema 的 description 里明确类型，并对这类字段开启 `strict=True` 校验，把类型错误显式暴露出来。
:::

:::warn 工具超时没有中断，进程卡死
原因：`requests`/`httpx` 默认无超时，或数据库查询慢查询。解法：所有对外调用显式传 `timeout=`；本地工具用 `concurrent.futures` 的 `future.result(timeout=...)` 包裹，超时就把 `{"ok": False, "error": "timeout"}` 作为工具结果回灌。
:::

:::warn 用本地 llama.cpp 服务时工具调用不生效
报错/现象：请求带 `tools` 但返回纯文本。原因：没加 `--jinja`，服务端没用模型的 chat 模板；或该 GGUF 版本的模板不含 tool 段。解法：加 `--jinja`；仍不行就退到 W17D4 的「第二层 JSON fallback」路径，让模型输出 JSON 后本地解析——**降级路径必须存在，这在 8GB 本地部署里是常态。**
:::

```python
import asyncio
import json
import sys
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent

from registry import REGISTRY, search_manual  # noqa: F401 触发注册
import registry as reg

server = Server("device-ops")


@server.list_tools()
async def list_tools() -> list[Tool]:
    out = []
    for name, item in reg.REGISTRY.items():
        out.append(Tool(name=name, description=item["description"],
                        inputSchema=item["model"].model_json_schema()))
    return out


@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    item = reg.REGISTRY.get(name)
    if item is None:
        return [TextContent(type="text",
                            text=json.dumps({"ok": False, "error": f"未知工具 {name}"},
                                            ensure_ascii=False))]
    try:
        args = item["model"].model_validate(arguments)
    except Exception as e:
        return [TextContent(type="text",
                            text=json.dumps({"ok": False, "error": "参数校验失败",
                                             "detail": str(e)}, ensure_ascii=False))]
    result = await asyncio.to_thread(item["fn"], **args.model_dump())
    return [TextContent(type="text",
                        text=json.dumps({"ok": True, "data": result}, ensure_ascii=False))]


async def main():
    async with stdio_server() as (read, write):
        await server.run(read, write, server.create_initialization_options())


if __name__ == "__main__":
    print("[mcp] device-ops server starting", file=sys.stderr)  # 日志必须走 stderr
    asyncio.run(main())
```

#### D4（周四，3h）｜LangGraph 状态图：Planner → Executor → Critic

```python
# graph.py：Planner-Executor-Critic 三段式状态图，带检查点
import json
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.graph.message import add_messages


class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    plan: list[str]
    step_idx: int
    tool_results: list[dict]
    critique: str
    retries: int


def planner(state: AgentState) -> dict:
    """把用户问题拆成 1–3 步，优先检索手册，涉及设备状态时查告警。"""
    q = state["messages"][-1].content
    plan = ["search_manual"]
    if any(k in q for k in ("告警", "报警", "最近")):
        plan.append("query_alarm")
    if any(k in q for k in ("温度", "摄氏", "华氏", "换算")):
        plan.append("convert_unit")
    return {"plan": plan, "step_idx": 0, "tool_results": [], "retries": 0}


def executor(state: AgentState) -> dict:
    name = state["plan"][state["step_idx"]]
    args = route_args(name, state["messages"][-1].content)
    res = run_tool_with_retry(name, args)
    return {"tool_results": state["tool_results"] + [{"tool": name, "args": args, "result": res}],
            "step_idx": state["step_idx"] + 1}


def critic(state: AgentState) -> dict:
    enough = all(r["result"].get("ok") for r in state["tool_results"])
    if state["tool_results"] and state["tool_results"][-1]["result"].get("ok"):
        data = state["tool_results"][-1]["result"].get("data")
        enough = bool(data)
    return {"critique": "信息充足" if enough else "信息不足，需要补充检索",
            "retries": state["retries"] + (0 if enough else 1)}


def should_continue(state: AgentState) -> str:
    if state["step_idx"] >= len(state["plan"]):
        return "critic"
    return "executor"


def after_critic(state: AgentState) -> str:
    if state["critique"].startswith("信息充足") or state["retries"] >= 2:
        return "answer"
    return "executor"


graph = StateGraph(AgentState)
graph.add_node("planner", planner)
graph.add_node("executor", executor)
graph.add_node("critic", critic)
graph.set_entry_point("planner")
graph.add_conditional_edges("planner", should_continue, {"executor": "executor", "critic": "critic"})
graph.add_conditional_edges("executor", should_continue, {"executor": "executor", "critic": "critic"})
graph.add_conditional_edges("critic", after_critic, {"answer": END, "executor": "executor"})

with SqliteSaver.from_conn_string("checkpoints/agent.sqlite") as saver:
    app = graph.compile(checkpointer=saver, interrupt_before=[])
```

### 自检题

1. **stdio MCP Server 为什么不能往 stdout 打印日志？** 答案要点：stdio transport 用 stdout 传 JSON-RPC 帧，任何非协议输出都会让客户端解析失败；日志必须写 stderr 或文件。
2. **HTTP transport 的请求头为什么要同时带 `application/json` 和 `text/event-stream`？** 答案要点：streamable HTTP 用 SSE 推流响应，缺少 `text/event-stream` 会返回 406 Not Acceptable。
3. **LangGraph 的 `Annotated[list, add_messages]` 起什么作用？** 答案要点：它是 reducer，决定节点返回的新值如何与旧状态合并——消息用追加而不是覆盖；自定义字段不写 reducer 就是覆盖语义。
4. **检查点解决什么问题？** 答案要点：状态持久化带来断点续跑、`thread_id` 级会话隔离、以及 `interrupt_before` 的人工审批介入。
5. **同一套工具用三种方式暴露，最大的风险是什么？** 答案要点：schema 漂移——Python 侧改了参数而 MCP 侧没同步，导致 Agent 调用失败；用一致性测试把两者的工具名与必填字段做断言。
6. **`asyncio.to_thread` 在这里为什么必要？** 答案要点：检索/数据库调用是阻塞 IO，直接在 async 函数里同步调用会阻塞事件循环，让 MCP Server 无法处理并发请求。

### 踩坑提醒

:::warn stdio server 里用了 `print` 导致客户端连接失败
报错原文：`mcp.shared.exceptions.McpError: Connection closed` 或客户端日志出现 `json.decoder.JSONDecodeError: Expecting value: line 1 column 1`。原因：调试用的 `print("调用了工具")` 混进了 stdout。解法：所有输出改 `print(..., file=sys.stderr)`；用 `python mcp_stdio_server.py > /dev/null` 跑一次验证协议帧没被污染。
:::

:::warn FastMCP 的端口/路径与客户端不一致
现象：`curl` 返回 404。原因：`FastMCP(host, port)` 只决定监听地址，端点路径默认是 `/mcp`，客户端却请求了 `/sse`。解法：先 `curl http://127.0.0.1:8090/mcp` 探端点；不同 SDK 版本的默认路径可能不同，以实际返回为准并写进 README。
:::

:::warn LangGraph 条件边返回了未声明的分支
报错原文：`ValueError: Expected node ... to be one of [...], got 'answer'`。原因：`add_conditional_edges` 的映射字典里没写全返回的所有取值。解法：把每个 `return` 的字符串都列进映射；用 `END` 而不是自定义字符串表示结束点，或显式把 `"answer": END` 写进映射。
:::

:::warn SQLite 检查点文件在多进程并发下报锁错误
报错原文：`sqlite3.OperationalError: database is locked`。解法：SqliteSaver 适合单进程；要并发就换成 Postgres 检查点或让每个进程用独立的 sqlite 文件。**别在生产形态下用 SQLite 存多 worker 的 Agent 状态。**
:::

#### D1（周一，2.5h）｜自研 trace 表：最小可用的可观测层

```python
# trace.py：自研 trace，每条 span 落 sqlite，零外部依赖
import json
import sqlite3
import time
import uuid
from contextlib import contextmanager
from pathlib import Path

DB = Path("logs/trace.sqlite")
DB.parent.mkdir(exist_ok=True)


def init():
    c = sqlite3.connect(DB)
    c.execute("""CREATE TABLE IF NOT EXISTS spans (
        span_id TEXT PRIMARY KEY, trace_id TEXT, parent_id TEXT,
        name TEXT, start_ts REAL, end_ts REAL, status TEXT,
        attrs TEXT, cost_usd REAL, tokens_in INT, tokens_out INT)""")
    c.commit()
    c.close()


@contextmanager
def span(trace_id: str, name: str, parent_id: str | None = None, **attrs):
    init()
    span_id = str(uuid.uuid4())
    t0 = time.time()
    box = {"status": "ok", "cost": 0.0, "tin": 0, "tout": 0}
    try:
        yield box
    except Exception as e:
        box["status"] = f"error:{type(e).__name__}"
        attrs["error"] = str(e)[:500]
        raise
    finally:
        c = sqlite3.connect(DB)
        c.execute("INSERT INTO spans VALUES (?,?,?,?,?,?,?,?,?,?,?)",
                  (span_id, trace_id, parent_id, name, t0, time.time(),
                   box["status"], json.dumps(attrs, ensure_ascii=False),
                   box["cost"], box["tin"], box["tout"]))
        c.commit()
        c.close()
```

预期输出：`logs/trace.sqlite` 创建成功，含 `spans` 表。**成本按 token 计：DeepSeek 类模型按输入/输出 token 分别计价，把 `tokens_in`/`tokens_out` 记下来就能算钱，比记「调了几次」有用得多。**

```python
# instrumented_graph.py：给每个节点与每次工具调用打 span
import uuid
from trace import span
from graph import app, run_tool_with_retry


def run_with_trace(question: str, thread_id: str | None = None) -> dict:
    trace_id = thread_id or str(uuid.uuid4())
    with span(trace_id, "agent_run", question=question) as root:
        from langchain_core.messages import HumanMessage
        cfg = {"configurable": {"thread_id": trace_id}}
        with span(trace_id, "planner", parent_id=None):
            out = app.invoke({"messages": [HumanMessage(content=question)]}, config=cfg)
        root["tout"] = len(out.get("critique", ""))
        for i, r in enumerate(out.get("tool_results", [])):
            with span(trace_id, f"tool:{r['tool']}", args=r.get("args")) as sp:
                sp["status"] = "ok" if r["result"].get("ok") else "error"
        return {"trace_id": trace_id, "plan": out["plan"],
                "critique": out["critique"], "results": out["tool_results"]}
```

**注意 `parent_id` 的正确用法**：根 span 的 id 在 `span()` 内部生成，外部拿不到，所以嵌套时要么改成把 `span_id` 通过 `yield` 返回，要么接受扁平结构。**扁平结构在 30 条用例的规模下完全够用，别为了父子关系把代码写复杂。**

#### D6（周六，2h）｜可靠性收尾：重试上限、幂等、超时

```python
# idempotent.py：幂等执行包装，避免重试导致重复副作用
import hashlib
import json
import sqlite3
from pathlib import Path

DB = Path("logs/idem.sqlite")


def key_of(name: str, args: dict) -> str:
    return hashlib.sha256(f"{name}:{json.dumps(args, sort_keys=True, ensure_ascii=False)}"
                          .encode("utf-8")).hexdigest()[:32]


def run_idempotent(name: str, args: dict, fn):
    DB.parent.mkdir(exist_ok=True)
    c = sqlite3.connect(DB)
    c.execute("CREATE TABLE IF NOT EXISTS done (k TEXT PRIMARY KEY, result TEXT)")
    k = key_of(name, args)
    row = c.execute("SELECT result FROM done WHERE k=?", (k,)).fetchone()
    if row:
        c.close()
        return {"cached": True, "data": json.loads(row[0])}
    data = fn(**args)
    c.execute("INSERT OR REPLACE INTO done VALUES (?,?)",
              (k, json.dumps(data, ensure_ascii=False)))
    c.commit()
    c.close()
    return {"cached": False, "data": data}
```

### 自检题

1. **任务级成功率与工具选择准确率为什么都要报？** 答案要点：前者衡量端到端可用性（用户关心），后者衡量模型理解工具的能力（开发者关心）；任务级低但工具级高说明编排或工具实现有问题，反之说明 prompt 引导有问题。
2. **「循环调用」这类失败怎么从 trace 里识别？** 答案要点：同一 trace 内同一工具+相同参数出现次数 > 阈值，或总步数超过上限；护栏应在运行时就终止并标记，而不是等事后分析。
3. **为什么成本要按 token 记而不是按调用次数？** 答案要点：一次 Agent 运行的输入上下文随对话轮数增长，调用次数相同成本可能差 5 倍；按 token 记才能算出真实的单次成本与预算上限。
4. **幂等键在一次 Agent 运行里什么时候真正起作用？** 答案要点：重试与检查点恢复时——同一个写操作可能被重复触发，幂等键保证副作用只发生一次。
5. **P95 延迟比平均延迟更能说明什么？** 答案要点：Agent 是长尾严重的系统，平均延迟好看但 P95 可能是 8 秒；用户抱怨的永远是 P95，护栏要按 P95 设。
6. **自研 trace 与 Langfuse 怎么选？** 答案要点：自研零依赖、数据在本地、字段完全可控，适合 30–200 条用例的规模；需要团队协作看板、跨服务链路、自动成本换算时再上 Langfuse。

### 踩坑提醒

:::warn trace 表写入在主线程里变成性能瓶颈
现象：加 trace 后单次运行从 3 秒变成 6 秒。原因：每次 `span` 都在主线程新建 sqlite 连接并 commit。解法：`init()` 只在进程启动时调用一次，用队列批量写入（攒 50 条或每 2 秒 flush 一次）；或者把 trace 写入放进独立线程。
:::

:::warn 评测脚本把「工具返回 ok」当成「答案正确」
现象：任务级成功率 95%，但人工看答案很多是错的。原因：检索到了内容（ok=True）不代表答案对。解法：成功率之外必须有「答案关键字命中率」或 LLM Judge 分数；三个指标一起看才不会自欺。
:::

:::warn 无限重试把 API 配额烧光
报错原文：`Error code: 429 - {'error': {'message': 'Rate limit reached'}}`，随后是账户欠费提醒。解法：`stop_after_attempt(3)` 是上限不是起点；对 429 用指数退避 + 抖动，并在 Agent 层加「单次运行总调用次数上限」；本地测试优先走 llama.cpp 的本地模型。
:::

:::warn 检查点恢复后重复执行了写操作
现象：从检查点恢复后，告警确认接口被调用了两次。原因：LangGraph 从上一个检查点重放节点，副作用没有幂等保护。解法：所有写操作加幂等键并在数据库里做 `INSERT OR IGNORE`；非幂等操作（发邮件、下发指令）必须放在 `interrupt_before` 之后由人确认。
:::

#### D2（周二，2.5h）｜静态 PTQ：校准数据 + `quantize_dynamic` 与静态量化对照

```python
# quantize_ptq.py：动态量化与静态量化两条路线
from pathlib import Path
import numpy as np
import onnxruntime as ort
from onnxruntime.quantization import (quantize_dynamic, quantize_static,
                                      QuantType, QuantFormat, CalibrationDataReader,
                                      CalibrationMethod)
from transformers import AutoTokenizer

SRC = "onnx/bert-base-chinese.onnx"
TOK = AutoTokenizer.from_pretrained("bert-base-chinese")
CALIB_TEXTS = [l.strip() for l in open("data/calib_texts.txt", encoding="utf-8") if l.strip()]


class Reader(CalibrationDataReader):
    def __init__(self, texts, max_len=64, limit=200):
        self.items = []
        for t in texts[:limit]:
            enc = TOK(t, padding="max_length", truncation=True, max_length=max_len,
                      return_tensors="np")
            self.items.append({k: v.astype(np.int64) for k, v in enc.items()
                               if k in ("input_ids", "attention_mask", "token_type_ids")})
        self.i = 0

    def get_next(self):
        if self.i >= len(self.items):
            return None
        item = self.items[self.i]
        self.i += 1
        return item

    def rewind(self):
        self.i = 0


quantize_dynamic(SRC, "onnx/bert_dynamic_int8.onnx", weight_type=QuantType.QInt8)
print("动态量化完成:", round(Path("onnx/bert_dynamic_int8.onnx").stat().st_size / 1024**2, 1), "MB")

quantize_static(
    SRC, "onnx/bert_static_int8.onnx", Reader(CALIB_TEXTS),
    quant_format=QuantFormat.QDQ, activation_type=QuantType.QInt8,
    weight_type=QuantType.QInt8, calibrate_method=CalibrationMethod.MinMax,
    per_channel=True,
)
print("静态量化完成:", round(Path("onnx/bert_static_int8.onnx").stat().st_size / 1024**2, 1), "MB")
```

预期输出：两个量化文件大小（通常 100–110MB）。**`calibrate_method` 先用 `MinMax`；如果精度掉太多换 `Percentile`（需传 `CalibrationMethod.Percentile` 与百分位参数）。校准集必须从**训练/验证分布**里取，不能随手拿测试集——那会造成信息泄漏。**

#### D3（周三，3h）｜三档精度的 benchmark：延迟 + 显存 + 精度

```python
# bench_onnx.py：fp32 / int8 动态 / int8 静态 三档对比
import json
import time
import numpy as np
import onnxruntime as ort
from transformers import AutoTokenizer

TOK = AutoTokenizer.from_pretrained("bert-base-chinese")
TEXTS = [l.strip() for l in open("data/bench_texts.txt", encoding="utf-8") if l.strip()][:200]
LABELS = [int(l.strip()) for l in open("data/bench_labels.txt", encoding="utf-8") if l.strip()][:200]
MODELS = {"fp32": "onnx/bert-base-chinese.onnx",
          "int8_dynamic": "onnx/bert_dynamic_int8.onnx",
          "int8_static": "onnx/bert_static_int8.onnx"}


def make_session(path, provider):
    so = ort.SessionOptions()
    so.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
    return ort.InferenceSession(path, so, providers=[provider])


def evaluate(sess, provider_tag):
    inputs = [i.name for i in sess.get_inputs()]
    batched = [TOK(t, padding="max_length", truncation=True, max_length=64,
                   return_tensors="np") for t in TEXTS]
    # 预热
    for b in batched[:10]:
        sess.run(None, {k: v.astype(np.int64) for k, v in b.items() if k in inputs})
    t0 = time.perf_counter()
    preds = []
    for b in batched:
        logits = sess.run(None, {k: v.astype(np.int64) for k, v in b.items() if k in inputs})[0]
        preds.append(int(np.argmax(logits, axis=-1)[0]))
    dt = (time.perf_counter() - t0) / len(batched) * 1000
    acc = sum(p == y for p, y in zip(preds, LABELS)) / len(LABELS)
    return {"provider": provider_tag, "latency_ms_per_sample": round(dt, 2),
            "accuracy": round(acc, 4), "n": len(batched)}


report = {}
for name, path in MODELS.items():
    try:
        s = make_session(path, "CUDAExecutionProvider")
        report[name] = evaluate(s, "CUDA")
    except Exception as e:
        print(name, "CUDA 不可用，回落 CPU:", type(e).__name__)
        s = make_session(path, "CPUExecutionProvider")
        report[name] = evaluate(s, "CPU")
    print(name, report[name])

json.dump(report, open("docs/w20_onnx_bench.json", "w", encoding="utf-8"),
          ensure_ascii=False, indent=2)
```

预期输出：三行对比，形如 `fp32 {'latency_ms_per_sample': 6.8, 'accuracy': 0.931}`、`int8_static {'latency_ms_per_sample': 2.1, 'accuracy': 0.926}`。**典型结果是延迟降 2–4 倍、精度掉 0.5–2 个百分点；如果精度掉超过 3 个百分点，回去查校准集与 `per_channel`。**

```python
# deploy/backends.py：三后端统一接口
from abc import ABC, abstractmethod


class Backend(ABC):
    name: str

    @abstractmethod
    def generate(self, prompt: str, max_new_tokens: int = 128) -> dict:
        ...

    @abstractmethod
    def info(self) -> dict:
        ...


class ONNXBackend(Backend):
    name = "onnx"

    def __init__(self, model_path: str, provider: str = "CUDAExecutionProvider"):
        import onnxruntime as ort
        self.sess = ort.InferenceSession(model_path, providers=[provider])
        self.provider = provider

    def generate(self, prompt: str, max_new_tokens: int = 128) -> dict:
        import time
        t0 = time.perf_counter()
        # 这里放具体的 tokenize / run / decode 逻辑
        outs = self.sess.run(None, self._encode(prompt))
        return {"text": str(outs[0]), "latency_ms": (time.perf_counter() - t0) * 1000}

    def _encode(self, prompt: str):
        raise NotImplementedError("接上你的 tokenizer")

    def info(self) -> dict:
        return {"backend": self.name, "provider": self.provider}


class LlamaCppBackend(Backend):
    name = "llamacpp"

    def __init__(self, base_url: str = "http://127.0.0.1:8080"):
        self.base_url = base_url

    def generate(self, prompt: str, max_new_tokens: int = 128) -> dict:
        import time
        import httpx
        t0 = time.perf_counter()
        r = httpx.post(f"{self.base_url}/v1/chat/completions", timeout=120, json={
            "messages": [{"role": "user", "content": prompt}],
            "max_tokens": max_new_tokens, "temperature": 0.0})
        r.raise_for_status()
        return {"text": r.json()["choices"][0]["message"]["content"],
                "latency_ms": (time.perf_counter() - t0) * 1000}

    def info(self) -> dict:
        import httpx
        return {"backend": self.name, "models": httpx.get(
            f"{self.base_url}/v1/models", timeout=10).json()}
```

### 自检题

1. **动态量化与静态量化的核心差别？** 答案要点：动态量化只量化权重、激活在推理时按需量化（无需校准集，适合 Transformer 的 MatMul）；静态量化需要校准集预先确定激活的 scale，精度通常更好，适合 CNN。
2. **校准集为什么不能用测试集？** 答案要点：确定激活 scale 的过程本身使用了数据分布信息，用测试集会构成信息泄漏，让量化后精度评估虚高。
3. **`per_channel=True` 解决什么问题？** 答案要点：逐通道（卷积/线性层的输出通道）分别定 scale，避免不同通道数值范围差异大时被单一 scale 压坏；代价是模型里多一份 scale 张量。
4. **8GB 显存为什么 Q4_K_M 是 LLM 的默认档位？** 答案要点：8B 模型 Q4_K_M 约 4.4GB，加 4K 上下文的 KV（fp16 约 0.5–1GB）与 CUDA context 落在 6GB 上下，留出余量；Q5_K_M 已接近 5.3GB，长上下文容易顶满。
5. **`--cache-type-k q8_0 --cache-type-v q8_0` 的代价？** 答案要点：KV Cache 显存约减半、长上下文可开更长，但 KV 量化会带来轻微质量损失与少量额外计算，实测通常生成速度降 2–5%。
6. **什么时候不该用 ONNX INT8 量化？** 答案要点：LLM 权重需要 group-wise 量化才有好效果，ONNX 的 INT8 缺少成熟的 group 支持；LLM 走 GGUF/GPTQ/AWQ，ONNX 留给 Transformer 编码器与 CNN。

### 踩坑提醒

:::warn `quantize_static` 报校准数据缺输入
报错原文：`RuntimeError: Calibration data is not enough or input names mismatch: ['token_type_ids']`。原因：`CalibrationDataReader` 返回的 dict 键与 ONNX 图的输入名不完全一致（新版 transformers 不再返回 `token_type_ids`）。解法：以 `sess.get_inputs()` 的名字为准动态过滤，或导出时就去掉该输入。
:::

:::warn ONNX Runtime 用了 CPU 版却以为在跑 GPU
现象：延迟和 CPU 一样，`info()["provider"]` 显示 `CPUExecutionProvider`。原因：装了 `onnxruntime` 而不是 `onnxruntime-gpu`，或 CUDA/cuDNN 版本不匹配。解法：`pip uninstall onnxruntime` 再装 `onnxruntime-gpu`，并用 `ort.get_available_providers()` 确认 `CUDAExecutionProvider` 在列表里。
:::

:::warn GGUF 转换时磁盘被 f16 中间文件撑爆
报错原文：`OSError: [Errno 28] No space left on device`。原因：`convert_hf_to_gguf.py` 输出 f16 GGUF 约 16GB，同时 HF 权重还在本地。解法：先确认 `df -h` 有 ≥35GB 空闲；转换完成后立即 `rm` 掉 f16 中间文件；在 Windows 侧清理 `%TEMP%`。
:::

:::warn `-ngl 99` 之后显存仍然爆掉
报错原文：`ggml_backend_cuda_buffer_type_alloc_buffer: allocating 1024.00 MiB on device 0: cudaMalloc failed: out of memory`。原因：`-c` 设太大（如 32768）导致 KV Cache 超限，或桌面端占用了显存。解法：先 `-c 4096`，加 `--cache-type-k q8_0 --cache-type-v q8_0`，关闭浏览器硬件加速；仍不行就 `-ngl 24`（8B 大概 32 层，卸载 3/4）牺牲速度。
:::

```python
# server.py：统一推理服务，含健康检查与非流式端点
import os
import time
from typing import Literal, Optional
import httpx
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="Edge Inference Platform", version="0.1.0")
LLAMA_BASE = os.environ.get("LLAMA_BASE", "http://127.0.0.1:8080")
START_TS = time.time()


class ChatRequest(BaseModel):
    prompt: str = Field(..., min_length=1, max_length=8000)
    max_new_tokens: int = Field(256, ge=1, le=2048)
    temperature: float = Field(0.0, ge=0.0, le=2.0)
    backend: Literal["llamacpp", "onnx"] = "llamacpp"


class ChatResponse(BaseModel):
    text: str
    latency_ms: float
    backend: str
    tokens_out: Optional[int] = None


@app.get("/healthz")
def healthz():
    ok = True
    try:
        r = httpx.get(f"{LLAMA_BASE}/v1/models", timeout=3)
        ok = r.status_code == 200
    except Exception:
        ok = False
    return {"status": "ok" if ok else "degraded", "uptime_s": round(time.time() - START_TS, 1),
            "backend_ready": ok}


@app.post("/v1/chat", response_model=ChatResponse)
def chat(req: ChatRequest):
    if req.backend != "llamacpp":
        raise HTTPException(status_code=501, detail="ONNX 后端仅支持分类任务")
    t0 = time.perf_counter()
    try:
        r = httpx.post(f"{LLAMA_BASE}/v1/chat/completions", timeout=180, json={
            "messages": [{"role": "user", "content": req.prompt}],
            "max_tokens": req.max_new_tokens, "temperature": req.temperature})
        r.raise_for_status()
    except httpx.HTTPError as e:
        raise HTTPException(status_code=502, detail=f"后端错误: {type(e).__name__}") from e
    data = r.json()
    return ChatResponse(text=data["choices"][0]["message"]["content"],
                        latency_ms=round((time.perf_counter() - t0) * 1000, 1),
                        backend=req.backend,
                        tokens_out=data.get("usage", {}).get("completion_tokens"))
```

```python
# sse.py：真正的流式输出，首 token 延迟可测
import json
import time
import httpx
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()
LLAMA_BASE = "http://127.0.0.1:8080"


async def token_stream(prompt: str, max_new_tokens: int = 256):
    payload = {"messages": [{"role": "user", "content": prompt}],
               "max_tokens": max_new_tokens, "stream": True, "temperature": 0.0}
    t0 = time.perf_counter()
    first = None
    async with httpx.AsyncClient(timeout=180) as client:
        async with client.stream("POST", f"{LLAMA_BASE}/v1/chat/completions",
                                 json=payload) as resp:
            async for line in resp.aiter_lines():
                if not line.startswith("data: "):
                    continue
                body = line[6:].strip()
                if body == "[DONE]":
                    break
                try:
                    delta = json.loads(body)["choices"][0]["delta"].get("content", "")
                except (json.JSONDecodeError, KeyError, IndexError):
                    continue
                if not delta:
                    continue
                if first is None:
                    first = (time.perf_counter() - t0) * 1000
                    yield f"event: meta\ndata: {json.dumps({'ttft_ms': round(first, 1)})}\n\n"
                yield f"data: {json.dumps({'token': delta}, ensure_ascii=False)}\n\n"
    total = (time.perf_counter() - t0) * 1000
    yield f"event: done\ndata: {json.dumps({'total_ms': round(total, 1), 'ttft_ms': round(first or 0, 1)})}\n\n"


@app.get("/v1/stream")
async def stream(prompt: str, max_new_tokens: int = 256):
    return StreamingResponse(token_stream(prompt, max_new_tokens),
                             media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache",
                                      "X-Accel-Buffering": "no"})
```

#### D3（周三，3h）｜并发压测：阶梯加压 + 指标落盘

```python
# load_test.py：用 httpx + asyncio 做阶梯并发压测（不依赖 locust，便于 CI）
import asyncio
import json
import statistics
import time
import httpx

URL = "http://127.0.0.1:8000/v1/chat"
PROMPT = "用三句话解释模型量化的原理"


async def one(client, sem, results):
    async with sem:
        t0 = time.perf_counter()
        try:
            r = await client.post(URL, json={"prompt": PROMPT, "max_new_tokens": 64},
                                  timeout=180)
            ok = r.status_code == 200
            tok = r.json().get("tokens_out") or 0
        except Exception as e:
            ok, tok = False, 0
        results.append({"ok": ok, "latency_s": time.perf_counter() - t0, "tokens": tok})


async def stage(concurrency: int, total: int = 40):
    results = []
    sem = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient() as client:
        await asyncio.gather(*[one(client, sem, results) for _ in range(total)])
    lat = sorted(r["latency_s"] for r in results)
    ok = sum(r["ok"] for r in results)
    toks = sum(r["tokens"] for r in results)
    wall = max(lat)
    return {"concurrency": concurrency, "total": total,
            "success_rate": round(ok / total, 3),
            "p50_s": round(lat[len(lat)//2], 2),
            "p95_s": round(lat[int(len(lat)*0.95)], 2),
            "throughput_tok_s": round(toks / wall, 1) if wall else 0}


async def main():
    out = []
    for c in (1, 2, 4, 8):
        res = await stage(c)
        print(res)
        out.append(res)
    json.dump(out, open("docs/w21_loadtest.json", "w", encoding="utf-8"),
              ensure_ascii=False, indent=2)


if __name__ == "__main__":
    asyncio.run(main())
```

预期输出：四行阶梯结果。**8GB 单卡的真实形态是：并发 1→2 吞吐略升，2→4 起 P95 明显恶化（显存不足以并行 batch），并发 8 时成功率可能掉到 80% 以下。把这个「并发天花板」写成结论——面试官会问。**

### 自检题

1. **SSE 的分帧规则是什么？** 答案要点：每个字段一行（`data: ...`），事件之间用空行分隔；`event:` 可自定义事件名，客户端按 `\n\n` 切分解析。
2. **首 token 延迟和总延迟分别受什么影响？** 答案要点：首 token 受预填充（prompt 长度、`-b`/`-ub` 批大小）影响；总延迟还受生成 token 数与 tok/s 影响——所以压测要分别记录。
3. **为什么 uvicorn 只起 1 个 worker？** 答案要点：单卡显存有限，多 worker 各自加载模型会 OOM，即使共享后端也会让 GPU 排队导致延迟抖动；吞吐要靠批处理而不是进程数。
4. **并发升高时 P95 为什么先恶化？** 答案要点：请求在 GPU 上排队串行执行，等待时间随队列长度增长，而单次执行时间不变，所以尾延迟快速上升。
5. **量化报告里「测试条件」为什么必须有？** 答案要点：延迟高度依赖功耗模式、上下文长度、批大小与是否预热；不同条件下的数字不可比，写清条件别人才能复现。
6. **健康检查为什么不能只返回 200？** 答案要点：进程活着不代表后端可用；`/healthz` 要实际探一次模型服务，把它作为 `degraded` 状态返回，配合负载均衡摘流。

### 踩坑提醒

:::warn SSE 被缓冲，前端一次收到全部内容
现象：`curl -N` 也是最后一次性吐出来。原因：中间有反向代理（Nginx）开了 `proxy_buffering`，或用了 GZip 中间件。解法：响应头加 `X-Accel-Buffering: no`，Nginx 侧 `proxy_buffering off;`，并确认没有 `GZipMiddleware` 包住流式响应。
:::

:::warn 压测把显存打爆导致服务静默重启
报错原文：`ggml_backend_cuda_buffer_type_alloc_buffer: ... out of memory`，随后 `uvicorn` 日志出现 `Worker exiting`。原因：并发 8 时每个请求都在申请 KV Cache 空间。解法：在服务层加信号量把并发请求数限制到实测的安全值（例如 4）；返回 429 而不是让后端 OOM；`/healthz` 暴露 `inflight` 计数。
:::

:::warn Docker 里 GPU 不可见
报错原文：`docker: Error response from daemon: could not select device driver "" with capabilities: [[gpu]]`。解法：安装 `nvidia-container-toolkit` 并 `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`；用 `docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi` 先验证基础镜像能看到 GPU。**WSL2 下的 Docker Desktop 需要在设置里开启 GPU 支持。**
:::

:::warn 压测数字看起来太好，因为没算排队时间
现象：并发 8 的 P50 比并发 1 还低。原因：`asyncio.gather` 的起跑不同步，或部分请求未等待完成就统计了 wall time。解法：用 `asyncio.Barrier` 同步起跑，wall time 用「最后完成的请求时间 - 统一起始时间」，并丢弃前 20% 作为预热。
:::

```python
# baseline_stat.py：两个统计基线，给出点级与事件级两套指标
import numpy as np
import pandas as pd


def zscore_detect(x: np.ndarray, win: int = 100, k: float = 3.0) -> np.ndarray:
    s = pd.Series(x)
    mu = s.rolling(win, min_periods=win // 2).mean()
    sd = s.rolling(win, min_periods=win // 2).std()
    z = (s - mu) / (sd + 1e-8)
    return (z.abs() > k).to_numpy()


def ewma_detect(x: np.ndarray, alpha: float = 0.05, k: float = 3.0) -> np.ndarray:
    s = pd.Series(x)
    mu = s.ewm(alpha=alpha).mean()
    sd = s.ewm(alpha=alpha).std()
    z = (s - mu) / (sd + 1e-8)
    return (z.abs() > k).to_numpy()


def point_metrics(pred: np.ndarray, label: np.ndarray) -> dict:
    tp = int(((pred == 1) & (label == 1)).sum())
    fp = int(((pred == 1) & (label == 0)).sum())
    fn = int(((pred == 0) & (label == 1)).sum())
    prec = tp / max(1, tp + fp)
    rec = tp / max(1, tp + fn)
    f1 = 2 * prec * rec / max(1e-9, prec + rec)
    return {"tp": tp, "fp": fp, "fn": fn,
            "precision": round(prec, 4), "recall": round(rec, 4), "f1": round(f1, 4)}


def segments(flag: np.ndarray) -> list[tuple[int, int]]:
    """把 0/1 序列转成 (start, end) 区间列表，用于事件级评估。"""
    d = np.diff(np.r_[0, flag, 0])
    starts = np.where(d == 1)[0]
    ends = np.where(d == -1)[0]
    return list(zip(starts.tolist(), ends.tolist()))
```

预期输出：两个基线的 `f1` 与 FP 数量。**统计基线在 SMD 上的点级 F1 通常在 0.3–0.6，看起来很差，但它跑得最快（毫秒级）、可解释（每个报警能说清是哪个维度超了几倍标准差），这是它的价值。**

```python
# detect_iforest_ae.py：Isolation Forest 与 AE 两类模型
import numpy as np
import torch
import torch.nn as nn
from sklearn.ensemble import IsolationForest
from sklearn.preprocessing import StandardScaler


def iforest_detect(train_x: np.ndarray, x: np.ndarray, contamination=0.01,
                   n_estimators=200, seed=42) -> np.ndarray:
    scaler = StandardScaler().fit(train_x)
    clf = IsolationForest(contamination=contamination, n_estimators=n_estimators,
                          random_state=seed, n_jobs=-1)
    clf.fit(scaler.transform(train_x))
    return (clf.predict(scaler.transform(x)) == -1).astype(int)


class AE(nn.Module):
    def __init__(self, d_in: int, hidden=(32, 16)):
        super().__init__()
        self.enc = nn.Sequential(nn.Linear(d_in, hidden[0]), nn.ReLU(),
                                 nn.Linear(hidden[0], hidden[1]), nn.ReLU())
        self.dec = nn.Sequential(nn.Linear(hidden[1], hidden[0]), nn.ReLU(),
                                 nn.Linear(hidden[0], d_in))

    def forward(self, x):
        return self.dec(self.enc(x))


def train_ae(train_x: np.ndarray, epochs: int = 30, lr: float = 1e-3,
             seed: int = 42) -> tuple[AE, StandardScaler]:
    torch.manual_seed(seed)
    scaler = StandardScaler().fit(train_x)
    x = torch.tensor(scaler.transform(train_x), dtype=torch.float32)
    model = AE(x.shape[1])
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    lossf = nn.MSELoss()
    for ep in range(epochs):
        model.train()
        perm = torch.randperm(len(x))
        tot = 0.0
        for i in range(0, len(x), 256):
            b = x[perm[i:i + 256]]
            opt.zero_grad()
            loss = lossf(model(b), b)
            loss.backward()
            opt.step()
            tot += loss.item() * len(b)
        if ep % 10 == 0:
            print(f"epoch {ep} loss {tot/len(x):.5f}")
    return model, scaler


@torch.no_grad()
def ae_scores(model: AE, scaler, x: np.ndarray) -> np.ndarray:
    """逐点重构误差作为异常分数（后续按分位数或 3-sigma 定阈值）。"""
    model.eval()
    xt = torch.tensor(scaler.transform(x), dtype=torch.float32)
    err = ((model(xt) - xt) ** 2).mean(dim=1).numpy()
    return err
```

预期输出：AE 的 loss 逐 10 epoch 下降（0.9 → 0.05 量级），`ae_scores` 返回长度等于 `len(x)` 的分数序列。

#### D4（周四，3h）｜LSTM-AE + 阈值选择 + 四模型对比

```python
# lstm_ae.py：窗口化 LSTM-AE，输出窗口级异常分数
import numpy as np
import torch
import torch.nn as nn


def make_windows(x: np.ndarray, win: int = 64, stride: int = 8):
    idx = np.arange(0, len(x) - win + 1, stride)
    return np.stack([x[i:i + win] for i in idx]), idx


class LSTMAE(nn.Module):
    def __init__(self, d_in: int, hidden: int = 32, latent: int = 16):
        super().__init__()
        self.enc = nn.LSTM(d_in, hidden, batch_first=True)
        self.to_latent = nn.Linear(hidden, latent)
        self.from_latent = nn.Linear(latent, hidden)
        self.dec = nn.LSTM(hidden, hidden, batch_first=True)
        self.out = nn.Linear(hidden, d_in)

    def forward(self, x):
        h, _ = self.enc(x)
        z = self.to_latent(h[:, -1])
        h2 = self.from_latent(z).unsqueeze(1).repeat(1, x.size(1), 1)
        d, _ = self.dec(h2)
        return self.out(d)


def score_windows(model: LSTMAE, windows: np.ndarray) -> np.ndarray:
    model.eval()
    with torch.no_grad():
        xt = torch.tensor(windows, dtype=torch.float32)
        rec = model(xt).numpy()
    return ((rec - windows) ** 2).mean(axis=(1, 2))


def pick_threshold(scores: np.ndarray, q: float = 0.995) -> float:
    """用训练集（正常数据）分数的分位数定阈值，避免用测试集调阈值造成泄漏。"""
    return float(np.quantile(scores, q))
```

四模型对比表必须包含：点级 P/R/F1、**事件级 F1（按段算，段内任意点命中即算召回）**、平均推理耗时（毫秒/千点）、阈值来源、以及是否可解释。

事件级评估的实现要点：

```python
# event_metrics.py：事件级评估——先合并成段，再算命中
import numpy as np
from baseline_stat import segments


def event_metrics(pred: np.ndarray, label: np.ndarray, delay_tolerance: int = 60) -> dict:
    """真实异常段若在 [start, start+delay_tolerance] 内被预测命中，算召回一次。
    预测段若与任何真实段无交集，算一次误报。"""
    true_segs = segments(label)
    pred_segs = segments(pred)
    hit, missed = 0, 0
    for ts, te in true_segs:
        ok = any(ps <= te + delay_tolerance and pe >= ts for ps, pe in pred_segs)
        hit += int(ok)
        missed += int(not ok)
    false_alarms = 0
    for ps, pe in pred_segs:
        if not any(ps <= te and pe >= ts for ts, te in true_segs):
            false_alarms += 1
    recall = hit / max(1, len(true_segs))
    precision = hit / max(1, hit + false_alarms)
    f1 = 2 * precision * recall / max(1e-9, precision + recall)
    return {"true_events": len(true_segs), "pred_events": len(pred_segs),
            "hit": hit, "missed": missed, "false_alarms": false_alarms,
            "event_precision": round(precision, 4),
            "event_recall": round(recall, 4), "event_f1": round(f1, 4)}
```

预期输出：四个模型的对比字典。**典型结论：Isolation Forest 事件级 F1 最高但推理最慢（每千点几十到几百毫秒）；z-score 事件召回最低但 FP 可控；AE/LSTM-AE 居中且容易过拟合正常数据。**

#### D5（周五，2.5h）｜多模型融合 + 告警压缩收敛

```python
# ensemble_alarm.py：多模型投票 + 告警压缩（去重、抑制、聚合）
import json
import time
from collections import defaultdict
from typing import Iterable


def fuse(votes: Iterable[np.ndarray], k: int = 2) -> np.ndarray:
    """至少 k 个模型同时报警才算异常：降 FP 的主要手段。"""
    v = np.vstack([np.asarray(x, dtype=int) for x in votes])
    return (v.sum(axis=0) >= k).astype(int)


def compress(alarms: list[dict], window_s: int = 300,
             group_keys=("device_id", "metric", "level")) -> list[dict]:
    """把 window_s 内同 (device, metric, level) 的告警合并成一条，附 count 与时间范围。"""
    buckets = defaultdict(list)
    for a in alarms:
        key = tuple(a[k] for k in group_keys)
        buckets[key].append(a)
    out = []
    for key, items in buckets.items():
        items.sort(key=lambda x: x["ts"])
        cur = [items[0]]
        for a in items[1:]:
            if a["ts"] - cur[-1]["ts"] <= window_s:
                cur.append(a)
            else:
                out.append(_merge(key, cur))
                cur = [a]
        out.append(_merge(key, cur))
    # 抑制：同 device+metric 下，critical 覆盖 warning
    out.sort(key=lambda x: (x["device_id"], x["metric"], -{"critical": 2, "warning": 1, "info": 0}[x["level"]]))
    filtered, seen = [], set()
    for a in out:
        skey = (a["device_id"], a["metric"])
        if a["level"] != "critical" and skey in seen:
            continue
        if a["level"] == "critical":
            seen.add(skey)
        filtered.append(a)
    return filtered


def _merge(key, items):
    device_id, metric, level = key
    return {"device_id": device_id, "metric": metric, "level": level,
            "start_ts": items[0]["ts"], "end_ts": items[-1]["ts"],
            "count": len(items), "sample_value": items[0].get("value")}


if __name__ == "__main__":
    raw = json.load(open("data/raw_alarms.json", encoding="utf-8"))
    kept = compress(raw, window_s=300)
    print(f"原始告警 {len(raw)} 条 → 压缩后 {len(kept)} 条，压缩率 "
          f"{1 - len(kept)/max(1,len(raw)):.1%}")
```

预期输出：例如 `原始告警 4820 条 → 压缩后 137 条，压缩率 97.2%`。**压缩收敛率是 AIOps 岗位最看重的指标之一（告警风暴是运维的真实痛点），把它和图一起放进 README。**

#### D6（周六，2h）｜把评估口径写清楚（本周最重要的文档）

`docs/w22_eval_protocol.md` 必须包含四节：

1. **点级 vs 事件级**：为什么点调整 F1（一个真实异常段里只要有一个点被命中就把整段算对）会严重高估——极端情况下随机报警也能拿高分。
2. **阈值来源**：必须只用训练集（正常数据）定阈值，任何用测试集调阈值的行为都是泄漏。
3. **延迟容忍**：`delay_tolerance` 取多少要说明理由（例如采样间隔 1 分钟时取 60 个点 = 1 小时）。
4. **误报代价**：一条误报 = 一次人工排查约 10 分钟，用它把 FP 换算成「人力成本」，这比 F1 更能说服人。

:::danger 不要报点调整 F1 作为主指标
点调整 F1（point-adjusted F1）在异常检测文献里被广泛滥用：它把「一个段里命中一个点」当成整段命中，会让随机报警器也拿到 0.9+ 的分数。**主指标用事件级 F1 + 误报数，点级指标只作为辅助。**面试时如果被问到评估口径，这就是你的加分点。
:::

### 自检题

1. **点调整 F1 为什么会高估？** 答案要点：它把真实异常段内任一命中视为整段命中，等于给了一个「延迟无限、只需命中一点」的宽松口径；随机报警也能刷到高分，所以不能当主指标。
2. **阈值为什么必须只用训练集定？** 答案要点：用测试集定阈值等于用答案调参，指标失去意义；正确做法是用正常训练数据的分数分位数（如 0.995）或 3-sigma。
3. **Isolation Forest 的 `contamination` 设大了会怎样？** 答案要点：它决定判定为异常的比例，设大直接导致 FP 暴增；因为异常率通常 < 1%，取 0.005–0.02 起步，再用验证集微调。
4. **多模型投票（k=2）为什么能降 FP？** 答案要点：不同模型的误报位置不重合，要求同时报警能过滤掉各自的偶发噪声；代价是漏报上升，所以 k 要按「误报与漏报哪个更贵」来定。
5. **告警压缩的三种手段分别是什么？** 答案要点：去重（相同告警合并）、聚合/分组（时间窗内同维度合并成一条带 count）、抑制（高等级覆盖低等级），对应 Alertmanager 的 grouping 与 inhibition。
6. **LSTM-AE 的窗口分数怎么映射回点级标签？** 答案要点：每个窗口对应一段区间，把窗口分数广播到区间内的点再取 max 或 mean；步长 stride 越小越平滑但计算量越大，注意边界点的处理。

### 踩坑提醒

:::warn 用测试集调阈值导致指标虚高
现象：事件级 F1 从 0.4 调到 0.85，但线上全是误报。原因：在测试集上扫阈值选最优。解法：阈值只在训练集（正常数据）上按分位数确定，测试集只用于最终评估一次；需要调就在训练集里切出验证段。
:::

:::warn LSTM-AE 把正常数据背得太熟，重构误差不区分异常
现象：正常与异常点的重构误差分布几乎重合。原因：模型容量过大 + 训练过久，学到了恒等映射。解法：缩小 hidden/latent 维度、加 dropout、减少 epoch、用带噪声的输入做去噪自编码；并检查训练集里是否混入了异常点（SMD 的 train 是纯正常数据，自己采的数据要人工确认）。
:::

:::warn 时序标准化用了全量数据造成泄漏
现象：指标好得不真实。原因：`StandardScaler().fit(全量数据)` 把测试集的均值方差带进了训练。解法：只在训练段上 fit，然后 transform 测试段；跨机器（SMD 有 28 台）时每台单独标准化。
:::

:::warn 告警压缩把关键告警也抑制掉了
后果：真实故障被 warning 的抑制规则吃掉，漏报。解法：抑制规则里**只允许高等级抑制低等级，且必须限定同一 device+metric 与时间窗**；对 `critical` 级别永不抑制；上线前用历史故障回放验证「所有真实故障都有至少一条告警被保留」。
:::

```python
miner = TemplateMiner(persistence, cfg)

# 关键：先把变量掩码掉，否则 IP/数字/路径会生成海量模板
MASKS = [
    (re.compile(r"\b\d{1,3}(?:\.\d{1,3}){3}\b"), "<IP>"),
    (re.compile(r"\b[0-9a-f]{8,}\b"), "<HEX>"),
    (re.compile(r"\b\d+\b"), "<NUM>"),
    (re.compile(r"/[\w./-]+"), "<PATH>"),
]

stats = Counter()
n = 0
with LOG.open("r", encoding="utf-8", errors="ignore") as f:
    for line in f:
        n += 1
        line = line.strip()
        if not line:
            continue
        for pat, rep in MASKS:
            line = pat.sub(rep, line)
        res = miner.add_log_message(line)
        stats[res["template_mined"]] += 1

print(f"处理 {n} 行，得到 {len(stats)} 个模板")
top = stats.most_common(15)
total = sum(stats.values())
for t, c in top:
    print(f"{c:>7} ({c/total:6.2%})  {t[:110]}")

OUT.write_text(json.dumps(
    {"total_lines": n, "n_templates": len(stats),
     "templates": [{"template": t, "count": c} for t, c in stats.most_common()]},
    ensure_ascii=False, indent=2), encoding="utf-8")
```

预期输出：例如 `处理 11200000 行，得到 320 个模板`，以及 Top15 模板与占比。**如果模板数超过 2000，说明掩码不够，继续加正则（时间戳、线程号、请求 ID）；如果少于 50，说明 `sim_th` 太大或日志本身太单一。**

#### D2（周二，2.5h）｜模板质量评估：PA 与 GA

```python
# template_quality.py：模板准确率（PA）与分组准确率（GA）
import json
import re
from collections import defaultdict
from pathlib import Path

# 需要人工标注 100 行：每条日志属于哪个真实模板（ground truth group）
gt = [json.loads(l) for l in open("data/logs/gt_100.jsonl", encoding="utf-8")]
pred_map = json.loads(Path("data/logs/templates.json").read_text(encoding="utf-8"))
by_template = defaultdict(list)
for item in pred_map["templates"]:
    by_template[item["template"]] = item

def template_accuracy(gt_rows) -> float:
    """PA：同一条模板里的日志，其真实模板集合是否唯一。"""
    groups = defaultdict(set)
    for r in gt_rows:
        groups[r["pred_template"]].add(r["true_template"])
    correct = sum(1 for v in groups.values() if len(v) == 1)
    return correct / max(1, len(groups))

def group_accuracy(gt_rows) -> float:
    """GA：同一个真实模板的日志，是否被分到同一条预测模板。"""
    groups = defaultdict(set)
    for r in gt_rows:
        groups[r["true_template"]].add(r["pred_template"])
    correct = sum(1 for v in groups.values() if len(v) == 1)
    return correct / max(1, len(groups))

print(f"PA = {template_accuracy(gt):.3f}   GA = {group_accuracy(gt):.3f}")
```

预期输出：两个 0–1 的分数。**Drain 类算法在人工选好掩码后 PA 通常能到 0.85–0.95；如果 PA 高但 GA 低，说明过合并（把不同模板压成一条），需要提高 `sim_th`。**

```python
import json
import os
from collections import Counter
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"], base_url="https://api.deepseek.com")

SYS = """你是资深 SRE。根据给出的告警、日志模板统计、时序异常分数，输出**严格 JSON**：
{
  "summary": "3 句话以内的中文摘要，说清现象、影响范围、最可能的根因",
  "severity": "critical|warning|info",
  "root_cause_candidates": [
    {"rank": 1, "cause": "候选根因", "evidence": ["证据1", "证据2"], "confidence": 0.0-1.0}
  ],
  "suggested_actions": ["先做什么", "再做什么"],
  "needs_human": true
}
证据必须来自输入数据，不要编造不存在的指标或日志。"""


def build_payload(alarms: list[dict], templates: list[dict], ts_scores: dict) -> str:
    return json.dumps({
        "alarms": alarms[:40],
        "top_templates_in_anomaly_window": templates[:20],
        "timeseries_anomaly": ts_scores,
    }, ensure_ascii=False)[:12000]


def summarize(payload_text: str) -> dict:
    resp = client.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "system", "content": SYS},
                  {"role": "user", "content": payload_text}],
        temperature=0.0,
        response_format={"type": "json_object"},
    )
    return json.loads(resp.choices[0].message.content)
```

#### D5（周五，2.5h）｜根因候选排序（规则 + LLM 分数融合）

```python
# root_cause_rank.py：规则打分与 LLM 置信度加权融合
import json
from collections import Counter

WEIGHTS = {"freq_ratio": 0.35, "first_seen_early": 0.25, "llm_confidence": 0.4}


def rule_score(template_stat: dict, anomaly_start_idx: int, all_stats: list[dict]) -> dict:
    ratios = [s["ratio"] for s in all_stats] or [1.0]
    max_ratio = max(ratios)
    freq_ratio = min(1.0, template_stat["ratio"] / max_ratio) if max_ratio else 0.0
    # 越早出现在异常窗口里的模板，越可能是触发源
    first_seen_early = 1.0 - min(1.0, template_stat["first_offset"] / 30.0)
    return {"freq_ratio": round(freq_ratio, 4), "first_seen_early": round(first_seen_early, 4)}


def fuse_rank(candidates: list[dict]) -> list[dict]:
    out = []
    for c in candidates:
        r = c.get("rule", {})
        llm = float(c.get("llm_confidence", 0.5))
        score = (WEIGHTS["freq_ratio"] * r.get("freq_ratio", 0)
                 + WEIGHTS["first_seen_early"] * r.get("first_seen_early", 0)
                 + WEIGHTS["llm_confidence"] * llm)
        out.append({**c, "final_score": round(score, 4)})
    out.sort(key=lambda x: -x["final_score"])
    for i, c in enumerate(out, 1):
        c["rank"] = i
    return out
```

评估根因排序的方式：对 10–20 个有明确答案的历史故障，看正确根因是否落在 Top3 里，报「Top3 命中率」。**这个指标比「摘要看起来不错」有说服力得多。**

```python
import json

from collections import Counter
```

```python
from drain3.template_miner_config import TemplateMinerConfig
from drain3.file_persistence import FilePersistence

MASKS = [(re.compile(r"\b\d{1,3}(?:\.\d{1,3}){3}\b"), "<IP>"),
```

### 自检题

1. **Drain3 的 `sim_th` 调大调小分别有什么后果？** 答案要点：调大→更难合并→模板更多更细（GA 高、PA 可能降）；调小→更容易合并→模板少但可能过合并（PA 高、GA 降）。
2. **日志掩码为什么必须在挖掘前做？** 答案要点：IP、数字、路径、十六进制 ID 每个取值都会生成新模板，不掩码会得到几万条无用模板，掩码后通常能压到几百条。
3. **PA 与 GA 分别衡量什么错误？** 答案要点：PA 衡量「过合并」（不同真实模板被合成一条），GA 衡量「过分裂」（同一真实模板被拆成多条）；两者要一起看。
4. **为什么根因候选排序要融合规则分数？** 答案要点：LLM 的置信度是主观且不稳定的；「异常窗口内增幅倍数」和「首次出现时间」是客观信号，融合后排序更稳定、更可解释。
5. **LLM 摘要最常见的幻觉形式是什么？** 答案要点：编造输入里没有的指标名、主机名或故障码；防御手段是在 prompt 里强制「证据必须来自输入」并要求输出 `evidence` 数组，再用代码检查 evidence 是否真的出现在输入中。
6. **日志与指标的时间戳对齐要注意什么？** 答案要点：时区统一（都用 UTC 或都用本地）、采样粒度一致（日志按 5min 聚合、指标也按 5min）、以及时钟漂移；对齐错了后面的增幅统计全部无意义。

### 踩坑提醒

:::warn Drain3 状态文件损坏导致模板 ID 漂移
现象：重启后同一日志拿到了新的 `template_id`，历史统计对不上。解法：`FilePersistence` 路径固定且不要手工编辑；进行增量挖掘前后各做一次 `miner.drain.clusters` 数量校验；把模板文本（不是 id）作为统计主键。
:::

:::warn LLM 返回的 JSON 被 Markdown 围栏包住
报错原文：`json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`。解法：`response_format={"type": "json_object"}` 能大幅降低概率，但仍要写兜底：先 `strip()` 去掉 ```json 围栏，再用 `re.search(r"\{.*\}", text, re.S)` 抽第一个完整对象。
:::

:::warn 日志量太大把内存打爆
现象：读入 1000 万行后进程被 OOM Killer 杀掉。解法：流式逐行处理（不要 `read_text().splitlines()`），Drain3 是增量算法天然支持流式；模板统计用 `Counter` 只存模板文本，不存原始行；需要落盘的中间结果用 parquet 分片。
:::

:::warn 把日志原文直接塞进 prompt 导致费用失控
后果：单次摘要输入 20 万 token，一次几元钱。纪律：只送 Top20 模板 + 计数 + 告警摘要，并用 `[:12000]` 硬截断；在 `docs/` 里记录单次摘要的 token 数与成本，与 W19 的成本护栏口径一致。
:::

```python
# 手撕专项之一：多头注意力（W13 检查点要求，面试最高频）
import math
import torch
import torch.nn as nn


class MultiHeadAttention(nn.Module):
    def __init__(self, d_model: int = 512, n_head: int = 8, dropout: float = 0.1):
        super().__init__()
        assert d_model % n_head == 0, "d_model 必须能被 n_head 整除"
        self.d_model = d_model
        self.n_head = n_head
        self.d_head = d_model // n_head
        self.qkv = nn.Linear(d_model, 3 * d_model, bias=False)
        self.out = nn.Linear(d_model, d_model, bias=False)
        self.drop = nn.Dropout(dropout)

    def forward(self, x, mask=None):
        B, T, C = x.shape
        qkv = self.qkv(x).view(B, T, 3, self.n_head, self.d_head)
        q, k, v = qkv.permute(2, 0, 3, 1, 4)          # (B, H, T, d_head)
        att = (q @ k.transpose(-2, -1)) / math.sqrt(self.d_head)
        if mask is not None:
            att = att.masked_fill(mask == 0, float("-inf"))
        att = self.drop(torch.softmax(att, dim=-1))
        y = (att @ v).transpose(1, 2).contiguous().view(B, T, C)
        return self.out(y)


mha = MultiHeadAttention()
x = torch.randn(2, 16, 512)
print("输出形状:", tuple(mha(x).shape))          # 期望 (2, 16, 512)
```

### 自检题

1. **简历 bullet 为什么必须带数字？** 答案要点：数字是可验证的承诺，也是面试官提问的入口；「效果良好」这种表述无法追问，等于浪费一行空间。

4. **手撕代码为什么要在 15 分钟内限时？** 答案要点：面试是限时环境，练的是「在压力下写出正确且能解释的代码」；超时的题目要归类到「不熟」并针对性重复。

### 踩坑提醒

:::warn 简历写了做不到的技能，面试当场崩
现象：简历写「熟悉 vLLM 高并发部署」，被问「PagedAttention 怎么管理显存」答不上来。解法：**只写有仓库证据的技能**；8GB 显存的事实口径是 vLLM 高并发实用性低，就写「在 8GB 显存上通过 llama.cpp GGUF Q4_K_M + KV 量化实现 38 tok/s 本地推理」，反而更可信。
:::

:::warn 演示视频里命令卡住或报错
原因：现场跑依赖网络下载模型、编译、或需要 API key。解法：提前把模型、数据、依赖全部本地化；视频里跑的是「已经装好的环境」；准备一条 `--dry-run` 路径展示离线可跑；录制前完整彩排两遍并掐表。
:::

:::warn README 里的数字与仓库代码对不上
现象：README 写「Hit@5 = 0.86」，面试官 clone 下来跑 `eval.py` 得到 0.71。原因：改过代码没重跑评测，或数字来自另一个数据集。解法：**每个数字旁边写清生成它的命令**（`python eval_all.py --config b4`），发简历前对每个仓库重跑一次并更新数字。
:::

:::warn 投递台账只记录不跟进
后果：投了 60 家，回访时说不清哪些进了笔试。解法：每条记录必须有 `next_action` 与 `next_date`，每周固定 30 分钟跑一次 `job_tracker.py` 的 `progress()`；笔试/面试时间的临期提醒用手机日历二次备份。
:::

:::danger 不要把公司内部数据或未公开代码放进公开仓库
后果：法律风险与职业信誉受损。纪律：实习或工作中的数据一律脱敏（`<IP>`、`<NUM>`、`<PATH>` 掩码只是第一步，主机名、业务指标名、内部接口名都要替换）；公开仓库只用公开数据集（SMD / HDFS / 自建手册）或自己造的合成数据；离职后也不要把带敏感信息的 commit 推上去。
:::
