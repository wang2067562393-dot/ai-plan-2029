# 第13章 简历、作品集与 GitHub：让你的 12 个项目被看见

这一章解决一件事：把你从 2026-10-05 到 2027-03-21 做出来的 12 个项目，变成 HR 愿意点开、面试官愿意深聊的求职材料。读完你能直接拿出：一份可投递的简历、12 个项目的标准简历句、一个像样的 GitHub 主页、一段 5 分钟演示视频、30 个技术博客选题、40 项自检清单与一张投递台账。所有模板都可以照抄，把示例数字换成你自己的实测数字即可。

## 13.1 招聘方怎么看简历：三轮筛选各看什么、各花多久

### 13.1.1 三轮筛选的真实节奏

简历不是「写给自己看的履历」，而是一份要连续通过三道关卡的文档。每一关的读者注意力不同，你在同一页上要同时满足三个人。

| 环节 | 读者 | 平均停留时间 | 关心的问题 | 致命失分项 |
| --- | --- | --- | --- | --- |
| 初筛（机筛 + HR） | HR / 招聘系统 | 8–20 秒 | 学校专业对不对、毕业时间对不对、有没有相关项目、关键词全不全 | 简历两页以上、没有量化数字、岗位名写错 |
| 一面（技术基础） | 一线算法/开发工程师 | 3–5 分钟 | 技术栈是否真用过、项目是不是自己做的、基础八股是否会 | 技术栈堆砌但一个都讲不深 |
| 二面/三面（项目与设计） | 组长 / 主管 | 5–10 分钟 | 项目有没有难点、有没有评测、能不能落地、成长速度 | 只会调库、没有指标、没有失败分析 |
| 主管终面 / HR 面 | 部门主管 / HRBP | 2–3 分钟 | 稳定性、职业规划、沟通表达、期望薪资 | 规划与岗位对不上、答不出为什么选这方向 |

:::ok 一句话结论
HR 看的是「匹配度和关键词」，技术官看的是「项目真实度和深度」，主管看的是「潜力和稳定性」。同一份简历要同时给出：醒目的岗位关键词 + 可追问的量化项目 + 清晰的方向表述。
:::

### 13.1.2 HR 初筛只看这四个位置

1. **姓名下方一行**：`2029 届 | 目标岗位：大模型应用开发 / Agent 工程师 | 硕士在读（研一）`。毕业年份必须出现，2029 届秋招的系统筛选项就是「2029-06 毕业」。
2. **教育背景**：学校、专业、入学与预计毕业时间（`2025.09–2029.06` 或 `2024.09–2027.06` 本科 + `2027.09–2029.06` 硕士，按你自己的真实学制写），GPA / 排名只在有优势时写。
3. **技能行**：把 JD 里的词原样放进来（`PyTorch`、`LoRA`、`RAG`、`Agent`、`vLLM`、`ONNX Runtime`、`TensorRT`、`FastAPI`、`Docker`）。
4. **项目标题行**：项目名 + 一句话 + 一行数字。HR 只扫这一行就会决定要不要把简历转给技术官。

### 13.1.3 技术官 3 分钟扫读时会停在哪些地方

- 停在**带数字的句子**：`召回率 0.62 → 0.87`、`P99 延迟 420ms → 180ms`、`显存峰值 7.6GB`。
- 停在**他能听懂的架构词**：`Planner–Executor–Critic`、`混合检索 = BM25 + 向量 + Rerank`、`KV Cache 量化`。
- 停在**你自己写的模块**：`手写多头注意力（不调用 nn.MultiheadAttention）`。
- 跳过**纯工具罗列**：`熟悉 Python、了解深度学习、会 Docker`——这三句等于没说。

:::warn 常见致命错误
把课程作业包装成「企业级系统」，但被追问数据量时答「大概几百条」。面试官当天就会在评价里写「项目水分大」。宁可写「自建 1,200 条评测集」，也不要写「企业级」。
:::

### 13.1.6 简历投递前的两次「换位阅读」

**第一遍：用 HR 的眼睛读（限时 20 秒）**

把简历 PDF 打开，计时 20 秒，只允许自己看四个位置：抬头、教育背景、技能行、项目标题行。关掉文件，凭记忆回答三个问题：这人什么岗？什么届？做过什么最相关的项目？

三个问题答不全，说明信息密度不够，回去把关键词提到标题行。

**第二遍：用面试官的眼睛读（限时 3 分钟）**

只做一件事：给每条项目描述写一个「我会追问什么」。写完你会有两个发现：一是有些句子根本没法追问（说明是废话），二是有些句子你自己都答不上来（说明是吹的）。两类句子都要重写，改成你能连续答 3 层的版本。

## 13.2 项目描述公式：动词 + 场景 + 技术方案 + 量化结果 + 难点

### 13.2.1 五段式的固定写法

一条项目句的骨架：

```text
【动词】+【业务场景 + 数据规模】+【技术方案】+【量化结果】+【难点与你的取舍】
```

拆开看每一段的写法：

| 成分 | 要求 | 反例 | 正例 |
| --- | --- | --- | --- |
| 动词 | 强动词开头，一句一个 | 参与了、负责了部分 | 搭建、实现、优化、重构、压测、评测 |
| 场景 | 谁用、多少数据、什么约束 | 做了一个 RAG 系统 | 面向 1,860 份工业设备手册的问答 |
| 技术方案 | 具体到模型名与组件 | 用了大模型和向量检索 | bge-m3 向量 + BM25 混合召回 + bge-reranker-v2-m3 重排 |
| 量化结果 | 前后对比或绝对值，含硬件 | 效果不错 | 召回率 0.62 → 0.87，P99 420ms → 180ms（RTX 4060 Laptop 8GB） |
| 难点 | 一个具体取舍或坑 | 遇到很多困难 | 8GB 显存下 KV Cache 爆显存，改 q8_0 量化后峰值降到 5.9GB |

### 13.2.2 三组「反面示例 → 正面改写」

**第 1 组：RAG 项目（P7）**

反面示例：

```text
使用大模型做了一个知识库问答系统，使用了向量数据库，效果良好。
```

正面改写：

```text
搭建面向 1,860 份工业设备手册的企业知识库问答系统（含 1,200 条自建评测集）：
bge-m3 向量召回 + BM25 混合检索 + bge-reranker-v2-m3 重排 + 引用溯源，
上下文召回率 0.62 → 0.87，答案忠实度（RAGAS）0.71 → 0.89，
端到端 P95 延迟 3.2s → 1.4s；难点：8GB 显存下 reranker 与 7B 生成模型无法同时常驻，
方案是 reranker 用 ONNX Runtime CPU 推理、生成模型走 GGUF Q4_K_M，显存峰值降到 5.9GB。
```

为什么有效：有数据量（1,860 份 / 1,200 条）、有完整链路（召回→重排→溯源）、有三个指标（召回率、忠实度、延迟）、有硬件约束下的真实取舍。

**第 2 组：微调项目（P8）**

反面示例：

```text
对 7B 大模型进行了 LoRA 微调，提升了模型在垂直领域的表现。
```

正面改写：

```text
完成 7B 模型的 QLoRA 微调对齐全链路（医疗问诊，5,800 条 SFT + 1,500 条偏好数据）：
4bit NF4 量化 + LoRA r=16/alpha=32（作用于 q_proj,k_proj,v_proj,o_proj），
seq 512、batch=1、梯度累积 16、梯度检查点、paged_adamw_8bit，单卡 RTX 4060 Laptop 8GB 峰值 7.4GB；
领域评测集准确率 0.54 → 0.72，格式合规率 0.81 → 0.98；
难点：合并适配器时 fp16 基座需约 14GB 显存，改为 CPU 合并 + llama.cpp 转换，
并做 r=8/16/32 三组消融，确认 r=16 是精度与显存的平衡点。
```

为什么有效：超参数全给、数据量全给、显存数字给到小数、有消融实验（这是算法岗最想看的）、有踩坑与替代路径。

**第 3 组：部署优化项目（P6）**

反面示例：

```text
把模型导出为 ONNX 并部署到服务器上，性能有所提升。
```

正面改写：

```text
构建 ONNX / TensorRT / GGUF 三后端统一推理平台并完成压测报告：
同一 MobileNetV3 分类模型 INT8 量化后 ONNX Runtime 延迟 42.3ms → 11.8ms（4.1×）、
模型体积 21.4MB → 5.6MB、ImageNet 子集 top-1 精度 74.2% → 73.1%（-1.1pt）；
7B GGUF Q4_K_M 生成速度 34 tok/s、首 token 延迟 0.62s；
难点：TensorRT engine 与显卡架构绑定，换机器必须重编，
因此把 ONNX 作为跨平台主链路、TensorRT 只做本地加速分支，并用 Docker 固化两套环境。
```

为什么有效：有加速比、有体积、有精度损失（真实汇报必须带精度损失）、有工程判断（为什么不全用 TensorRT）。

### 13.2.3 数字从哪来

| 数字类型 | 怎么测 | 写在哪里 |
| --- | --- | --- |
| 效果指标 | 自建评测集 + 固定随机种子跑 3 次取均值 | 项目第 2 行 |
| 延迟 | `time.perf_counter()` 预热 10 次后测 100 次，报 P50/P95/P99 | 项目第 2 行 |
| 显存 | `torch.cuda.max_memory_allocated()/1024**3` | 项目第 3 行（难点句） |
| 数据规模 | 样本条数、文档页数、时长 | 项目第 1 行 |
| 加速比 | 优化前 ÷ 优化后，写倍数 | 项目第 2 行 |

### 13.2.4 显存与延迟的实测片段（复制到项目里跑）

下面这段代码用来采集「显存峰值 + 延迟分位数」，是简历里绝大多数数字的来源。在 WSL2 或 Windows 的 Python 环境里都能跑。

```python
bench.py：测单次推理的延迟分位与显存峰值（存成 bench.py 后运行 python bench.py）
import time
import statistics

import torch


def bench(fn, warmup: int = 10, iters: int = 100) -> dict:
    """预热 warmup 次后测 iters 次，返回延迟分位数与显存峰值（单位：ms / GB）。"""
    for _ in range(warmup):
        fn()
    torch.cuda.synchronize()

    lat = []
    for _ in range(iters):
        torch.cuda.synchronize()
        t0 = time.perf_counter()
        fn()
        torch.cuda.synchronize()
        lat.append((time.perf_counter() - t0) * 1000)

    lat.sort()

    def pct(p: float) -> float:
        idx = min(len(lat) - 1, int(round(p / 100 * len(lat))) - 1)
        return lat[max(idx, 0)]

    return {
        "p50_ms": round(statistics.median(lat), 2),
        "p95_ms": round(pct(95), 2),
        "p99_ms": round(pct(99), 2),
        "mean_ms": round(statistics.fmean(lat), 2),
        "peak_gb": round(torch.cuda.max_memory_allocated() / 1024**3, 2),
        "iters": iters,
    }


if __name__ == "__main__":
    model = torch.nn.Linear(1024, 1024).cuda().eval()
    x = torch.randn(1, 1024, device="cuda")
    with torch.no_grad():
        print(bench(lambda: model(x)))
```

预期输出（RTX 4060 Laptop 8GB，数值仅示意）：

```text
{'p50_ms': 0.42, 'p95_ms': 0.51, 'p99_ms': 0.58, 'mean_ms': 0.44, 'peak_gb': 0.01, 'iters': 100}
```

采集显存占用的完整写法（先清缓存再测，否则会读到上一次的峰值）：

```python
peak_mem.py：测一段训练/推理过程的显存峰值
import torch

torch.cuda.empty_cache()
torch.cuda.reset_peak_memory_stats()

下面三行就是你要测的那段代码（训练一步、加载模型、跑一次推理）
model = torch.nn.Sequential(
    torch.nn.Linear(2048, 4096), torch.nn.GELU(), torch.nn.Linear(4096, 2048)
).cuda()
out = model(torch.randn(8, 2048, device="cuda"))
out.sum().backward()

print(f"peak allocated = {torch.cuda.max_memory_allocated() / 1024**3:.2f} GB")
print(f"peak reserved  = {torch.cuda.max_memory_reserved() / 1024**3:.2f} GB")
```

预期输出（仅示意）：`peak allocated = 0.32 GB`、`peak reserved = 0.38 GB`。写简历时用 `allocated`，写部署容量规划时用 `reserved`。

:::warn 数字口径要统一
同一个项目里所有数字必须同口径：延迟统一写 P95，召回统一写 Recall@5，显存统一写 peak allocated。面试官一旦发现你同一个指标在两处数字不一致，会认为整份简历都不可信。
:::

### 13.5.4 commit message 规范与示例

用 Conventional Commits：`类型(范围): 简短描述`。首行 ≤ 50 个字符，正文写「为什么」不写「是什么」。

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| feat | 新功能 | `feat(retrieval): add RRF fusion for BM25 and dense results` |
| fix | 修缺陷 | `fix(eval): correct Recall@k when k > retrieved count` |
| perf | 性能优化 | `perf(onnx): enable INT8 dynamic quant, 11.8ms -> 7.2ms` |
| refactor | 重构（不改行为） | `refactor(data): extract chunker into standalone module` |
| docs | 文档 | `docs(readme): add reproduction steps and eval table` |
| test | 测试 | `test(metrics): cover empty-context edge case` |
| chore | 杂项（依赖、配置） | `chore(deps): pin transformers to 4.46.0` |
| exp | 实验记录（个人项目专用） | `exp(lora): r=32 ablation, acc 0.727 (+0.6pt vs r=16)` |

一条带正文的例子：

```text
perf(rerank): move bge-reranker to ONNX Runtime CPU

Why:
- 8GB 显存下 reranker 与 7B 生成模型无法同时常驻，OOM 概率约 30%
- CPU 推理单条 42ms，可接受；显存峰值从 8.1GB 降到 5.9GB

How:
- 导出 ONNX（opset 17）+ INT8 动态量化
- 加 32 条批量打包，CPU 利用率从 38% 提到 71%

Impact: Recall@5 不变（0.871 -> 0.869），P95 延迟 +0.2s
```

:::ok commit 的硬要求
每个项目至少 40 次 commit，分布在多天；不要出现「一天提交全部代码」。面试官很在意「你是不是循序渐进做的」。如果前期的活已经做完，就把实验分支的消融实验补交上去，形成真实的迭代轨迹。
:::

### 13.5.5 开源 LICENSE 怎么选

| LICENSE | 允许商用 | 要求开源衍生 | 专利条款 | 适合场景 |
| --- | --- | --- | --- | --- |
| MIT | 是 | 否 | 无 | **默认选它**，最省事，公司最放心 |
| Apache-2.0 | 是 | 否 | 有 | 你担心专利问题、或项目引用了 Apache-2.0 的代码 |
| BSD-3-Clause | 是 | 否 | 无 | 与 MIT 类似，学术项目常见 |
| GPL-3.0 | 是 | **是（传染）** | 有 | 想强制下游开源；求职项目**不建议** |
| AGPL-3.0 | 是（含 SaaS） | 是 | 有 | 网络服务也必须开源；**不要用在求职项目** |
| 不放 LICENSE | 默认保留全部权利 | — | — | 绝对不要，公司不敢看你的代码 |

操作：GitHub 仓库页面 → Add file → Create new file → 文件名输入 `LICENSE` → 右侧「Choose a license template」→ 选 MIT → 填年份与你的名字 → Commit。

### 13.5.6 模型权重的许可与合规提示

:::warn 适配器的许可
你微调出来的适配器（adapter）要单独看基座模型的许可（Qwen 系列、Llama 系列各有自己的条款）。README 里写清基座模型名与许可，不要把一个 Llama 系微调权重标成 MIT 就发布。数据来源同样要写清：如果用了他人的数据集，标注名称与许可；如果用了公司内部数据，**一个字节都不要上传**。
:::

### 13.5.7 从零把一个项目推上 GitHub（完整命令）

在项目根目录执行下面的 PowerShell 命令，一次走完建仓、配置、提交、推送。前提是已装 Git 并在 GitHub 建好空仓库。

```powershell
Write-Host "步骤 2) 初始化并写 .gitignore（排除大文件与数据）"

@"
.venv/
__pycache__/
*.pyc
data/
outputs/
reports/*.json
*.pt
*.gguf
*.onnx
.env
"@ | Out-File -Encoding utf8 .gitignore

Write-Host "步骤 3) 首次提交"
git add .
git commit -m "chore: init repo with project skeleton"

Write-Host "步骤 4) 关联远端并推送（把 <用户名>/<仓库名> 换成你的）"

```

预期输出：`git push` 后打印 `branch 'main' set up to track 'origin/main'`，浏览器刷新仓库页面能看到文件。


### 13.5.9 演示 GIF / 截图的制作方法
| 用途 | 工具（Windows） | 关键设置 | 体积目标 |
| --- | --- | --- | --- |
| 短 GIF（10–20 秒，README 首屏） | ScreenToGif（开源，免安装） | 15 fps、宽 960px、只录窗口 | ≤ 4MB |
| 长录屏（5 分钟视频） | OBS Studio 或 Windows 自带 Xbox Game Bar（Win+G） | 1920x1080、30 fps、麦克风 + 系统声音分轨 | 200–500MB |
| 静态截图标注 | ShareX / Snipaste | 加箭头与编号，统一深色或浅色主题 | ≤ 300KB/张 |
| 终端录制 | asciinema（WSL2 里 `pip install asciinema`） | 录 `make smoke` 全过程 | 文本，极小 |
| 视频压缩 | HandBrake | 1080p → 720p、CRF 26、AAC 128k | 压到 1/3 |

录制建议（按重要性排序）：

1. **先写脚本再录**：把要说的每句话、要点的每个按钮写成文字稿，按稿录，一遍就过。
2. **分辨率统一**：浏览器窗口固定 1440x900，不要录整个 2560 宽屏桌面，字会看不清。
3. **放大字号**：终端字号 16–18，浏览器缩放 125%，代码编辑器 16。
4. **关通知**：Windows 专注助手打开，微信/QQ 退出。
5. **第一屏就是结果**：GIF 前 3 秒要出现「提问 → 带引用的答案」，不要从 `pip install` 开始录。
6. **放真实数据**：用真实文档里的一页做演示，别用 lorem ipsum。
7. **加字幕**：ScreenToGif 支持逐帧加文字；视频用剪映自动识别字幕再人工改。
8. **GIF 放 `docs/` 目录**，README 用相对路径引用，不要传网盘链接。

终端录制示例（在 WSL2 里执行，录完输出一个 `.cast` 文件，可嵌到 README 的 asciinema 播放器）：

```bash
下面是录制一次冒烟测试（bash 注释用行首井号），录完输入 exit 停止
asciinema rec docs/smoke.cast -c "make smoke" --idle-time-limit 2
```

预期输出：当前目录出现 `docs/smoke.cast`，文本格式，几百 KB。

### 13.6.2 每一段的具体台词骨架（可直接改写）

**第 1 段（自我介绍）**

```text

```

**第 2 段（问题背景）**

```text
<场景> 下，<使用者> 每次查资料要翻 <多少> 份文档，平均 <多少> 分钟才能找到一处。
原来的关键词检索有三个问题：一是同义说法搜不到，二是命中段落太长要自己读，三是没有出处不敢用。
我的目标很具体：把找资料的时间压到 30 秒以内，并且每条答案都能点回原文。
```

**第 3 段（方案总览）**

```text
整个链路四层。数据层把 PDF 与 Word 解析成文本，按 512 字切块、重叠 128 字。
检索层用 bge-m3 做向量召回、BM25 做字面召回，两路用 RRF 融合，再用 bge-reranker-v2-m3 重排。

服务层是 FastAPI，用 SSE 流式返回，前端每 30 毫秒刷新一次。
我独立完成的是检索融合、重排与评测三部分。
```

**第 4 段（现场演示）**

```text

可以看到左边滚动了检索日志：BM25 命中 3 段、向量命中 5 段、融合后 5 段，重排后前 3 段打分分别是 0.91、0.44、0.31。

系统没有编，它回答「检索到的资料里没有相关信息」，并给出最接近的两段让人工判断。
这就是我要的拒答行为。
```

**第 5 段（难点 1：显存）**

```text
这台机器只有 8GB 显存，实际可用约 7GB。
最开始的方案里，重排模型 1.2GB 加上生成模型 4.4GB 加 KV Cache，峰值到 8.1GB，直接 OOM。
我做了三件事：重排改走 ONNX Runtime 的 CPU 推理，生成模型用 Q4_K_M，KV Cache 用 q8_0。
```

### 13.6.5 用 Markdown 做一份 8 页项目 PPT（可导出 PDF）

不要用花哨模板。用 Marp 或 Slidev 写 Markdown 再导出 PDF，版本可控。页面结构固定 8 页：

```text
第1页 标题：项目名 + 你的姓名 + 目标岗位 + 三个关键数字
第2页 问题：场景、数据规模、原做法差在哪（1 张图 + 3 个要点）
第3页 方案：架构图（分层），标出你负责的部分
第4页 演示：2 张界面截图（提问前 / 提问后带引用）
第5页 难点一：显存账本（表格：权重/适配器/激活/KV Cache 各占多少）
```

### 13.7.3 文章结构模板：问题 → 方案 → 实验 → 结论 → 踩坑

```text
标题：具体动作 + 具体对象 + 具体结果
例：《8GB 显存跑 7B QLoRA：显存峰值从 8.1GB 压到 7.4GB 的逐项拆解》

【一、问题】
- 我遇到的具体现象（含报错原文，单独用代码块包起来）
- 复现条件：硬件、版本、数据规模、命令
- 为什么这个问题值得写（别人也会遇到）

【二、方案】
- 候选方案列表（至少 3 个），每个写清代价
- 我选了哪个、为什么（给判断标准，不给感觉）
- 关键代码（完整可运行，不省略）

【三、实验】
- 变量与对照组（一次只动一个变量）
- 表格：配置 / 指标 / 耗时 / 显存
- 固定随机种子与重复次数；给出波动范围

【四、结论】
- 3 条可复用的结论，每条一句话，能被别人直接抄走
- 适用边界：什么情况下这套结论不成立

【五、踩坑】
- 每条坑写：现象 -> 原因 -> 解法 -> 验证方式
- 至少 3 条，最多 8 条

【六、参考】
- 官方文档与论文链接（不要放二手博客）
```
