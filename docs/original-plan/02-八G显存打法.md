# 第2章 8GB 显存的真实打法：能做、不能做、以及怎么做

这一章是整份规划的地基约束。每次遇到「跑不动」，回到这一章按流程走一遍，99% 的问题都能在不买卡的前提下解决。

先记住一句话：**4060 Laptop 是 Ada 架构（sm_89）、8GB GDDR6、带宽约 256GB/s、整卡功耗 35–115W。笔记本内屏会占用 0.3–1GB 显存，实际可用约 7GB。** 这 0.5GB 往往就是「能不能启动」的分界线。

## 2.1 先量一下你的真实可用显存（5 分钟）

在 PowerShell 或 WSL2 Bash 里执行，看当前显存占用：

```bash
nvidia-smi
```

预期输出关键字段（示例）：

```text
+-----------------------------------------------------------------------------+
| NVIDIA-SMI 566.xx       Driver Version: 566.xx       CUDA Version: 12.7     |
|-------------------------------+----------------------+----------------------+
| GPU  Name            TCC/WDDM | Bus-Id        Disp.A | Volatile Uncorr. ECC |
| Fan  Temp  Perf  Pwr:Usage/Cap|         Memory-Usage | GPU-Util  Compute M. |
|===============================+======================+======================|
|   0  NVIDIA GeForce ... WDDM  | 00000000:01:00.0 Off |                  N/A |
| N/A   52C    P8    12W /  90W |    842MiB /   8188MiB |      1%      Default |
+-------------------------------+----------------------+----------------------+
```

**842MiB / 8188MiB 就是被桌面与浏览器占掉的部分。** 训练前先把它压到 300MiB 以下。

:::ok 三件事立刻做
1. 关掉浏览器（尤其是有硬件加速的 Chrome/Edge），或至少关掉视频页面与本地 LLM 网页。
2. 关掉 Ollama、LM Studio 等本地模型服务（`ollama ps` 看有没有驻留模型，用 `ollama stop <model>` 卸载）。
3. 训练前接外接显示器或干脆合盖用远程桌面，内屏占用的显存会下降。
:::

### 用代码量出「你的模型到底吃多少显存」

把下面这段保存为 `vram_probe.py`，在项目环境里运行。它会告诉你空闲显存、加载模型后的占用、以及一次前向的峰值。

```python
import torch, gc, time

def human(n):
    return f"{n / 1024 ** 3:.2f} GB"

def report(tag):
    torch.cuda.synchronize()
    free, total = torch.cuda.mem_get_info()
    alloc = torch.cuda.memory_allocated()
    peak = torch.cuda.max_memory_allocated()
    print(f"[{tag}] 已分配 {human(alloc)} | 峰值 {human(peak)} | 系统剩余 {human(free)} / {human(total)}")

print("设备:", torch.cuda.get_device_name(0))
report("空闲")

x = torch.randn(4096, 4096, device="cuda", dtype=torch.bfloat16)
report("张量 4096x4096 bf16")
y = x @ x
report("矩阵乘之后")

del x, y
gc.collect()
torch.cuda.empty_cache()
torch.cuda.reset_peak_memory_stats()
report("清理之后")
```

预期输出（数值仅供参考，关键是学会看「峰值」）：

```text
设备: NVIDIA GeForce RTX 4060 Laptop GPU
[空闲] 已分配 0.00 GB | 峰值 0.00 GB | 系统剩余 6.90 GB / 8.00 GB
[张量 4096x4096 bf16] 已分配 0.03 GB | 峰值 0.03 GB | 系统剩余 6.87 GB / 8.00 GB
[矩阵乘之后] 已分配 0.06 GB | 峰值 0.09 GB | 系统剩余 6.81 GB / 8.00 GB
[清理之后] 已分配 0.00 GB | 峰值 0.00 GB | 系统剩余 6.90 GB / 8.00 GB
```

:::warn 两个容易误判的地方
- `torch.cuda.memory_allocated()` 是 PyTorch 分配器视角，**不等于** `nvidia-smi` 显示的占用（后者含缓存与 CUDA 上下文，通常多 200–600MB）。
- 判断会不会 OOM 看 **峰值（max_memory_allocated）**，不是当前值。训练时必须把峰值打出来，否则不知道自己离悬崖多远。
:::

## 2.2 能做 / 不能做清单

### ✅ 绰绰有余（本机直接做，覆盖 80% 以上的学习内容）

- 深度学习基础训练：CNN / RNN / 小 Transformer、CIFAR、IMDB 级数据集全速跑。
- 视觉任务：YOLOv8n/s、MobileNet、EfficientNet-lite、U-Net 小尺寸的**完整训练与部署**。
- 时序异常检测：Anomaly Transformer / TimesNet / PatchTST 在 SMD/SWaT/PSM 上训练（模型很小）。
- 日志与 NLP 小模型：BERT-base 文本分类 / NER、≤200M 参数模型的微调。
- **7B/8B 模型的 QLoRA 微调**（4bit NF4 + LoRA + 梯度检查点，序列 512 起步、1024 为极限，batch 1 + 梯度累积）。
- **约 0.5B 模型的全量微调**（如 `Qwen/Qwen3-0.6B`，bf16 + 梯度检查点）。
- 推理与部署：7B/8B GGUF Q4_K_M（llama.cpp / Ollama，约 30–50 tok/s）、ONNX / TensorRT 导出与 benchmark。
- RAG / Agent / 后端服务：向量库、LangGraph、FastAPI、Docker 全套本地跑。
- 评测：用 API 或本地 4B 模型跑评测集、RAGAS 评测。

### ❌ 本机做不了（必须租云或换思路）

| 做不了的事 | 为什么 | 替代方案 |
| --- | --- | --- |
| 1.5B–3B 全量微调 | 需 24–48GB（8G 上限约 0.5B） | 换 ≤0.5B，或改 LoRA |
| 7B 以上全量微调 / 预训练 | AdamW 状态 + 梯度 + 激活 ≈ 16 bytes/参数，7B 需 ≥112GB | 只做 LoRA/QLoRA；对比实验租一次云 |
| 大规模 RLHF / GRPO（>3B） | 需同时驻留策略、参考、奖励模型 | 数据蒸馏：用 API 造 CoT 数据再 QLoRA 小模型 |
| MoE 训练、32K 长上下文训练 | 参数量与激活显存都超标 | 用现成 MoE 模型做推理与调研，不训练 |
| SDXL 级扩散模型全量微调 | 需 24GB+ | LoRA / DreamBooth LoRA 可以 |
| **7B 适配器合并** | 合并需 fp16 基座约 14GB | CPU 上合并（`device_map="cpu"`）或用 llama.cpp 的转换工具 |
| vLLM 高并发服务 | KV Cache 必须常驻显存，8G 实用性低；Windows 需 WSL2 | 用 llama.cpp / Ollama |

## 2.3 三个必须张口就来的显存公式

| 场景 | 公式 | 7B 实例 | 对你的意义 |
| --- | --- | --- | --- |
| 全量微调 | bf16 权重 2 + bf16 梯度 2 + fp32 主权重 4 + AdamW 一阶 4 + 二阶 4 ≈ **16 bytes/参数**（再加激活） | 0.5B×16B=8GB（极限）；1.5B×16B=24GB；7B×16B=112GB+ | 8G 上限约 0.5B；1B 全量只能靠 8bit 优化器（约 6 bytes/参数 ≈ 6GB）极限玩法 |
| LoRA / QLoRA | 冻结权重 fp16 ≈ 2B/参数；**QLoRA 4bit ≈ 0.5B/参数**，再加适配器与其优化器、激活 | 7B×0.5B≈3.9–4.3GB + 适配器/优化器 0.3–0.8GB + 激活 1–2GB ≈ 峰值 **6.5–7.8GB** | 8G 的甜蜜点：7B/8B QLoRA 可训，**序列必须 ≤512（1024 极限，2048 必 OOM）** |
| 推理（KV Cache） | KV ≈ 2(K,V) × 2 字节 × KV 头数 × 头维 × 层数 × 序列长 × batch | 7B bf16 权重 14GB（放不下）；**7B Q4_K_M ≈ 4.4GB + KV 1–2GB ≈ 6GB ✅** | 量化推理是 8G 的标准姿势；`--cache-type-k q8_0 --cache-type-v q8_0` 可把 KV 砍半 |

### 动手算一遍：写个估算器

把下面存成 `estimate_vram.py`，以后换模型先算再跑，能省下大量 OOM 时间。

```python
def qlora_gb(params_b, seq_len, batch=1, hidden=4096, layers=32, bytes_per_param=0.5):
    """粗略估算 QLoRA 训练峰值显存（GB），误差约 ±20%。"""
    weights = params_b * 1e9 * bytes_per_param / 1024 ** 3        # 4bit 冻结权重
    adapter = params_b * 1e9 * 0.01 * 4 / 1024 ** 3               # 适配器+优化器，约 1% 参数的 fp32 状态
    act = batch * seq_len * hidden * layers * 2 / 1024 ** 3       # 激活（开梯度检查点后的量级）
    return weights, adapter, act

def full_ft_gb(params_b):
    """全量微调（AdamW，bf16 计算）近似：16 bytes/参数。"""
    return params_b * 1e9 * 16 / 1024 ** 3

def kv_gb(layers, kv_heads, head_dim, seq_len, batch=1, bytes_per=2):
    """KV Cache 显存（GB），GQA 模型用 kv_heads 而不是总头数。"""
    return 2 * bytes_per * layers * kv_heads * head_dim * seq_len * batch / 1024 ** 3

for p in (0.6, 1.7, 4, 7, 8, 14):
    w, a, act = qlora_gb(p, 512)
    print(f"QLoRA {p}B seq512: 权重 {w:.2f} + 适配器 {a:.2f} + 激活 {act:.2f} = 峰值约 {w+a+act:.2f} GB")

print()
for p in (0.5, 1.5, 3, 7):
    print(f"全量微调 {p}B: 约 {full_ft_gb(p):.1f} GB")

print()
# 以 Qwen3-8B 为例：36 层、8 个 KV 头、头维 128
for s in (2048, 8192, 32768):
    print(f"8B 模型 KV Cache seq={s}: 约 {kv_gb(36, 8, 128, s):.2f} GB")
```

预期输出量级：

```text
QLoRA 7B seq512: 权重 3.26 + 适配器 0.27 + 激活 0.50 = 峰值约 4.03 GB
QLoRA 8B seq512: 权重 3.73 + 适配器 0.30 + 激活 0.50 = 峰值约 4.53 GB
全量微调 0.5B: 约 7.5 GB
全量微调 1.5B: 约 22.4 GB
全量微调 7B: 约 104.3 GB
8B 模型 KV Cache seq=8192: 约 1.50 GB
```

:::tip 估算器怎么用
估算值 ≤5.5GB → 直接跑；5.5–7GB → 把序列砍半、开梯度检查点、用 `paged_adamw_8bit`；>7GB → 换更小模型或降 4bit。**永远留 0.5GB 余量给桌面与 CUDA 上下文。**
:::

## 2.4 五个把 8G 用到极致的工程手段

| 手段 | 怎么做 | 效果 | 代价 |
| --- | --- | --- | --- |
| 1. 4bit 量化训练 | `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16)` | 冻结权重从 2B/参数降到 0.5B/参数 | 计算时反量化，速度略降 |
| 2. 梯度检查点 | `gradient_checkpointing=True` + `model.enable_input_require_grads()` | 激活显存降 50–70% | 速度降 20–30% |
| 3. 8bit 分页优化器 | `optim="paged_adamw_8bit"` | 优化器状态省约 75%，峰值时换页到内存防 OOM | 略慢 |
| 4. 控制序列与精度 | `max_seq_length=512` 起步；一律 bf16（Ada 支持，fp16 易梯度溢出）；设 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | 激活显存近似线性下降 | 长文本任务要拆样本 |
| 5. 先本地调通再上云 | 用 0.5B 或 100 条数据本地跑通脚本，云上只换路径与参数 | 云上按小时计费不浪费在 debug 上 | 多写一层配置 |

:::danger 千万别用 `optim="adamw_torch"` 跑 8G 微调
它会把 fp32 优化器状态全塞进显存，7B 的 LoRA 也会直接 OOM。必须用 `paged_adamw_8bit` 或 `adamw_8bit`。
:::

## 2.5 遇到 CUDA out of memory 的排查流程（按顺序做）

```text
1. nvidia-smi 看是谁占了显存
   ├─ 桌面/浏览器占 >1GB  → 关浏览器硬件加速、关本地模型服务，重试
   ├─ 有残留 python 进程   → taskkill / kill -9 掉，重试
   └─ 只有自己              → 往下
2. 报错里看「Tried to allocate X MiB」和「GPU 0 has a total capacity of 8.00 GiB of which Y MiB is free」
   ├─ Y 很小（<1GB）     → 是碎片或泄漏：加 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True，重启进程
   └─ Y 还有 3GB 以上     → 是峰值不够：降 max_seq_length（512→384→256）
3. 还不行 → 按性价比依次降：
   batch_size 1 → 开梯度检查点 → 关 double quant 之外的多余特性 → 换 4bit → 换更小模型（8B→4B→1.7B）
4. 还是不行 → 确认任务是否本来就超出 8G（对照 2.2 表格），走租云或换思路
```

对应的环境变量设置：

```powershell
# 在 PowerShell 中，仅对当前窗口生效
$env:PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"
python train.py
```

```bash
# 在 WSL2 Bash 中
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
python train.py
```

:::warn 「显存明明够却 OOM」的三个真实原因
- 前一次实验的进程没退干净（Jupyter 里尤其常见）：`nvidia-smi` 查到 PID 后杀掉，或重启内核。
- `max_memory` 碎片：连续加载多个模型而不 `empty_cache()`。
- Windows WDDM 的显存管理比 Linux 保守，同样的配置在 WSL2 里往往能多跑 300–500MB。**长序列微调优先在 WSL2 里跑。**
:::

## 2.6 什么时候该租云 GPU（附预算与纪律）

| 场景 | 推荐卡型 | 时长 | 大致花费 | 备注 |
| --- | --- | --- | --- | --- |
| 7B 全参数微调（只为对比 LoRA 效果） | 1×A100 40G | 4–8 小时 | 60–200 元 | 只做一次，结论写进博客；不是学习路径 |
| 13B/32B QLoRA 实验 | 1×A100 80G | 6–12 小时 | 150–500 元 | 只做「有无对比」，不必训完 |
| 大规模评测（几千条样本） | API（不等卡） | 数小时 | 20–100 元 | 8G 用户最划算的「算力」 |
| GRPO / 强化学习小实验 | 1×A100 80G | 8–20 小时 | 200–800 元 | 可选；更推荐数据蒸馏 |
| 端侧部署压测 | 本机 4060 | — | 0 元 | 量化、导出、延迟测试全部本机 |

:::danger 租云三条纪律
1. **本地先调通再上云。** 用 0.5B 模型或 100 条数据本地跑通脚本，云上只换路径和参数。
2. **数据和代码提前传好。** 用网盘/对象存储（OSS/S3）传数据集，别在 SSH 里慢慢拖；检查点及时下载，实例释放后本地盘不保留。
3. **设预算上限和自动关机。** 训练脚本加 `timeout` 与保存间隔，用完立刻释放。忘关一晚上 A100 就是几百块。
:::

完整的租云操作步骤（AutoDL 选卡 → 镜像 → 上传 → 训练 → 下载 → 释放）见第 9 章 9.12。

## 2.7 不用租云也能做的替代方案（优先级从高到低）

1. **缩小模型**：`Qwen/Qwen3-0.6B` / `1.7B` / `4B` 在中文任务上已经够用，做对比实验完全成立。
2. **缩小数据**：5k–20k 条高质量样本做指令微调，效果往往好过 100k 条脏数据（数据质量 > 数量）。
3. **冻结大部分参数**：只训 LoRA、只训最后几层、只训分类头。
4. **用预训练权重**：80% 的项目只需要微调和部署，不需要从头训练。
5. **借实验室机器**：哪怕共享一台 3090/4090，也比你一个人卡在 8G 上强；主动问师兄师姐的排期。
6. **用免费额度**：Colab（T4 16G）、Kaggle（P100）适合跑验证想法的小实验，注意时长与断线。
7. **走数据蒸馏绕开大算力**：用 API 大模型生成思维链与标注数据，再 QLoRA 微调 4B 小模型——这是 8G 做出「推理类」效果最现实的路径（代码见第 9 章 9.11）。
8. **改选 ORPO / SimPO 而非 DPO**：DPO 要同时驻留策略与参考模型（约 2× 显存），8G 上只有 2B–4B 的 4bit 可行。
